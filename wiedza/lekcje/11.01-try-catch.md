# Lekcja 11.1 — `try`, `catch`, `finally`

## Cel
Po lekcji uczeń:
- Łapie wyjątek przez `try` / `catch` i program nie przewraca się
- Łapie **konkretny** typ wyjątku, nie wszystko naraz
- Wie, że `finally` wykonuje się zawsze — także po `return`
- Rozumie, kiedy `TryParse` jest lepszy od `try`/`catch`, a kiedy odwrotnie
- Rozpoznaje `CS0160` (nieosiągalny `catch`)

> **Uczeń zna wyjątki od lekcji 2.3** — widział ich cztery różne rodzaje i za każdym razem program się przewracał. Dziś dowiaduje się, co z tym zrobić.

## Krok 1 — Zakotwiczenie (5 min)

**Pytanie wejściowe:**
> „Prosisz kogoś: »przynieś mi teczkę z półki«. Półki nie ma. Co ta osoba może zrobić?"

**Co chcesz usłyszeć trzy możliwości:** wrócić i powiedzieć, że nie ma; przynieść cokolwiek innego; stanąć i czekać.

**Drugie pytanie:**
> „Która z tych reakcji jest najgorsza?"

**Co chcesz usłyszeć:** przyniesienie czegoś innego — bo **nie wiesz, że coś poszło źle**.

**Trzecie pytanie:**
> „A gdyby ta osoba po prostu przestała pracować i wyszła z budynku?"

To jest dokładnie to, co robił twój program: `Unhandled exception` i koniec. **Wyjątek nieobsłużony zatrzymuje wszystko.**

## Krok 2 — Mostek (12 min)

Przypomnij uczniowi lekcję 2.3:

```csharp
int liczba = int.Parse("abc");
```
→
```
Unhandled exception. System.FormatException: The input string 'abc' was not in a correct format.
```

> „Zwróć uwagę na pierwsze słowo: **Unhandled** — nieobsłużony. Sugeruje, że dałoby się go obsłużyć."

**Mostek:**
> „Kod, który może się nie udać, otacza się blokiem `try`. Reakcję na porażkę pisze się w `catch`."

Uczeń tworzy `kurs/zadania/32-try-catch.cs`:

```csharp
try
{
    int liczba = int.Parse("abc");
    Console.WriteLine(liczba);
}
catch (FormatException e)
{
    Console.WriteLine("To nie jest liczba.");
    Console.WriteLine($"Szczegóły: {e.Message}");
}

Console.WriteLine("Program idzie dalej.");
```
→
```
To nie jest liczba.
Szczegóły: The input string 'abc' was not in a correct format.
Program idzie dalej.
```

**Pytania:**
- „Czy `Console.WriteLine(liczba)` się wykonało?" → **nie.** Po wyjątku reszta `try` jest pomijana.
- „Co jest w nawiasach przy `catch`?" → **typ** wyjątku, który łapiemy, i zmienna z jego opisem
- „Skąd wiedziałeś, że to `FormatException`?" → z komunikatu, który widziałeś w 2.3

Nazwij: **wyjątek**, **rzucenie** (`throw`), **złapanie** (`catch`), **blok `try`**.

> **Wyjątek nie jest błędem programisty** — jest **sytuacją**, którą program ma przewidzieć. Plik może nie istnieć, użytkownik może wpisać bzdurę, sieć może paść.

## Krok 3 — Eksperyment (25 min)

### A. Łap konkretny typ, nie wszystko

```csharp
try
{
    int[] tablica = new int[2];
    Console.WriteLine(tablica[5]);
}
catch (IndexOutOfRangeException)
{
    Console.WriteLine("Sięgnąłeś poza tablicę.");
}
```

> „Zauważ: w nawiasie jest sam typ, bez nazwy zmiennej. Kiedy tak można?"
→ gdy nie potrzebujesz szczegółów, tylko reakcji.

Teraz niech uczeń **zamieni** typ na `FormatException` i uruchomi ponownie.
→ program się przewraca. **`catch` łapie tylko to, co obiecał.**

### B. Kilka `catch` — kolejność ma znaczenie

```csharp
try
{
    string wpis = Console.ReadLine();
    int liczba = int.Parse(wpis);
    int wynik = 100 / liczba;
    Console.WriteLine(wynik);
}
catch (FormatException)
{
    Console.WriteLine("To nie liczba.");
}
catch (DivideByZeroException)
{
    Console.WriteLine("Nie dzielę przez zero.");
}
```

Uczeń testuje trzema wejściami: `5`, `abc`, `0`.

> „Ile bloków `catch` wykonuje się przy jednym wyjątku?"
→ **dokładnie jeden** — pierwszy pasujący. To ta sama zasada co `else if` z lekcji 4.1.

Teraz odwróć kolejność i dodaj `Exception` na początku:
```csharp
catch (Exception) { }
catch (FormatException) { }
```
→ `CS0160: A previous catch clause already catches all exceptions of this or of a super type ('Exception')`

> „Czemu kompilator protestuje?"
→ `Exception` jest **klasą bazową wszystkich wyjątków** (dziedziczenie z modułu 9!). Skoro łapie wszystko, to drugi `catch` nigdy by nie zadziałał.

**Zasada: od najbardziej szczegółowego do najbardziej ogólnego.**

### C. `finally` — wykonuje się zawsze

```csharp
try
{
    Console.WriteLine("próbuję");
    int x = int.Parse("abc");
}
catch (FormatException)
{
    Console.WriteLine("złapane");
}
finally
{
    Console.WriteLine("finally");
}
```
→ `próbuję`, `złapane`, `finally`

Teraz zamień `"abc"` na `"42"`:
→ `próbuję`, `finally` — **bez** `catch`.

> „Kiedy wykonuje się `finally`?"
→ **zawsze**: i gdy się udało, i gdy nie.

Najciekawszy przypadek:
```csharp
int Test()
{
    try
    {
        return 1;
    }
    finally
    {
        Console.WriteLine("finally mimo return");
    }
}

Console.WriteLine(Test());
```
→ `finally mimo return`, potem `1`

> „`return` kończy metodę, a `finally` i tak się wykonało. Do czego to służy?"
→ do **sprzątania**: zamknięcia pliku, zwolnienia zasobu. Coś, co musi się stać niezależnie od tego, jak wyszło.

To jest zapowiedź `using` z lekcji 11.2.

### D. `try`/`catch` kontra `TryParse`

Uczeń zna `TryParse` od lekcji 2.3. Zestaw obie drogi:

```csharp
// wersja A
try
{
    int liczba = int.Parse(wpis);
    Console.WriteLine(liczba);
}
catch (FormatException)
{
    Console.WriteLine("nie liczba");
}

// wersja B
if (int.TryParse(wpis, out int liczba))
{
    Console.WriteLine(liczba);
}
else
{
    Console.WriteLine("nie liczba");
}
```

> „Obie robią to samo. Która jest lepsza?"

**Wersja B** — i to jest ważna zasada:

> **Wyjątki są od sytuacji wyjątkowych.** Zły wpis użytkownika **nie jest** wyjątkowy — zdarza się stale. Jeśli istnieje metoda `TryCoś`, używaj jej.

> „Kiedy w takim razie `try`/`catch`?"
→ gdy **nie ma** wersji `Try`: przy plikach (moduł 12), sieci, bazach danych. I gdy błąd naprawdę jest niespodzianką.

### E. `Exception` — łapanie wszystkiego

```csharp
try
{
    // coś ryzykownego
}
catch (Exception e)
{
    Console.WriteLine($"Coś poszło nie tak: {e.Message}");
}
```

> „To działa i czasem jest potrzebne. Co jest w tym niebezpiecznego?"
→ łapie **także** błędy, których się nie spodziewałeś — w tym literówki we własnym kodzie. Program „działa", a wynik jest zły.

**Zasada:** łap `Exception` tylko na **samym końcu** programu, żeby zamiast białej ściany tekstu pokazać użytkownikowi zdanie po polsku.

### F. Co jest w obiekcie wyjątku

```csharp
catch (FormatException e)
{
    Console.WriteLine(e.Message);
    Console.WriteLine(e.GetType().Name);
}
```

| Właściwość | Zawiera |
| --- | --- |
| `Message` | opis po ludzku |
| `GetType().Name` | nazwa typu wyjątku |
| `StackTrace` | ślad, skąd wyjątek przyszedł |

> „`StackTrace` to te linie z nazwami plików, które widziałeś przy każdym przewróconym programie. Przy szukaniu błędu są najważniejsze."

## Krok 4 — Pogłębienie (10 min)

**Wyjątki, które uczeń już poznał**

| Wyjątek | Kiedy | Lekcja |
| --- | --- | --- |
| `FormatException` | `Parse` na tekście, który nie jest liczbą | 2.3 |
| `DivideByZeroException` | dzielenie całkowite przez zero | 2.4 |
| `IndexOutOfRangeException` | indeks poza tablicą | 6.1 |
| `KeyNotFoundException` | brak klucza w słowniku | 6.3 |
| `NullReferenceException` | użycie obiektu, którego nie ma | 8.1 |
| `InvalidOperationException` | `Sort()` bez `IComparable`, zmiana kolekcji w `foreach` | 6.2, 10.2 |

> „Wszystkie dziedziczą po `Exception`. To dlatego `catch (Exception)` łapie każdy z nich."

To domyka dziedziczenie z modułu 9 na konkretnym, praktycznym przykładzie.

**Czego nie robić**

```csharp
catch (Exception) { }
```
> „Pusty `catch` to najgorsza rzecz w tej lekcji: błąd znika bez śladu, a program udaje, że wszystko gra. To jest »przyniósł cokolwiek innego« z kroku 1."

**Kiedy nie łapać wcale**

> „Jeśli nie wiesz, co zrobić z wyjątkiem — **nie łap go**. Niech poleci wyżej, do kogoś, kto wie. Program, który się przewraca z czytelnym komunikatem, jest lepszy niż program, który po cichu robi bzdury."

**Koszt**

> „Rzucenie wyjątku jest kosztowne — dużo droższe niż zwykłe `if`. Dlatego nie używa się wyjątków do sterowania normalnym przebiegiem programu."

To drugi argument za `TryParse` z kroku 3.D.

## Krok 5 — Ćwiczenie

→ Skill `cwiczenie`. Temat: „`try`/`catch`". Propozycje:

- 🔥 **Rozgrzewka** (`32-try-catch-a.cs`): napisz program dzielący dwie liczby wpisane przez użytkownika. Złap `FormatException` i `DivideByZeroException` osobno, każdy z własnym komunikatem. Sprawdź na trzech wejściach.
- ⭐ **Główne** (`32-try-catch-b.cs`): kalkulator z tablicą. Utwórz tablicę pięciu liczb. Pytaj użytkownika o indeks i wypisuj element, dopóki nie wpisze `koniec`. Obsłuż: zły indeks (`IndexOutOfRangeException`) i tekst zamiast liczby — **przy czym drugą sytuację załatw przez `TryParse`, nie przez `catch`**. W komentarzu napisz mi, czemu tak.
- ⚡ **Gwiazdka** (`32-try-catch-c.cs`): napisz metodę `int BezpiecznieOdczytaj(int[] tablica, int indeks)`, która zwraca element albo zero przy złym indeksie — używając `try`/`catch`. Potem napisz **drugą** wersję tej samej metody **bez** wyjątków, samym `if`. Uruchom obie w pętli po dziesięć tysięcy razy ze złym indeksem, mierząc czas przez `System.Diagnostics.Stopwatch`. Wklej mi oba czasy i powiedz, co z nich wynika.
- 🔧 **Naprawa** (`wiedza/przyklady/zepsute/32-try-catch-zepsute.cs`): po wpisaniu `abc` program wypisuje `Podwojone: 0` i kończy się jak gdyby nigdy nic. Znajdź, gdzie **ginie** informacja o błędzie. Napraw na dwa sposoby: z `catch`, który mówi użytkownikowi, co się stało, i bez `try` w ogóle (lekcja 2.3). Który jest lepszy tutaj?

Gwiazdka pokazuje koszt wyjątków **liczbą**, a nie zapewnieniem. To najlepszy argument za `if` tam, gdzie `if` wystarcza.

## Pułapki

- **`catch` na złym typie** — wyjątek nie zostaje złapany i program się przewraca mimo `try`.
- **`catch (Exception)` przed szczegółowym** → `CS0160`.
- **Pusty `catch`** — błąd znika bez śladu. Najgorszy nawyk tej lekcji.
- **`try`/`catch` zamiast `TryParse`** — działa, ale jest wolniejsze i mówi „to sytuacja wyjątkowa", gdy nie jest.
- **Kod po wyjątku w bloku `try`** — nie wykona się. Objaw: „przecież tam jest `WriteLine`".
- **Zmienna zadeklarowana w `try`** — nie jest widoczna w `catch` ani po bloku (zasięg z 7.3).
- **Łapanie wyjątku tylko po to, żeby go wypisać i iść dalej** — zwykle znaczy, że program powinien się zatrzymać.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)

Sekcja `[moduł 11]`. `try`/`catch`/`finally` nie zmieniły się od pierwszej wersji C#.

Zmienił się natomiast **zwyczaj**: starsze materiały używają `try`/`catch` do sprawdzania danych od użytkownika, bo `TryParse` weszło do powszechnego użycia później. Dziś do przewidywalnych sytuacji używa się metod `TryCoś`, a wyjątków — do nieprzewidywalnych.

## Notatki tutora

- **Krok 2 musi zacząć się od słowa „Unhandled".** Uczeń widział je cztery razy, nie zwracając uwagi. Wskazanie, że sugeruje istnienie obsługi, jest ładnym wejściem.
- **Krok 3.D jest najważniejszy praktycznie.** Bez niego uczeń wyjdzie z lekcji przekonany, że `try`/`catch` zastępuje `TryParse` — i zacznie opakowywać wszystko w bloki.
- **Krok 4 (tabela wyjątków) domyka sześć wcześniejszych lekcji.** Uczeń widział te wyjątki pojedynczo; tutaj widzi, że to jedna rodzina.
- **Nie wprowadzaj `throw`.** To lekcja 11.2. Uczeń może zapytać, jak rzucić własny — nazwa i numer.
- **Nie wprowadzaj `using`.** Krok 3.C kończy się zapowiedzią; to 11.2.
- **Nie wprowadzaj `when`** ani filtrów wyjątków. Poza kursem.
- **Nie strasz wyjątkami.** Uczeń ma zrozumieć, że wyjątek to normalny mechanizm, a nie katastrofa.
- Jeśli uczeń zaczyna opakowywać każdą linię w `try` — wróć do kroku 3.D i do zasady „nie wiesz, co zrobić — nie łap".
