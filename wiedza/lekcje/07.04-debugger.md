# Lekcja 7.4 — Debugger

## Cel
Po lekcji uczeń:
- Zatrzymuje program w wybranej linii (**breakpoint**) i wznawia go
- Wykonuje program **linia po linii** i rozróżnia „przeskocz wywołanie" od „wejdź do środka"
- Czyta wartości zmiennych w panelu zamiast dopisywać `Console.WriteLine`
- Czyta **stos wywołań**: kto wywołał metodę, w której program stoi
- Wie, kiedy debugger jest szybszy od `Console.WriteLine`, a kiedy nie

> **Ta lekcja domyka odroczenie z lekcji 1.2.** Tam padło: „do modułu 5 `Console.WriteLine` wystarcza". Teraz uczeń ma metody wywołujące metody (7.1, 7.3) i pierwszy raz naprawdę nie widzi, **gdzie** wartość przestaje być dobra. Debugger nie jest nowym C# — to nowe okno na ten sam program.

> **Narzędzie:** scenariusz zakłada **VS Code z rozszerzeniem C# Dev Kit** (krok 5 skillu `setup-dotnet`) i **gotowy projekt** `wiedza/przyklady/debugger/`. Debugger w VS Code potrzebuje projektu z `.csproj` — na pojedynczym pliku `.cs` F5 kończy się komunikatem „Waiting for projects to load" i nic więcej. Uczeń nie tworzy projektu sam (to lekcja 14.1); dostaje go gotowy i tylko kopiuje. Sprawdź w `student.json` pole `srodowisko.edytor`, zanim zaczniesz. **Rider albo Visual Studio** → otwiera `Debugger.csproj`, te same kroki, inne klawisze: uczeń zna swoje IDE, ty pytasz o wartości i stos, nie o klawisze; zaliczenie liczy się tak samo. **Goły edytor bez debuggera** → poproś o instalację VS Code z C# Dev Kit **przed** tą lekcją (darmowy, każdy system — `setup-dotnet`, krok 5) i zapisz `postep update-srodowisko --edytor "VS Code"`; nie zaczynaj 7.4 bez debuggera. Ścieżka awaryjna z kroku 3.A jest wyłącznie na wypadek, gdy debugger mimo instalacji nie startuje.

## Krok 1 — Zakotwiczenie (3-5 min)

**Pytanie wejściowe:**
> „Masz przepis na ciasto i ciasto nie wyszło. Możesz upiec je jeszcze raz i patrzeć na wynik — albo zatrzymać się po każdym kroku i sprawdzić: mąka odmierzona? jajka wbite? Co jest szybsze, gdy nie wiesz, który krok zawinił?"

**Co chcesz usłyszeć:** zatrzymywać się po krokach — bo wynik końcowy nie mówi, **gdzie** poszło źle.

**Drugie pytanie:**
> „Do tej pory, gdy program liczył źle, co robiłeś?"

**Co chcesz usłyszeć:** dopisywałem `Console.WriteLine` w podejrzanym miejscu. Potwierdź, że to dobra metoda — i zapytaj, ile razy trzeba było ją dopisać, uruchomić, przeczytać, usunąć.

## Krok 2 — Mostek (5 min)

**Mostek:**
> „Program da się zatrzymać w dowolnej linii, obejrzeć każdą zmienną i puścić dalej o jedną linię. To robi **debugger**. Nie zmienia programu — tylko go zatrzymuje."

Trzy słowa, które padną w lekcji — nazwij je teraz, nie tłumacz:
- **breakpoint** — linia, przed którą program ma się zatrzymać
- **krok** — wykonaj jedną linię i zatrzymaj się znowu
- **stos wywołań** — lista metod, które właśnie trwają, od najgłębszej do góry

Uczeń **kopiuje gotowy projekt** i uruchamia go zwykłym `dotnet run` — z katalogu głównego repozytorium:
```
cp -r wiedza/przyklady/debugger kurs/zadania/debugger
cd kurs/zadania/debugger
dotnet run
```
(Windows, PowerShell: `Copy-Item -Recurse wiedza\przyklady\debugger kurs\zadania\debugger`.)
→
```
15
OK      Suma(3, 4) = 7
BŁĄD    Srednia(3, 4): jest 3, miało być 3,5
```

W folderze są dwa pliki: `Program.cs` z kodem i `Debugger.csproj`. Jedno zdanie o tym drugim, nie więcej:
> „`Debugger.csproj` to mały plik, który mówi .NET-owi: »ten folder to jeden program«. Debugger w VS Code potrzebuje takiego pliku — na luźnym `.cs` nie zadziała. W 14.1 nauczysz się go tworzyć; dziś dostajesz gotowy."

`Program.cs` ma dwa fragmenty: na górze pętla z lekcji 5.2 (linie 5-10), niżej `Sprawdz`, `Suma` i `Srednia` z lekcji 7.1 — z tym samym błędem, co w ćwiczeniu 🔧 (linie 12-23). Uczeń otwiera go i patrzy na pętlę:

> „Ile razy wykonała się linia 8, `suma = suma + i;`? Widziałeś to, czy wiesz z lekcji 5.2?"
→ wiem — nie widziałem. Zaraz zobaczy.

Teraz VS Code: **File → Open Folder…** → `kurs/zadania/debugger` (folder projektu, nie całe repozytorium). Po kilku sekundach pasek stanu na dole pokazuje `Debugger` i `net10.0 | Debug` — to znak, że C# Dev Kit zobaczył projekt. Bez tego F5 nie zadziała; poczekaj.

## Krok 3 — Eksperyment (20 min)

Cztery czynności na całą lekcję. Zapisz je uczniowi w czacie, zanim zacznie:

| Czynność | Klawisz | Nazwa w VS Code | Uwaga |
| --- | --- | --- | --- |
| włącz/wyłącz breakpoint w bieżącej linii | **F9** | Toggle Breakpoint | F9 na linii, która **już ma** kropkę, usuwa ją — program wtedy nie staje |
| uruchom pod debuggerem / jedź do następnego breakpointu | **F5** | Start Debugging / Continue | |

Zatrzymanie: **Shift+F5** (albo czerwony kwadrat na pasku). Po F5 VS Code sam otwiera widok **Run and Debug** po lewej: **Variables** (rozwiń **Locals**), **Watch**, **Call Stack**, **Breakpoints**. Wyjście programu pojawia się w panelu **Debug Console** na dole, nie w Terminalu — tam też jest pole, w które można wpisać wyrażenie i dostać jego wartość.

**Pierwsze F5 w tym projekcie zadaje trzy pytania** (potem już nie — wybór zostaje zapamiętany, w pasku stanu widać `C#: Launch Startup Project`). Uczeń wybiera po kolei, w każdej liście strzałką w dół albo kliknięciem, bo **nic nie jest zaznaczone i sam Enter nic nie robi**:
1. „Select debugger" → **C#** (podpisane „Suggested"; strzałka w górę przeskakuje na „Install an extension for C#..." — nie to)
2. „Select Launch Configuration" → **C#: Launch Startup Project**
3. „Select C# Startup Project" → jedyna pozycja, `Debugger`

### A. Zatrzymaj pętlę

Uczeń klika w linię 8, `suma = suma + i;`, i naciska **F9**. Przy numerze linii pojawia się czerwona kropka. Potem **F5** — i trzy listy z tabeli wyżej.

**Ścieżka awaryjna — zanim pójdziesz dalej.** Jeśli po trzech listach program się nie zatrzymał — uczeń wkleja do czatu to, co pokazał VS Code (powiadomienie, Debug Console, Terminal). Dwa znane przypadki: (1) „Waiting for projects to load" bez końca → otwarty jest zły folder (całe repozytorium zamiast `kurs/zadania/debugger`) albo pasek stanu nie pokazał jeszcze `Debugger` — otwórz właściwy folder i poczekaj; (2) w Terminalu `You must install .NET to run this application` → .NET zainstalowany skryptem w `~/.dotnet` bez `DOTNET_ROOT`; naprawa jest w skillu `setup-dotnet` (krok „Debugger i `DOTNET_ROOT`"), po niej VS Code trzeba uruchomić ponownie. Cokolwiek innego, po czym debugger nadal nie startuje → **nie walcz dłużej niż pięć minut**. Powiedz: „Debugger dla plików bez projektu bywa kapryśny; wrócimy do niego w 14.1, gdy będziemy mieli projekt." Zapisz `postep add-notatka "debugger: do uzupełnienia w 14.1 — F5 nie wystartował na pliku jednoplikowym"` i prowadź resztę lekcji w wersji **`Console.WriteLine`**: te same programy, te same pytania, tylko zamiast panelu Variables uczeń dopisuje `Console.WriteLine($"i={i} suma={suma}")` w linii breakpointu. Wnioski lekcji nie zmieniają się — ale **lekcja nie jest zaliczona**: bez breakpointu, kroku i stosu uczeń nie ćwiczył tego, o co w niej chodzi. `add-lekcja 7.4` wykona 14.1, gdy debugger ruszy na projekcie (sekcja „Zaliczenie lekcji" w skillu `lekcja`).

Gdy zadziałało — linia jest podświetlona, program stoi.

> „Spójrz na panel Variables, rozwiń Locals. Ile wynosi `i`? Ile `suma`?"
→ `1` i `0`. Linia **jeszcze się nie wykonała** — breakpoint zatrzymuje **przed** linią.

> „Naciśnij F10. Co się zmieniło?"
→ `suma` = `1`, podświetlenie przeszło dalej (do `}` albo do `i++` — zależnie od wersji debuggera; nie ma to znaczenia).

> „Naciśnij F5. Gdzie stanął program?"
→ znowu w tej samej linii — `i` = `2`, `suma` = `1`. **F5 jedzie do następnego breakpointu**, a ten sam breakpoint łapie każdy obieg pętli.

Uczeń naciska F5 jeszcze trzy razy i **liczy zatrzymania**. Pięć. Tyle, ile obiegów.

> „Po ostatnim F5 program dokończył się sam — w Debug Console jest `15`, a pod nim `OK` i `BŁĄD` z drugiej części pliku. Czemu już się nie zatrzymał?"
→ bo `i` doszło do `6`, pętla się skończyła, linia z breakpointem nie wykonała się szósty raz.

### B. Wejdź do metody, która liczy źle

Druga część `Program.cs` to zepsute metody z lekcji 7.1 — te same, co w ćwiczeniu 🔧 z 18-metody-zepsute.cs. Zwykłe `dotnet run` już pokazało:
```
OK      Suma(3, 4) = 7
BŁĄD    Srednia(3, 4): jest 3, miało być 3,5
```

> „`Sprawdz` mówi, **że** jest źle. Nie mówi, **gdzie**. Gdzie postawisz breakpoint?"

Dobra odpowiedź: w `Srednia`, w linii 22, `return (a + b) / 2;`. Uczeń najpierw **usuwa** breakpoint z linii 8 (F9 w tej linii — kropka znika), stawia nowy w linii 22 (**F9**) i uruchamia **F5** (tym razem bez pytań).

> „Program stoi. Co widzisz w Variables?"
→ `a` = `3`, `b` = `4`. Parametry metody są zmiennymi jak każde inne.

> „Spójrz na panel Call Stack. Co tam jest?"
→ dwa wpisy: na górze `Debugger.dll!Program.<Main>$.__Srednia|0_1(int a, int b)`, pod nim `Debugger.dll!Program.<Main>$(string[] args)`, jeszcze niżej szare `[External Code]`. Nazwy są długie i dziwne — `Program.<Main>$` to wewnętrzna nazwa pliku najwyższego poziomu, a `__Srednia|0_1` to `Srednia` z dopiskiem kompilatora. Uczeń ma wyłuskać dwa słowa: `Srednia` na górze, `Main` pod spodem. **Stos czyta się od góry: tu jestem, a poniżej — kto mnie wywołał.**

> „Program stoi **przed** `return`. Wynik jeszcze nie istnieje. Możesz go poznać, zanim metoda odda?"

Uczeń klika w pole na dole panelu **Debug Console** (nad nim wyjście programu), wpisuje `a + b` i naciska Enter → `7`. Wpisuje `(a + b) / 2` → `3`. To samo pokazuje najechanie kursorem na wyrażenie w kodzie — jeśli uczeń woli mysz, niech spróbuje; Debug Console jest pewniejsza.

> „`7 / 2` dało `3`. Z której lekcji znasz ten efekt?"
→ 2.3, dzielenie całkowite. **Debugger nie znalazł błędu — pokazał wartość, a błąd rozpoznał uczeń.** Podkreśl to.

> „Naciśnij F10. Gdzie stoi program?"
→ na linii 23, na klamrze `}` — metoda się kończy, ale jeszcze nie oddała wyniku.

> „Jeszcze raz F10. A teraz?"
→ z powrotem w linii 13, `SprawdzDouble(...)`, bo metoda się skończyła. Stos ma znowu jeden wpis, a w Locals pojawił się wiersz `Program.<Main>$.__Srednia|0_1 returned` z wartością, którą metoda oddała — `3`.

Uczeń zatrzymuje debugger (**Shift+F5**), naprawia (`/ 2.0`), uruchamia zwykłym `dotnet run` — dwa `OK`.

### C. F10 kontra Step Into — na tym samym programie

Uczeń usuwa breakpoint z `Srednia` (F9 w linii 22) i stawia nowy w linii 12: `Sprawdz("Suma(3, 4)", Suma(3, 4), 7);`. **F5**.

> „Naciśnij **F10**. Co się stało z wywołaniem `Suma`?"
→ wykonało się „w jednym kroku" — program przeszedł do linii 13, tej z `SprawdzDouble`, a w Debug Console pojawiło się `OK      Suma(3, 4) = 7`. **F10 traktuje metodę jak jedną linię.** (W Locals: `…__Suma|0_0 returned` = `7`.)

> „Teraz, w linii 13, wejdź do środka: przycisk **↓** na pasku debugowania (albo Run → Step Into). Gdzie jesteś?"
→ w `Srednia`, na linii 21 — otwierającej klamrze `{`. **Step Into wchodzi do środka.** Call Stack ma dwa wpisy, Locals: `a` = `3`, `b` = `4`.

> „Wchodź dalej, aż wyjdziesz z `Srednia`, i jeszcze raz. Licz naciśnięcia. A teraz gdzie?"
→ trzy naciśnięcia: linia 22, linia 23, powrót do linii 13 (z `…Srednia|0_1 returned` = `3` w Locals). Czwarte: linia 38, klamra `{` metody `SprawdzDouble`, a w Locals `opis` = `"Srednia(3, 4)"`, `wynik` = `3`, `oczekiwane` = `3.5`. Jedna linia kodu, **dwie** metody do wejścia: najpierw `Srednia`, bo jej wynik jest potrzebny, żeby w ogóle wywołać `SprawdzDouble`. Kolejność wchodzenia to kolejność **obliczania**, nie czytania od lewej.

> „Kiedy wolisz F10, a kiedy Step Into?"
→ F10, gdy ufam metodzie (`Console.WriteLine`, `Sprawdz`); Step Into, gdy podejrzewam, że to w niej jest błąd.

Uczeń zatrzymuje debugger (**Shift+F5**).

## Krok 4 — Pogłębienie (5-10 min)

**Kiedy debugger, kiedy `Console.WriteLine`**

| Sytuacja | Lepsze |
| --- | --- |
| nie wiesz, w której linii wartość psuje się | debugger — zatrzymujesz i idziesz krokami |
| chcesz zobaczyć wartość w **każdym** ze stu obiegów pętli naraz | `Console.WriteLine` — sto zatrzymań to męka |
| błąd jest w metodzie wywoływanej z wielu miejsc i nie wiesz, z którego | debugger — Call Stack mówi, kto wywołał |
| program czyta z klawiatury i chcesz szybko sprawdzić jeden przypadek | `Console.WriteLine` i `dotnet run` — mniej klikania |

> „Debugger nie zastępuje `Sprawdz` z 7.1. `Sprawdz` mówi **czy** działa — za każdym razem, automatycznie. Debugger mówi **dlaczego nie** — raz, gdy szukasz."

**Breakpoint w linii bez kodu**

Uczeń stawia F9 na pustej linii albo na `}` — niech sprawdzi, co VS Code z tym zrobi (przesunie kropkę do najbliższej linii z kodem albo jej nie postawi). Nie jest to błąd; pokaż i jedź dalej.

**Zmiana w panelu Variables**

Wartość zmiennej da się w panelu **nadpisać** w trakcie zatrzymania. Wspomnij jednym zdaniem, nie ćwicz — początkujący, który to polubi, zacznie „naprawiać" program w debuggerze zamiast w kodzie.

## Krok 5 — Ćwiczenie

→ Skill `cwiczenie`. Temat: „debugger". Propozycje:

Wszystkie trzy ćwiczenia idą w **tym samym projekcie** `kurs/zadania/debugger/`: uczeń podmienia zawartość `Program.cs` (oryginał ma w `wiedza/przyklady/debugger/`), a przed podmianą zapisuje poprzednią wersję obok jako `kurs/zadania/21-debugger-a.cs` itd. — tylko jako archiwum, bo debugger widzi jedynie `Program.cs` w projekcie.

- 🔥 **Rozgrzewka** (`21-debugger-a.cs`): weź swoją pętlę `for` z lekcji 5.2, która wypisuje tabliczkę mnożenia dla jednej liczby. Postaw breakpoint w środku, zatrzymaj się **trzy** razy i po każdym zatrzymaniu wpisz do czatu wartości wszystkich zmiennych z panelu Variables — **zanim** naciśniesz F5. Potem sprawdź, czy się zgadzały z tym, co wypisał program.
- ⭐ **Główne** (`21-debugger-b.cs`): przepisz poniższy program **dokładnie**. `SprawdzDouble` weź z pliku zepsutego z kroku 3.B. Uruchom — zobaczysz `BŁĄD    Srednia(oceny): jest 3,25, miało być 4,25`. Znajdź przyczynę **debuggerem**: breakpoint w środku pętli, obserwuj `i` i `suma` przy każdym zatrzymaniu. Napisz mi, przy którym zatrzymaniu zauważyłeś, co jest nie tak, i **dopiero potem** napraw.
  ```csharp
  int[] oceny = { 4, 5, 3, 5 };
  SprawdzDouble("Srednia(oceny)", Srednia(oceny), 4.25);

  double Srednia(int[] liczby)
  {
      int suma = 0;
      for (int i = 1; i < liczby.Length; i++)
      {
          suma = suma + liczby[i];
      }
      return (double)suma / liczby.Length;
  }
  ```
- ⚡ **Gwiazdka** (`21-debugger-c.cs`): przepisz poniższy program. Druga linia wyjścia jest zła: `-- [imie]` zamiast `-- [Bo]`. Postaw **jeden** breakpoint — w `Ladnie` — i za pomocą samego panelu **Call Stack** ustal, przy którym zatrzymaniu i z której metody przyszło złe wywołanie. Nie czytaj kodu `Powitanie` ani `Podpis` przed uruchomieniem — chodzi o to, żeby stos powiedział ci to, co inaczej musiałbyś wyczytać.
  ```csharp
  Console.WriteLine(Powitanie("Ala"));
  Console.WriteLine(Podpis("Bo"));
  Console.WriteLine(Powitanie("Cyd"));

  string Powitanie(string imie)
  {
      return "Cześć, " + Ladnie(imie) + "!";
  }

  string Podpis(string imie)
  {
      return "-- " + Ladnie("imie");
  }

  string Ladnie(string tekst)
  {
      return "[" + tekst + "]";
  }
  ```

Główne sprawdza, czy uczeń umie **patrzeć na zmienne w czasie**: przy pierwszym zatrzymaniu `i` = `1`, a `oceny[0]` nigdy nie trafia do sumy. Gwiazdka sprawdza stos: przy drugim zatrzymaniu Call Stack pokazuje `Ladnie` na górze, a `Podpis` pod nim, a `tekst` = `"imie"` — cudzysłów zamiast zmiennej. Uczeń, który to wyczyta z panelu, nie z kodu, rozumie lekcję.

## Pułapki

- **Breakpoint zatrzymuje przed linią, nie po niej.** Objaw: „zmienna ma starą wartość". Naciśnij F10 i spójrz jeszcze raz.
- **F5 zamiast F10.** Program pojechał do końca (albo do następnego breakpointu) i uczeń myśli, że „debugger nie działa". Pytanie: „który klawisz nacisnąłeś?"
- **F11 na macOS pokazuje biurko.** Okno VS Code znika, uczeń myśli, że „debugger się zawiesił". To systemowy skrót; naciśnij F11 jeszcze raz, żeby wrócić, a do wchodzenia w metodę używaj przycisku ↓ albo Run → Step Into.
- **Step Into na `Console.WriteLine`.** Uczeń wchodzi do kodu biblioteki albo VS Code przeskakuje go sam — w obu przypadkach zamieszanie. Reguła: w cudze metody wchodź F10.
- **Pierwsze F5 pyta trzy razy, sam Enter nic nie robi.** Uczeń naciska Enter, lista stoi — „nie działa". Strzałka w dół (albo klik) i dopiero Enter, w każdej z trzech list.
- **Otwarte całe repozytorium zamiast folderu projektu.** F5 → „Waiting for projects to load" bez końca. File → Open Folder → `kurs/zadania/debugger`.
- **`You must install .NET to run this application` w Terminalu.** .NET jest, ale zainstalowany skryptem w `~/.dotnet` bez `DOTNET_ROOT`; `dotnet run` działa, debugger nie. Naprawa w `setup-dotnet`, potem restart VS Code.
- **Breakpoint w pętli na 1000 obiegów.** Tysiąc razy F5. Tu lepszy jest `Console.WriteLine` — tabela z kroku 4.
- **Zapomniany breakpoint.** Zwykłe `dotnet run` go ignoruje, ale przy następnym F5 program „dziwnie staje". Czerwone kropki widać przy numerach linii i w panelu Breakpoints — usuń F9.
- **F9 na linii, która już ma kropkę.** Wyłącza ją; program przelatuje bez zatrzymania i wypisuje wszystko w Debug Console. Pytanie: „jest kropka przy linii?"
- **Naprawianie w panelu Variables zamiast w kodzie.** Po Shift+F5 wszystko wraca do starego. Zmiana ma być w pliku.

Debugowanie krokowe nie jest częścią języka i sekcje `AKTUALIZACJE.md` go nie dotyczą. Klawisze F5, F9, F10 i idea breakpointu są **te same** w VS Code (F11 = Step Into też, poza macOS, gdzie ten klawisz zajmuje system) — jeśli uczeń trafi na taki poradnik, przełoży go jeden do jednego.
