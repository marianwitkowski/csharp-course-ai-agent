# Lekcja 7.4 — Debugger

## Cel
Po lekcji uczeń:
- Zatrzymuje program w wybranej linii (**breakpoint**) i wznawia go
- Wykonuje program **linia po linii** i rozróżnia „przeskocz wywołanie" od „wejdź do środka"
- Czyta wartości zmiennych w panelu zamiast dopisywać `Console.WriteLine`
- Czyta **stos wywołań**: kto wywołał metodę, w której program stoi
- Wie, kiedy debugger jest szybszy od `Console.WriteLine`, a kiedy nie

> **Ta lekcja domyka odroczenie z lekcji 1.2.** Tam padło: „do modułu 5 `Console.WriteLine` wystarcza". Teraz uczeń ma metody wywołujące metody (7.1, 7.3) i pierwszy raz naprawdę nie widzi, **gdzie** wartość przestaje być dobra. Debugger nie jest nowym C# — to nowe okno na ten sam program.

> **Narzędzie:** scenariusz zakłada **VS Code z rozszerzeniem C# Dev Kit** (krok 5 skillu `setup-dotnet`). Sprawdź w `student.json` pole `srodowisko.edytor`, zanim zaczniesz. **Rider albo Visual Studio** → te same kroki, inne klawisze: uczeń zna swoje IDE, ty pytasz o wartości i stos, nie o klawisze; zaliczenie liczy się tak samo. **Goły edytor bez debuggera** → poproś o instalację VS Code z C# Dev Kit **przed** tą lekcją (darmowy, każdy system — `setup-dotnet`, krok 5) i zapisz `postep update-srodowisko --edytor "VS Code"`; nie zaczynaj 7.4 bez debuggera. Ścieżka awaryjna z kroku 3.A jest wyłącznie na wypadek, gdy debugger mimo instalacji nie startuje.

## Krok 1 — Zakotwiczenie (3-5 min)

**Pytanie wejściowe:**
> „Masz przepis na ciasto i ciasto nie wyszło. Możesz upiec je jeszcze raz i patrzeć na wynik — albo zatrzymać się po każdym kroku i sprawdzić: mąka odmierzona? jajka wbite? Co jest szybsze, gdy nie wiesz, który krok zawinił?"

**Co chcesz usłyszeć:** zatrzymywać się po krokach — bo wynik końcowy nie mówi, **gdzie** poszło źle.

**Drugie pytanie:**
> „Do tej pory, gdy program liczył źle, co robiłeś?"

**Co chcesz usłyszeć:** dopisywałem `Console.WriteLine` w podejrzanym miejscu. Potwierdź, że to dobra metoda — i zapytaj, ile razy trzeba było ją dopisać, uruchomić, przeczytać, usunąć.

## Krok 2 — Mostek (5 min)

**Mostek:**
> „Program da się zatrzymać w dowolnej linii, obejrzeć każdą zmienną i puścić dalej o jedną linię. To robi **debugger**. Nie zmienia programu — tylko go zatrzymuje."

Trzy słowa, które padną w lekcji — nazwij je teraz, nie tłumacz:
- **breakpoint** — linia, przed którą program ma się zatrzymać
- **krok** — wykonaj jedną linię i zatrzymaj się znowu
- **stos wywołań** — lista metod, które właśnie trwają, od najgłębszej do góry

Uczeń tworzy `kurs/zadania/21-debugger.cs`:
```csharp
int suma = 0;
for (int i = 1; i <= 5; i++)
{
    suma = suma + i;
}
Console.WriteLine(suma);
```
→ `15`

> „Ile razy wykonała się linia 4? Widziałeś to, czy wiesz z lekcji 5.2?"
→ wiem — nie widziałem. Zaraz zobaczy.

## Krok 3 — Eksperyment (20 min)

Cztery klawisze na całą lekcję. Zapisz je uczniowi w czacie, zanim zacznie:

| Klawisz | Co robi | Nazwa w VS Code |
| --- | --- | --- |
| **F9** | włącz/wyłącz breakpoint w bieżącej linii | Toggle Breakpoint |
| **F5** | uruchom pod debuggerem / jedź dalej do następnego breakpointu | Start Debugging / Continue |
| **F10** | wykonaj bieżącą linię; wywołanie metody potraktuj jak jedną linię | Step Over |
| **F11** | wykonaj bieżącą linię; jeśli to wywołanie metody — **wejdź do niej** | Step Into |

Zatrzymanie: **Shift+F5**. Panele po lewej podczas debugowania: **Variables** (zmienne) i **Call Stack** (stos wywołań).

### A. Zatrzymaj pętlę

Uczeń otwiera `21-debugger.cs` w VS Code, klika w linię `suma = suma + i;` i naciska **F9**. Przy numerze linii pojawia się czerwona kropka. Potem **F5**.

**Ścieżka awaryjna — zanim pójdziesz dalej.** Jeśli po F5 program się nie zatrzymał, a VS Code pokazał listę do wyboru albo komunikat — uczeń wkleja go do czatu. Lista z wyborem środowiska → wybierz **C#**. Komunikat o braku projektu, konfiguracji albo cokolwiek, po czym debugger nadal nie startuje → **nie walcz dłużej niż pięć minut**. Powiedz: „Debugger dla plików bez projektu bywa kapryśny; wrócimy do niego w 14.1, gdy będziemy mieli projekt." Zapisz `postep add-notatka "debugger: do uzupełnienia w 14.1 — F5 nie wystartował na pliku jednoplikowym"` i prowadź resztę lekcji w wersji **`Console.WriteLine`**: te same programy, te same pytania, tylko zamiast panelu Variables uczeń dopisuje `Console.WriteLine($"i={i} suma={suma}")` w linii breakpointu. Wnioski lekcji nie zmieniają się — ale **lekcja nie jest zaliczona**: bez breakpointu, kroku i stosu uczeń nie ćwiczył tego, o co w niej chodzi. `add-lekcja 7.4` wykona 14.1, gdy debugger ruszy na projekcie (sekcja „Zaliczenie lekcji" w skillu `lekcja`).

Gdy zadziałało — linia jest podświetlona, program stoi.

> „Spójrz na panel Variables. Ile wynosi `i`? Ile `suma`?"
→ `1` i `0`. Linia **jeszcze się nie wykonała** — breakpoint zatrzymuje **przed** linią.

> „Naciśnij F10. Co się zmieniło?"
→ `suma` = `1`, podświetlenie przeszło dalej (do `}` albo do `i++` — zależnie od wersji debuggera; nie ma to znaczenia).

> „Naciśnij F5. Gdzie stanął program?"
→ znowu w tej samej linii — `i` = `2`, `suma` = `1`. **F5 jedzie do następnego breakpointu**, a ten sam breakpoint łapie każdy obieg pętli.

Uczeń naciska F5 jeszcze trzy razy i **liczy zatrzymania**. Pięć. Tyle, ile obiegów.

> „Po ostatnim F5 program dokończył się sam i wypisał `15`. Czemu już się nie zatrzymał?"
→ bo `i` doszło do `6`, pętla się skończyła, linia z breakpointem nie wykonała się szósty raz.

### B. Wejdź do metody, która liczy źle

Uczeń kopiuje zepsuty program z lekcji 7.1: `cp wiedza/przyklady/zepsute/18-metody-zepsute.cs kurs/zadania/` (na Windows `copy`) i uruchamia go **zwykłym** `dotnet run`:
```
OK      Suma(3, 4) = 7
BŁĄD    Srednia(3, 4): jest 3, miało być 3,5
```

> „`Sprawdz` mówi, **że** jest źle. Nie mówi, **gdzie**. Gdzie postawisz breakpoint?"

Dobra odpowiedź: w `Srednia`, w linii `return (a + b) / 2;`. Uczeń stawia go tam (**F9**) i uruchamia **F5**.

> „Program stoi. Co widzisz w Variables?"
→ `a` = `3`, `b` = `4`. Parametry metody są zmiennymi jak każde inne.

> „Spójrz na panel Call Stack. Co tam jest?"
→ dwa wpisy: na górze `Srednia`, pod nim linia z `Main` (nazwa może być dłuższa i dziwna — to plik najwyższego poziomu, VS Code pokazuje jego wewnętrzną nazwę). **Stos czyta się od góry: tu jestem, a poniżej — kto mnie wywołał.**

> „Program stoi **przed** `return`. Wynik jeszcze nie istnieje. Możesz go poznać, zanim metoda odda?"

Uczeń najeżdża kursorem na `a + b` — VS Code pokazuje `7`. Najeżdża na `(a + b) / 2` — pokazuje `3`.

> „`7 / 2` dało `3`. Z której lekcji znasz ten efekt?"
→ 2.3, dzielenie całkowite. **Debugger nie znalazł błędu — pokazał wartość, a błąd rozpoznał uczeń.** Podkreśl to.

> „Naciskaj F10, aż wyjdziesz z metody. Gdzie jesteś?"
→ z powrotem w linii `SprawdzDouble(...)`, bo metoda się skończyła. Stos ma znowu jeden wpis.

Uczeń zatrzymuje debugger (**Shift+F5**), naprawia (`/ 2.0`), uruchamia zwykłym `dotnet run` — dwa `OK`.

### C. F10 kontra F11 — na tym samym programie

Uczeń usuwa breakpoint z `Srednia` (F9 w tej linii) i stawia nowy w **pierwszej** linii pliku: `Sprawdz("Suma(3, 4)", Suma(3, 4), 7);`. **F5**.

> „Naciśnij **F10**. Co się stało z wywołaniem `Suma`?"
→ wykonało się „w jednym kroku" — program przeszedł do następnej linii, tej z `SprawdzDouble`, a w konsoli VS Code pojawiło się `OK      Suma(3, 4) = 7`. **F10 traktuje metodę jak jedną linię.**

> „Teraz, w linii z `SprawdzDouble`, naciśnij **F11**. Gdzie jesteś?"
→ w środku `Srednia`, w jej pierwszej linii. **F11 wchodzi do środka.** Call Stack ma dwa wpisy.

> „Naciskaj F11, aż wyjdziesz z `Srednia`, i jeszcze raz. A teraz gdzie?"
→ w `SprawdzDouble` — bo wynik `Srednia` już wrócił, a następne wywołanie w tej linii to `SprawdzDouble`. Jedna linia kodu, **dwie** metody do wejścia. Zwróć uwagę: kolejność wchodzenia to kolejność **obliczania**, nie czytania od lewej.

> „Kiedy wolisz F10, a kiedy F11?"
→ F10, gdy ufam metodzie (`Console.WriteLine`, `Sprawdz`); F11, gdy podejrzewam, że to w niej jest błąd.

## Krok 4 — Pogłębienie (5-10 min)

**Kiedy debugger, kiedy `Console.WriteLine`**

| Sytuacja | Lepsze |
| --- | --- |
| nie wiesz, w której linii wartość psuje się | debugger — zatrzymujesz i idziesz krokami |
| chcesz zobaczyć wartość w **każdym** ze stu obiegów pętli naraz | `Console.WriteLine` — sto zatrzymań to męka |
| błąd jest w metodzie wywoływanej z wielu miejsc i nie wiesz, z którego | debugger — Call Stack mówi, kto wywołał |
| program czyta z klawiatury i chcesz szybko sprawdzić jeden przypadek | `Console.WriteLine` i `dotnet run` — mniej klikania |

> „Debugger nie zastępuje `Sprawdz` z 7.1. `Sprawdz` mówi **czy** działa — za każdym razem, automatycznie. Debugger mówi **dlaczego nie** — raz, gdy szukasz."

**Breakpoint w linii bez kodu**

Uczeń stawia F9 na pustej linii albo na `}` — VS Code przesunie kropkę do najbliższej linii z kodem albo jej nie postawi. Nie jest to błąd; pokaż i jedź dalej.

**Zmiana w panelu Variables**

Wartość zmiennej da się w panelu **nadpisać** w trakcie zatrzymania. Wspomnij jednym zdaniem, nie ćwicz — początkujący, który to polubi, zacznie „naprawiać" program w debuggerze zamiast w kodzie.

## Krok 5 — Ćwiczenie

→ Skill `cwiczenie`. Temat: „debugger". Propozycje:

- 🔥 **Rozgrzewka** (`21-debugger-a.cs`): weź swoją pętlę `for` z lekcji 5.2, która wypisuje tabliczkę mnożenia dla jednej liczby. Postaw breakpoint w środku, zatrzymaj się **trzy** razy i po każdym zatrzymaniu wpisz do czatu wartości wszystkich zmiennych z panelu Variables — **zanim** naciśniesz F5. Potem sprawdź, czy się zgadzały z tym, co wypisał program.
- ⭐ **Główne** (`21-debugger-b.cs`): przepisz poniższy program **dokładnie**. `SprawdzDouble` weź z pliku zepsutego z kroku 3.B. Uruchom — zobaczysz `BŁĄD    Srednia(oceny): jest 3,25, miało być 4,25`. Znajdź przyczynę **debuggerem**: breakpoint w środku pętli, obserwuj `i` i `suma` przy każdym zatrzymaniu. Napisz mi, przy którym zatrzymaniu zauważyłeś, co jest nie tak, i **dopiero potem** napraw.
  ```csharp
  int[] oceny = { 4, 5, 3, 5 };
  SprawdzDouble("Srednia(oceny)", Srednia(oceny), 4.25);

  double Srednia(int[] liczby)
  {
      int suma = 0;
      for (int i = 1; i < liczby.Length; i++)
      {
          suma = suma + liczby[i];
      }
      return (double)suma / liczby.Length;
  }
  ```
- ⚡ **Gwiazdka** (`21-debugger-c.cs`): przepisz poniższy program. Druga linia wyjścia jest zła: `-- [imie]` zamiast `-- [Bo]`. Postaw **jeden** breakpoint — w `Ladnie` — i za pomocą samego panelu **Call Stack** ustal, przy którym zatrzymaniu i z której metody przyszło złe wywołanie. Nie czytaj kodu `Powitanie` ani `Podpis` przed uruchomieniem — chodzi o to, żeby stos powiedział ci to, co inaczej musiałbyś wyczytać.
  ```csharp
  Console.WriteLine(Powitanie("Ala"));
  Console.WriteLine(Podpis("Bo"));
  Console.WriteLine(Powitanie("Cyd"));

  string Powitanie(string imie)
  {
      return "Cześć, " + Ladnie(imie) + "!";
  }

  string Podpis(string imie)
  {
      return "-- " + Ladnie("imie");
  }

  string Ladnie(string tekst)
  {
      return "[" + tekst + "]";
  }
  ```

Główne sprawdza, czy uczeń umie **patrzeć na zmienne w czasie**: przy pierwszym zatrzymaniu `i` = `1`, a `oceny[0]` nigdy nie trafia do sumy. Gwiazdka sprawdza stos: przy drugim zatrzymaniu Call Stack pokazuje `Ladnie` na górze, a `Podpis` pod nim, a `tekst` = `"imie"` — cudzysłów zamiast zmiennej. Uczeń, który to wyczyta z panelu, nie z kodu, rozumie lekcję.

## Pułapki

- **Breakpoint zatrzymuje przed linią, nie po niej.** Objaw: „zmienna ma starą wartość". Naciśnij F10 i spójrz jeszcze raz.
- **F5 zamiast F10.** Program pojechał do końca (albo do następnego breakpointu) i uczeń myśli, że „debugger nie działa". Pytanie: „który klawisz nacisnąłeś?"
- **F11 na `Console.WriteLine`.** Uczeń wchodzi do kodu biblioteki albo VS Code przeskakuje go sam — w obu przypadkach zamieszanie. Reguła: w cudze metody wchodź F10.
- **Breakpoint w pętli na 1000 obiegów.** Tysiąc razy F5. Tu lepszy jest `Console.WriteLine` — tabela z kroku 4.
- **Zapomniany breakpoint.** Zwykłe `dotnet run` go ignoruje, ale przy następnym F5 program „dziwnie staje". Czerwone kropki widać przy numerach linii — usuń F9.
- **Naprawianie w panelu Variables zamiast w kodzie.** Po Shift+F5 wszystko wraca do starego. Zmiana ma być w pliku.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)

Debugowanie krokowe nie jest częścią języka i sekcje `AKTUALIZACJE.md` go nie dotyczą. Jedna praktyczna różnica względem starych poradników: te pokazują debugger w **Visual Studio** (pełnym IDE, tylko Windows). Klawisze F5, F9, F10, F11 i idea breakpointu są **te same** w VS Code — jeśli uczeń trafi na taki poradnik, przełoży go jeden do jednego. Kurs nie instaluje Visual Studio (skill `setup-dotnet`, krok 2).

## Notatki tutora

- **Sprawdź edytor przed lekcją.** `srodowisko.edytor` w `student.json`. Rider / Visual Studio → prowadź normalnie, uczeń sam tłumaczy klawisze swojego IDE. Goły edytor → instalacja VS Code **przed** lekcją, a nie ścieżka awaryjna — powiedz to uczniowi na wstępie, nie w połowie.
- **Nie cytuj komunikatów VS Code z pamięci.** Uczeń wkleja, ty czytasz. Rozszerzenia zmieniają teksty częściej niż kompilator.
- **Ścieżka awaryjna to odroczenie, nie zaliczenie.** Wnioski (gdzie wartość się psuje, kto wywołał) da się wyciągnąć z `Console.WriteLine`, ale lekcja uczy narzędzia, a nie wniosków — bez breakpointu, F10/F11 i Call Stack **nie wołaj `add-lekcja 7.4`**. Zostaje notatka `debugger:` z kroku 3.A; 14.1 ma krok H, który wraca do tego na projekcie i dopiero wtedy zalicza 7.4. Uczniowi powiedz to wprost i bez dramatu: „debugger dopiszemy przy projekcie".
- **Krok 3.B jest sercem lekcji.** Uczeń ma zobaczyć `7 / 2` = `3` **przed** `return`, nie w wyniku. Jeśli od razu mówi „to dzielenie całkowite" bez patrzenia — świetnie, ale i tak niech najedzie kursorem na wyrażenie. Ma zobaczyć, że debugger pokazuje wartości **wyrażeń**, nie tylko zmiennych.
- **Nie wprowadzaj breakpointów warunkowych, Watch ani logpointów.** Cztery klawisze wystarczą na cały kurs. Jeśli uczeń pyta — „są, i przydadzą się przy projekcie; teraz F9, F5, F10, F11".
- **Nie tłumacz, czym jest stos w pamięci.** „Lista trwających metod, od najgłębszej" wystarcza. To ta sama granica co przy stercie w 7.3.
- **Uczeń na ścieżce skróconej** zna zwykle debugger z innego narzędzia. Pytanie zamiast wykładu: „gdzie postawisz breakpoint, żeby zobaczyć wartość przed `return`?" — i od razu krok 3.B.
