# Lekcja 4.1 — Instrukcja warunkowa

## Cel
Po lekcji uczeń:
- Pisze `if`, `if / else` i łańcuch `else if`
- **Reaguje** na wynik `TryParse` — domyka to, czego zabrakło w lekcji 3.2
- Wie, że bez klamer do `if` należy **tylko jedna** instrukcja — i umie to rozpoznać
- Rozumie, po co wcięcia: przy `if` bez klamer wcięcie potrafi kłamać
- Rozpoznaje dwie pułapki: `=` zamiast `==` i średnik zaraz po `if`

> **To najbardziej wyczekiwana lekcja kursu.** Do tej pory program wykonywał wszystkie instrukcje po kolei, zawsze tak samo. Od dziś potrafi się zachować różnie.

## Krok 1 — Zakotwiczenie (5 min)

**Pytanie wejściowe:**
> „Kiedy wychodzisz z domu, czasem bierzesz parasol, a czasem nie. Jaką regułę masz w głowie?"

**Co chcesz usłyszeć:** „jeśli pada (albo się zanosi), to biorę". Drąż o formę: **warunek** i **co wtedy**.

**Drugie pytanie:**
> „A jeśli nie pada — robisz coś innego, czy po prostu nic?"

**Co chcesz usłyszeć:** albo nic, albo „biorę okulary przeciwsłoneczne". Obie odpowiedzi są dobre i obie są potrzebne — to różnica między `if` samym a `if` z `else`.

**Trzecie pytanie:**
> „A gdyby reguła miała trzy stopnie: leje, mży, sucho?"

To przygotowanie pod `else if`. **Nie nazywaj jeszcze niczego.**

## Krok 2 — Mostek (10 min)

**Mostek:**
> „To, co opisałeś — »jeśli warunek, to zrób to« — w C# nazywa się **instrukcją warunkową**. Pisze się ją słowem `if`, po nim warunek w nawiasach, a to, co ma się wtedy stać, w klamrach."

Uczeń tworzy `kurs/zadania/08-if.cs`:

```csharp
int wiek = 20;

if (wiek >= 18)
{
    Console.WriteLine("Pełnoletni");
}
else
{
    Console.WriteLine("Niepełnoletni");
}
```

Uruchomienie: `dotnet run 08-if.cs` → `Pełnoletni`

**Pytania:**
- „Co jest warunkiem, a co się dzieje, gdy jest spełniony?"
- „Zmień `wiek` na `15` i uruchom. Która klamra zadziałała?"
- „Jakiego typu jest `wiek >= 18`? Znasz to z lekcji 2.4."
  → `bool`. **W nawiasach `if` musi stać coś typu `bool`** — nic innego nie przejdzie.

Teraz nazwij: **warunek**, **gałąź `if`**, **gałąź `else`**.

> **Klamry i wcięcia — teraz mają sens.** W lekcji 1.2 włączyłeś w edytorze automatyczne formatowanie i obiecałem, że zobaczysz po co. To jest ten moment: kod przestał być płaską listą i zaczął mieć **poziomy**. Wcięcie pokazuje, co jest w środku czego.

## Krok 3 — Eksperyment (25 min)

### A. Zareaguj wreszcie na złe dane

To domknięcie lekcji 3.2. Uczeń pisze:

```csharp
Console.Write("Podaj rok urodzenia: ");
bool ok = int.TryParse(Console.ReadLine(), out int rok);

if (ok)
{
    Console.WriteLine($"Rocznik {rok}. Dziękuję.");
}
else
{
    Console.WriteLine("To nie wygląda na rok.");
}
```

Uczeń uruchamia **dwa razy**: raz z `1990`, raz z `tysiąc`.

> „W lekcji 3.2 program tylko wypisywał `False` i szedł dalej. Co robi teraz?"

To jest cała nagroda za czekanie przez moduł 3. Zatrzymaj się na tym.

> **Zwróć uwagę:** w nawiasie stoi samo `ok`, bez `== true`. `ok` **jest** typu `bool`, więc nie ma czego porównywać. `if (ok == true)` też zadziała, ale to jak zapytać „czy to prawda, że prawda?".

### B. Łańcuch `else if`

```csharp
int ocena = 4;

if (ocena == 5)
{
    Console.WriteLine("bardzo dobry");
}
else if (ocena == 4)
{
    Console.WriteLine("dobry");
}
else if (ocena == 3)
{
    Console.WriteLine("dostateczny");
}
else
{
    Console.WriteLine("nieznana ocena");
}
```

> „Zmień `ocena` na 5, potem na 3, potem na 7. Ile gałęzi wykonuje się przy każdym uruchomieniu?"
→ **dokładnie jedna.** Pierwsza, której warunek jest spełniony; reszta jest pomijana.

> „Co się stanie, jeśli usuniesz ostatnie `else`? Ustaw `ocena = 7` i sprawdź."
→ nie wypisze się nic. Program nie protestuje — po prostu żadna gałąź nie pasowała.

### C. Klamry, które wyglądają na zbędne

Uczeń pisze **dokładnie tak**, z wcięciem:

```csharp
int wiek = 15;

if (wiek >= 18)
    Console.WriteLine("A");
    Console.WriteLine("B");
```

> „Zgadnij, zanim uruchomisz: `wiek` to 15, więc warunek nie jest spełniony. Co się wypisze?"

Uczeń zwykle odpowiada: nic.
→ wypisze się **`B`**.

To jest najważniejsze zaskoczenie lekcji. Rozłóż je na czynniki:

> „Bez klamer do `if` należy **tylko pierwsza** instrukcja po nim. Druga jest już poza warunkiem — wykonuje się zawsze."

> „A teraz najciekawsze: **wcięcie sugerowało co innego.** Obie linie były wcięte tak samo, więc wyglądały na parę. C# nie patrzy na wcięcia — patrzy na klamry."

**Tutaj wraca lekcja 1.2.** Niech uczeń **zapisze plik** (Cmd+S / Ctrl+S) z włączonym „Format on Save" i zobaczy, co zrobi edytor z linią `Console.WriteLine("B");`.

> „Co się stało z wcięciem po zapisie? Czy kod nadal wygląda tak samo?"

**Uwaga dla ciebie:** nie obiecuj konkretnego wyniku — zachowanie zależy od edytora i wersji rozszerzenia. Jeśli edytor wyrówna `B` do lewej, masz gotową puentę:

> „Formatowanie nie jest ozdobą. Ono pokazuje **prawdziwą** strukturę kodu — a przed chwilą wcięcie kłamało. Edytor to naprostował."

Jeśli edytor nic nie zmienił — puenta zostaje ta sama, tylko bez demonstracji: to uczeń musi patrzeć na klamry, nie na wcięcia.

**Naprawa:**
```csharp
if (wiek >= 18)
{
    Console.WriteLine("A");
    Console.WriteLine("B");
}
```

> **Zasada na cały kurs: zawsze pisz klamry, nawet przy jednej instrukcji.** Kosztują dwie linie i wykluczają całą klasę błędów. Zobaczysz kod bez klamer u innych — wtedy czytaj uważnie.

### D. `=` zamiast `==`

```csharp
int x = 1;
if (x = 5)
{
    Console.WriteLine("a");
}
```
→ `CS0029: Cannot implicitly convert type 'int' to 'bool'`

> „Co próbowałeś zrobić, a co napisałeś? Przypomnij sobie z 2.4, co robi pojedynczy `=`."
→ wkłada `5` do `x`, a wynikiem wkładania jest liczba. `if` chce `bool`.

C# łapie tę pomyłkę, bo warunek **musi** być `bool`. To ten sam mechanizm, który widziałeś w 2.4 przy `bool test = (a = b);`.

### E. Średnik zaraz po `if`

```csharp
int x = 1;
if (x == 1);
{
    Console.WriteLine("zawsze");
}
```
→ buduje się, ale z ostrzeżeniem:
```
warning CS0642: Possible mistaken empty statement
```
Uruchom: wypisze `zawsze` **niezależnie** od wartości `x`.

> „To drugie ostrzeżenie w tym kursie — pamiętasz pierwsze, z lekcji 3.2? Znowu: `warning`, nie `error`, program działa. Ale tym razem działa **źle**."

Rozłóż komunikat: średnik zamknął instrukcję `if`, więc `if` nie ma już co wykonywać. Klamry poniżej stały się zwykłym blokiem kodu, który wykonuje się zawsze.

> „Kiedy warto czytać ostrzeżenia?"
→ zawsze. To jest przykład ostrzeżenia, które oznacza prawdziwy błąd.

## Krok 4 — Pogłębienie (10 min)

**Porównywanie tekstów** — działa tak, jak uczeń by chciał:
```csharp
string haslo = "abc";
if (haslo == "abc")
{
    Console.WriteLine("Zgadza się");
}
```
> „`==` porównuje tu **treść**, nie to, czy to ten sam obiekt. Przy tekstach C# robi to, czego się spodziewasz."

Wielkość liter ma znaczenie: `"Abc" == "abc"` daje `false`. Niech uczeń sprawdzi.

**`if` w `if`** — pokaż, że się da, i od razu ostrzeż:
```csharp
if (ok)
{
    if (rok > 2000)
    {
        Console.WriteLine("Rocznik dwutysięczny");
    }
}
```
> „Każdy poziom to kolejne wcięcie. Trzy poziomy w głąb i kod robi się nieczytelny. W lekcji 4.2 poznasz sposób, żeby dwa warunki połączyć w jeden i nie zagnieżdżać."

**Nie ucz zagnieżdżania na siłę.** Jedno pokazanie, jedno ostrzeżenie, dalej.

**Czego `if` nie zrobi:**
```csharp
// if (wiek) { ... }        // CS0029 — wiek jest int, nie bool
```
> „W nawiasie musi być odpowiedź prawda/fałsz. Sama liczba nią nie jest."

**Kolejność w łańcuchu ma znaczenie:**
```csharp
int ocena = 5;
if (ocena >= 3) { Console.WriteLine("zdane"); }
else if (ocena == 5) { Console.WriteLine("piątka!"); }
```
> „Co się wypisze? Czemu druga gałąź nigdy nie zadziała?"
→ bo pierwsza łapie wszystko od 3 w górę. **W łańcuchu `else if` układaj warunki od najwęższego do najszerszego.**

## Krok 5 — Ćwiczenie

→ Skill `cwiczenie`. Temat: „instrukcja warunkowa". Propozycje:

- 🔥 **Rozgrzewka** (`08-if-a.cs`): zapytaj o wiek (przez `TryParse`). Jeśli odczyt się powiódł i wiek wynosi 18 lub więcej — wypisz `Pełnoletni`, w przeciwnym razie `Niepełnoletni`. Gdy odczyt się nie powiódł — `To nie jest liczba`.
- ⭐ **Główne** (`08-if-b.cs`): oceny. Zapytaj o ocenę (1–6). Wypisz jej słowny opis łańcuchem `else if`: 6 celujący, 5 bardzo dobry, 4 dobry, 3 dostateczny, 2 dopuszczający, 1 niedostateczny. Dla liczby spoza zakresu 1–6 wypisz `Nie ma takiej oceny`, a dla tekstu, który nie jest liczbą — `To nie jest ocena`.
- ⚡ **Gwiazdka** (`08-if-c.cs`): kalkulator kosztu dostawy. Zapytaj o wartość zamówienia. Zasady: powyżej 200 zł dostawa gratis, od 100 do 200 zł kosztuje 9,90 zł, poniżej 100 zł — 15,90 zł. Wypisz wartość zamówienia, koszt dostawy i sumę, wszystkie z dwoma miejscami po przecinku. **Ułóż warunki tak, żeby żaden nie był martwy** — sprawdź na kwotach 250, 150, 100, 200 i 50, czy wynik jest za każdym razem sensowny.

Gwiazdka celowo ma dwie granice (100 i 200), na których łatwo się pomylić o jeden. To pierwszy raz, gdy uczeń musi pomyśleć o przypadkach brzegowych sam.

## Pułapki

- **Brak klamer przy dwóch instrukcjach** — druga wykonuje się zawsze, a wcięcie sugeruje co innego. Najgroźniejsza pułapka lekcji, bo program się buduje i milczy.
- **Średnik po `if`** → `CS0642`, ostrzeżenie, program działa źle. Uczyć czytać ostrzeżenia.
- **`=` zamiast `==`** → `CS0029`. Tu C# ratuje; w wielu sytuacjach nikt by nie uratował.
- **Martwa gałąź w łańcuchu** — `if (x >= 3)` przed `else if (x == 5)`. Kompilator nie protestuje; gałąź po prostu nigdy nie zadziała.
- **Zapomniane `else`** — gdy żaden warunek nie pasuje, nie dzieje się nic. Często to błąd, którego nikt nie zauważa, bo brak wyniku wygląda jak brak danych.
- **Wielkość liter przy porównaniu tekstów** — `"Tak" == "tak"` to `false`.
- **`if (ok == true)`** — działa, ale jest nadmiarowe. Nie poprawiaj tego u ucznia więcej niż raz; to kwestia stylu, nie poprawności.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)

Ta lekcja nie ma zmian. `if`, `else if` i `else` wyglądają w C# tak samo od pierwszej wersji języka — każdy stary poradnik jest tu w pełni aktualny i warto to uczniowi powiedzieć, bo po module 1 mógł stracić zaufanie do starszych materiałów.

Jedna rzecz, której **nie** wprowadzamy: dopasowywanie wzorców (`if (x is > 18)`, `is not null`). Zwięzłe dla kogoś, kto już czyta C#; dla początkującego to kolejna składnia na to samo. Patrz `INDEX.md`.

## Notatki tutora

- **Krok 3.A jest emocjonalnie najważniejszy.** Uczeń czekał na to od lekcji 3.2 — program wreszcie reaguje. Nie przelatuj przez to; zapytaj wprost, czy widzi różnicę wobec poprzedniej lekcji.
- **Krok 3.C to serce lekcji technicznie.** Uczeń musi zgadnąć („nic się nie wypisze"), pomylić się i zobaczyć `B`. Bez tej pomyłki zasada „zawsze klamry" jest tylko zaleceniem, którego nikt nie przestrzega.
- **Nie obiecuj, co zrobi edytor** przy Format on Save w kroku 3.C. Zachowanie zależy od wersji rozszerzenia; potraktuj to jako eksperyment ucznia, nie jako fakt do zapowiedzenia.
- **Nie wprowadzaj `&&` ani `||`.** Uczeń będzie chciał („a jak sprawdzić dwie rzeczy naraz?") — to lekcja 4.2, następna. Nazwa i numer, wracacie do tematu.
- **Nie wprowadzaj `switch`.** Przy łańcuchu pięciu `else if` pokusa jest duża — lekcja 4.3.
- **Nie wprowadzaj pętli.** „A jak zapytać jeszcze raz, gdy się pomylił?" → moduł 5.
- **Zagnieżdżanie pokaż raz i ostrzeż.** Uczniowie, którzy nie znają `&&`, zagnieżdżają wszystko; lekcja 4.2 to naprawi za dzień lub dwa.
- Jeśli uczeń pisze warunki bez klamer, bo „krócej" — nie walcz stylem, wróć do kroku 3.C. Jeden `B` wypisany w złym miejscu przekonuje lepiej niż zasada.
