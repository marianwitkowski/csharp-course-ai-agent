# Lekcja 14.5 — Git: gałęzie, scalanie, konflikt

> **Druga i ostatnia lekcja o Gicie.** Po 14.2 uczeń ma historię jednej linii. Dziś dowiaduje się, jak pracować nad zmianą, **nie ruszając wersji, która działa** — i jak testy z 14.4 mówią mu, kiedy wolno ją wprowadzić.

## Cel
Po lekcji uczeń:
- Zakłada gałąź na nową funkcję i wie, że `main` przez ten czas się nie zmienia
- Scala gałąź do `main` i rozróżnia scalenie proste (fast-forward) od scalenia z osobnym commitem
- Rozpoznaje konflikt, czyta znaczniki `<<<<<<<` / `=======` / `>>>>>>>` i rozwiązuje go ręcznie
- Uruchamia `dotnet test` **przed** scaleniem i traktuje to jako regułę
- Wie, czym jest zdalne repozytorium i pull request, i zna komendy, żeby wypchnąć projekt na GitHuba — jeśli zechce

## Krok 1 — Zakotwiczenie (5 min)

**Pytanie wejściowe:**
> „Remontujesz kuchnię, ale nadal musisz w niej codziennie gotować. Jak to zorganizujesz?"

**Co chcesz usłyszeć:** remont kawałkami, albo gotowanie gdzie indziej, dopóki remont trwa. Nie rozwalasz wszystkiego naraz.

**Drugie pytanie:**
> „Twój program działa — etap 1 skończony, testy przechodzą. Zaczynasz etap 2 i przez trzy sesje będzie **zepsuty**, bo nowa funkcja jest w połowie. Co z wersją, która działa?"

**Co chcesz usłyszeć:** przepada, dopóki nie skończę. Chyba że mam kopię — a kopia to znów `v2_final` z lekcji 14.2.

> „Git ma na to **gałęzie**: dwie historie z tego samego miejsca, jedna dla wersji działającej, druga dla remontu. Gdy remont skończony — łączysz."

## Krok 2 — Mostek (12 min)

**Mostek:**
> „**Gałąź** to nazwana linia historii. Do tej pory miałeś jedną, `main`. Nowa gałąź zaczyna się od bieżącego commita i od tej chwili commity idą **na nią**, a `main` stoi w miejscu."

Uczeń wybiera z `README.md` **jedną** funkcję z etapu 2 — najmniejszą. Przykład poniżej zakłada „klasa `ListaZadan`", ale uczeń robi swoją.

```sh
cd kurs/projekt
git status
```
→ ma być `working tree clean`. Jeśli nie — commit najpierw (14.2).

```sh
git switch -c lista-zadan
```
→ `Switched to a new branch 'lista-zadan'`

```sh
git branch
```
→
```
* lista-zadan
  main
```

> „Gwiazdka — co oznacza?"
→ gałąź, na której **jesteś**. Commity pójdą tam.

> „`-c` w `switch -c`?"
→ **create**: utwórz i przełącz. Bez `-c` `switch` tylko przełącza na istniejącą.

**Nazwa gałęzi** mówi, co na niej powstaje: `lista-zadan`, `usuwanie`, `filtr-zrobione`. Małe litery, myślniki, bez spacji.

## Krok 3 — Eksperyment (28 min)

### A. Commit na gałęzi

Uczeń pisze pierwszy kawałek funkcji. W przykładzie — nowy plik `zadania/ListaZadan.cs`:

```csharp
public class ListaZadan
{
    private readonly List<Zadanie> zadania = new List<Zadanie>();

    public void Dodaj(string opis) => zadania.Add(new Zadanie { Id = zadania.Count + 1, Opis = opis });

    public int IleNiezrobionych() => zadania.Count(z => !z.Zrobione);
}
```

```sh
dotnet build zadania
git add .
git commit -m "Klasa ListaZadan: dodawanie i licznik"
```
→
```
[lista-zadan b23acce] Klasa ListaZadan: dodawanie i licznik
 1 file changed, 8 insertions(+)
 create mode 100644 zadania/ListaZadan.cs
```

> „W nawiasie kwadratowym było dotąd `main`. Co jest teraz?"
→ `lista-zadan`. Commit poszedł na gałąź.

```sh
git log --oneline
```
→
```
b23acce Klasa ListaZadan: dodawanie i licznik
0bb9653 Plik danych poza historią
bab02bb Zadanie dostaje Id
bff16c3 Szkielet projektu: klasa Zadanie
```

### B. Powrót na `main` — plik znika

```sh
git switch main
ls zadania
```
→ `Switched to branch 'main'`, a w katalogu: `Program.cs`, `Zadanie.cs`, `zadania.csproj`, `bin`, `obj`, `zadania.json` — **bez `ListaZadan.cs`**.

> „Gdzie jest plik, który przed chwilą napisałeś?"

Zanim uczeń spanikuje — `git log --oneline`:
```
0bb9653 Plik danych poza historią
bab02bb Zadanie dostaje Id
bff16c3 Szkielet projektu: klasa Zadanie
```

> „`main` nie ma tego commita, więc nie ma tego pliku. **`switch` przestawia cały katalog** na stan gałęzi. Plik jest bezpieczny — na gałęzi `lista-zadan`. Wróć tam i sprawdź."

```sh
git switch lista-zadan
ls zadania
```
→ `ListaZadan.cs` jest z powrotem.

**Zatrzymaj się tutaj.** To najważniejsze zaskoczenie lekcji: katalog na dysku pokazuje **jedną** gałąź naraz. Uczeń, który to zobaczył, nie pomyli już gałęzi z kopią katalogu.

> „Otwórz teraz VS Code — pasek na dole, po lewej, pokazuje nazwę gałęzi. Patrz tam, zanim zaczniesz pisać."

### C. Scalenie proste

Funkcja z etapu 2 gotowa? Zanim trafi do `main` — **testy**:

```sh
cd zadania.testy
dotnet test
cd ..
```
→ `Powodzenie!` jak w 14.4. Jeśli nie — naprawiasz na gałęzi; `main` czeka.

> „Czemu testy **przed** scaleniem, a nie po?"
→ po scaleniu zepsuta funkcja jest już w wersji, która miała działać. Przed — jest tylko na gałęzi i `main` nadal jest w porządku.

```sh
git switch main
git merge lista-zadan
```
→
```
Updating 0bb9653..b23acce
Fast-forward
 zadania/ListaZadan.cs | 8 ++++++++
 1 file changed, 8 insertions(+)
 create mode 100644 zadania/ListaZadan.cs
```

> „`Fast-forward` — przewinięcie do przodu. Dlaczego Git nazwał to tak?"
→ `main` nie ruszył się od rozgałęzienia, więc Git po prostu **przesunął** go na koniec gałęzi. Żadnego nowego commita, żadnego łączenia — historia wygląda, jakby gałęzi nie było:

```sh
git log --oneline
```
→
```
b23acce Klasa ListaZadan: dodawanie i licznik
0bb9653 Plik danych poza historią
bab02bb Zadanie dostaje Id
bff16c3 Szkielet projektu: klasa Zadanie
```

Gałąź zrobiła swoje:
```sh
git branch -d lista-zadan
```
→ `Deleted branch lista-zadan (was b23acce).`

> „Commit `b23acce` zniknął?"
→ nie — jest na `main`. Zniknęła tylko **etykieta**. Gałąź to nazwa wskazująca commit, nie katalog z kodem.

### D. Konflikt — gdy obie strony zmieniły to samo

Teraz sytuacja, w której Git **nie umie** scalić sam. Uczeń robi ją celowo, na `README.md`:

Na nowej gałęzi zmienia zdanie opisu:
```sh
git switch -c opis
```
W `README.md` linia opisu dostaje końcówkę „i pozwala je usuwać":
```sh
git commit -am "README: usuwanie"
```

Wraca na `main` i zmienia **tę samą linię** inaczej — końcówka „obsługiwany z terminala":
```sh
git switch main
git commit -am "README: terminal"
```

```sh
git merge opis
```
→
```
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
```

> „Git się zatrzymał. Nie zepsuł niczego — czeka na ciebie. Co mówi `git status`?"

```sh
git status
```
→
```
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   README.md
```

> „`both modified` — obie strony zmieniły ten plik. Git nie wie, która wersja jest dobra, bo **to nie jest pytanie do Gita**. Otwórz plik."

```markdown
# Zadania

<<<<<<< HEAD
Program, który trzyma moje zadania w pliku JSON, obsługiwany z terminala.
=======
Program, który trzyma moje zadania w pliku JSON i pozwala je usuwać.
>>>>>>> opis
```

**Rozbierz znaczniki pytaniami:**
- „Co jest między `<<<<<<< HEAD` a `=======`?" → wersja z `main` (`HEAD` to gałąź, na której jesteś)
- „A między `=======` a `>>>>>>> opis`?" → wersja z gałęzi `opis`
- „Która jest dobra?" → **żadna z osobna** — chcesz obie informacje

Uczeń pisze **jedną** wersję zdania i **usuwa wszystkie trzy znaczniki**:
```markdown
Program, który trzyma moje zadania w pliku JSON, obsługiwany z terminala, i pozwala je usuwać.
```

Sprawdzenie, że nic nie zostało:
```sh
grep -c "<<<<<<<\|=======\|>>>>>>>" README.md
```
→ `0`

```sh
git add README.md
git commit -m "Scalenie opisu: terminal i usuwanie"
```
→ `[main 0f463bc] Scalenie opisu: terminal i usuwanie`

> „`git add` po konflikcie znaczy: **rozwiązałem**. Dopóki go nie zrobisz, Git uważa plik za sporny."

```sh
git log --oneline --graph
```
→
```
*   0f463bc Scalenie opisu: terminal i usuwanie
|\
| * 019b03b README: usuwanie
* | 4280b32 README: terminal
|/
* b23acce Klasa ListaZadan: dodawanie i licznik
* 0bb9653 Plik danych poza historią
* bab02bb Zadanie dostaje Id
* bff16c3 Szkielet projektu: klasa Zadanie
```

> „Tym razem powstał osobny commit scalający, z dwoma rodzicami. Czemu nie było fast-forward?"
→ bo `main` **też** się ruszył po rozgałęzieniu. Przewinąć się nie da — trzeba połączyć.

```sh
git branch -d opis
```

### E. Wycofanie scalenia

Gdy konflikt jest za duży na dziś:
```sh
git merge --abort
```
→ katalog wraca do stanu sprzed `git merge`, `git status` mówi `working tree clean`. Gałąź czeka, nic nie przepada.

### F. Znaczniki w pliku `.cs`

> „Co się stanie, jeśli zostawisz znaczniki w pliku z kodem i zbudujesz?"

Uczeń może sprawdzić na kopii dowolnego pliku: `dotnet build` zgłasza
```
error CS8300: Napotkano znacznik konfliktu scalania
```

> „Kompilator zna te znaczniki. W kodzie C# nie da się ich przeoczyć. W `README.md` — da się, więc tam `grep`."

Ten komunikat jest po polsku, bo pochodzi z `dotnet`, nie z Gita — reszta lekcji jest angielska.

## Krok 4 — Pogłębienie (10 min)

**Reguła na cały etap 2**

```
1. git switch -c nazwa-funkcji        (z czystego main)
2. praca, commity na gałęzi           (cykl z 14.3)
3. dotnet test                         (na gałęzi, wszystko zielone)
4. git switch main && git merge nazwa-funkcji
5. git branch -d nazwa-funkcji
```

> „Jedna funkcja — jedna gałąź. Gałąź żyje dni, nie miesiące. Im dłużej żyje, tym więcej konfliktów przy scaleniu."

**Scalenie bez konfliktu, ale z commitem**

Gdy `main` i gałąź zmieniły **różne** pliki, Git scala sam, ale tworzy commit scalający i chce opisu. Podaj go od razu, żeby nie otworzył się edytor:
```sh
git merge nazwa -m "Scalenie: nazwa"
```
→ `Merge made by the 'ort' strategy.` i lista plików.

**Zdalne repozytorium — kod w drugim miejscu**

Wszystko, co dotąd zrobiłeś, żyje w `kurs/projekt/.git/` na jednym dysku. **Zdalne repozytorium** to kopia historii na serwerze — najczęściej GitHub. Po co:
- kopia poza laptopem
- druga osoba może pobrać kod, zmienić na swojej gałęzi i **poprosić o scalenie**
- ta prośba nazywa się **pull request**: gałąź, opis, czyjś przegląd, przycisk „Merge". To ten sam `git merge`, tylko z rozmową przed nim

Jeśli uczeń chce — komendy są trzy, a GitHub pokaże je sam po założeniu pustego repozytorium:
```sh
git remote add origin https://github.com/TWOJA-NAZWA/zadania.git
git push -u origin main
```
Potem, po każdej sesji: `git push`.

> „Konto, logowanie i pierwszy `push` — poza tą lekcją. Kurs nie zakłada, że chcesz pokazywać kod światu. Ale jeśli myślisz o pracy w programowaniu, to jest pierwsza rzecz z 14.7, którą zrobisz."

**`.gitignore` przed `push`**

> „Co wypchniesz na GitHub razem z kodem?"
→ **całą historię**. Jeśli kiedykolwiek zacommitowałeś hasło albo plik z danymi, jest w historii, nawet jeśli potem go usunąłeś. Gwiazdka z 14.2 miała powód.

## Krok 5 — Ćwiczenie

→ Skill `cwiczenie`. Temat: „gałęzie i scalanie". Wszystko na własnym projekcie w `kurs/projekt/`.

- 🔥 **Rozgrzewka**: gałąź `porzadki`, jeden commit poprawiający cokolwiek w `README.md`, `git switch main`, `git merge porzadki`, `git branch -d porzadki`. Wklej wynik `merge` i powiedz, czy był fast-forward i skąd wiesz.
- ⭐ **Główne**: **jedna funkcja z etapu 2** na własnej gałęzi. Co najmniej dwa commity na gałęzi, jeden test xUnit (14.4) dla tej funkcji, `dotnet test` zielone **przed** scaleniem. Po scaleniu `git log --oneline --graph` i `git branch` — ma zostać samo `main`.
- ⚡ **Gwiazdka**: zrób konflikt **celowo** i rozwiąż go. Na gałęzi i na `main` zmień tę samą linię w `README.md` (albo tę samą metodę w `.cs`) inaczej. Po `git merge` pokaż wynik `git status`, plik ze znacznikami, wersję po rozwiązaniu, `grep -c` równy `0`, `dotnet build` bez błędów i `git log --oneline --graph` z commitem o dwóch rodzicach. Na koniec sprawdź `git merge --abort` na drugim, świeżym konflikcie — pokaż `git status` po wycofaniu.

Gwiazdka jest jedynym miejscem w kursie, gdzie uczeń **sam** wywołuje konflikt. Kto raz go zrobił i rozwiązał, przy prawdziwym nie wpada w panikę.

## Pułapki

- **Commit na złej gałęzi** — najczęstsza. Objaw: `git log` na `main` pokazuje coś, co miało być na gałęzi. Nawyk: `git branch` (albo pasek VS Code) **przed** pierwszym commitem sesji.
- **`git switch` z niezapisanymi zmianami, które gałąź by nadpisała** → `error: Your local changes to the following files would be overwritten by checkout` i `Aborting`. Git odmawia, nic nie ginie. Commit albo `git restore`, potem `switch`.
- **Znaczniki zostawione w pliku** — w `.cs` łapie je `CS8300`; w `README.md`, `.json`, `.csproj` nie łapie nic. `grep` z kroku 3.D.
- **Rozwiązanie konfliktu = wybór jednej strony** — czasem, ale zwykle chodzi o **obie** zmiany naraz. Czytaj oba fragmenty, zanim skasujesz któryś.
- **`git branch -d` na niescalonej gałęzi** → `error: The branch 'x' is not fully merged.` Git chroni commity, których nigdzie indziej nie ma. Jeśli **na pewno** chcesz je stracić — `-D`; jeśli nie — najpierw `merge`.
- **Scalenie bez `dotnet test`** — testy są po to, żeby to pytanie zadać maszynie. Reguła z kroku 4.
- **Gałąź na cały etap 2** zamiast na jedną funkcję — po tygodniu konflikt na dziesięć plików. Małe gałęzie, częste scalanie.
- **`git merge` otwiera edytor** — brak `-m` przy scaleniu, które tworzy commit. Git wpisał już domyślny opis (`Merge branch 'nazwa'`), więc wyjście z `vim` przez `:q!` **nie przerywa** scalenia — commit powstaje z tym opisem. Sprawdź `git log --oneline -1`; jeśli tak się stało, nic nie naprawiaj, tylko następnym razem podaj `-m`.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)

Sekcja `[moduł 14]` nie obejmuje Gita. W starszych poradnikach uczeń zobaczy:

| Stare poradniki | Dzisiaj |
| --- | --- |
| `git checkout -b nazwa` | `git switch -c nazwa` (od Gita 2.23) |
| `git checkout nazwa` | `git switch nazwa` |
| gałąź `master` | `main` (ustawienie z 14.2, domyślne na GitHubie) |
| `Merge made by the 'recursive' strategy.` | `'ort'` — nowy algorytm scalania, ten sam wynik |

`checkout` nadal działa i robi trzy rzeczy naraz; `switch` robi jedną. Jeśli w cudzym poradniku jest `checkout -b`, to znaczy `switch -c`.

## Notatki tutora

- **Krok 3.B jest sercem lekcji** — plik „znika" po `switch main`. Nie uprzedzaj. Uczeń ma zobaczyć, poczuć niepokój i sam sprawdzić `git log`, że commit jest na drugiej gałęzi.
- **Konflikt w kroku 3.D robicie razem, w README.** Nie czekaj, aż przydarzy się w kodzie — wtedy uczeń ma dwa problemy naraz. Sztuczny konflikt na jednej linii tekstu uczy mechanizmu bez presji.
- **Nie wykonuj za ucznia `switch`, `merge`, `commit`, `push`.** Wolno ci `git status`, `git log --oneline --graph`, `git diff` — i powiedz, że to robisz.
- **`dotnet test` uruchamia uczeń.** Ty czytasz wklejony wynik.
- **Nie wprowadzaj `rebase`, `stash`, `cherry-pick`, `reset --hard`.** Uczeń, który pyta „a jak cofnąć commit" — jedno zdanie: „`git revert`, i jest to temat na później; na razie wystarczy, że nie scalasz niesprawdzonego".
- **GitHub tylko na życzenie.** Jeśli uczeń chce wypchnąć projekt, prowadź: konto, puste repozytorium bez README (GitHub pokaże komendy), `git remote add`, `git push -u origin main`. Uwierzytelnienie przez przeglądarkę albo token — GitHub prowadzi za rękę, ty nie musisz. **Nie zapisuj żadnych tokenów ucznia** i nie proś o ich wklejanie.
- **Uczeń na Windows:** komendy identyczne. `grep` z kroku 3.D → `Select-String "<<<<<<<|=======|>>>>>>>" README.md` w PowerShellu (brak wyniku = brak znaczników).
- Jeśli uczeń pracuje sam i pyta, po co mu gałęzie — odpowiedź jest w kroku 1: żeby `main` zawsze działał, także gdy etap 2 jest w połowie. Praca zespołowa to dodatkowy powód, nie jedyny.
