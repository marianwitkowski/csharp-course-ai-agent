# Lekcja 9.3 — Klasy abstrakcyjne

## Cel
Po lekcji uczeń:
- Oznacza klasę jako `abstract` i wie, że nie da się jej utworzyć
- Pisze metodę `abstract` — bez ciała, do obowiązkowej implementacji
- Rozumie różnicę: `virtual` „można podmienić", `abstract` „**trzeba** napisać"
- Rozpoznaje `CS0144` i `CS0534`
- Umie zdecydować, czy klasa bazowa powinna być zwykła czy abstrakcyjna

> **Tę lekcję otwiera pytanie z 9.2:** co to za zwierzę, które mówi „kropki"? Czy `new Zwierze("Coś")` w ogóle powinno być możliwe?

## Krok 1 — Zakotwiczenie (5 min)

**Pytanie wejściowe:**
> „Narysuj mi figurę geometryczną. Nie koło, nie kwadrat — po prostu figurę."

**Co chcesz usłyszeć:** nie da się. „Figura" to kategoria, nie konkret.

**Drugie pytanie:**
> „A czy pojęcie »figura« jest bezużyteczne, skoro nie da się jej narysować?"

**Co chcesz usłyszeć:** nie — mówi, czego można od każdej figury oczekiwać: że ma pole, obwód, nazwę.

**Trzecie pytanie:**
> „Gdybyś kazał komuś zrobić »jakąś figurę« i on przyniósł kartkę z napisem »figura«, byłbyś zadowolony?"

To jest `new Zwierze("Coś")` z lekcji 9.2. **Klasa bazowa, której obiekt nie ma sensu.**

## Krok 2 — Mostek (12 min)

Pokaż problem wprost:

```csharp
Zwierze z = new Zwierze("Coś");
z.Przedstaw();
```
→ `Coś mówi: ...`

> „Co to za zwierzę? Jak się nazywa gatunek »Coś«, który mówi kropki?"
→ takie zwierzę nie istnieje. Klasa `Zwierze` jest **kategorią**, nie konkretem.

**Mostek:**
> „Klasę, której obiektu nie da się utworzyć, oznacza się słowem `abstract`. Istnieje po to, żeby po niej dziedziczyć — i po nic więcej."

Uczeń tworzy `kurs/zadania/27-abstrakcyjne.cs`:

```csharp
abstract class Zwierze
{
    public string Imie { get; }
    protected Zwierze(string imie) => Imie = imie;

    public abstract string DajGlos();

    public void Przedstaw() => Console.WriteLine($"{Imie} mówi: {DajGlos()}");
}

class Kot : Zwierze
{
    public Kot(string imie) : base(imie) { }
    public override string DajGlos() => "miau";
}
```

```csharp
new Kot("Mruczek").Przedstaw();
```
→ `Mruczek mówi: miau`

A teraz:
```csharp
Zwierze z = new Zwierze("Coś");
```
→ `CS0144: Cannot create an instance of the abstract type or interface 'Zwierze'`

**Pytania:**
- „Co się zmieniło w klasie `Zwierze`? Dwa słowa."
- „Zauważ, że `DajGlos` **nie ma ciała** — kończy się średnikiem. Czemu?"
  → bo zwierzę w ogólności nie wie, jaki dźwięk wydaje. **To pochodna musi to powiedzieć.**
- „Czy `Przedstaw` też jest abstrakcyjne?"
  → nie. Ono wie, co robić — dla wszystkich tak samo.

Nazwij: **klasa abstrakcyjna**, **metoda abstrakcyjna**.

> **`abstract` na metodzie znaczy: »ta klasa nie umie tego zrobić, ale każda pochodna musi«.**

## Krok 3 — Eksperyment (22 min)

### A. Pochodna **musi** zaimplementować

```csharp
class Ryba : Zwierze
{
    public Ryba(string imie) : base(imie) { }
}
```
→ `CS0534: 'Ryba' does not implement inherited abstract member 'Zwierze.DajGlos()'`

> „Kompilator nie pozwala napisać ryby bez głosu. Porównaj to z `virtual` z lekcji 9.2 — tam pochodna **mogła**, ale nie musiała."

| | `virtual` | `abstract` |
| --- | --- | --- |
| ciało w bazie | jest | **nie ma** |
| pochodna musi nadpisać | nie | **tak** |
| da się utworzyć obiekt bazy | tak | **nie** |

> „Kiedy wybrać które?"
→ `virtual`, gdy istnieje sensowne zachowanie domyślne. `abstract`, gdy każdy przypadek musi zdecydować sam.

Naprawa:
```csharp
class Ryba : Zwierze
{
    public Ryba(string imie) : base(imie) { }
    public override string DajGlos() => "(cisza)";
}
```

> „Ryba milczy — ale **napisała to świadomie**. To jest różnica między »milczy, bo taka jest« a »milczy, bo ktoś zapomniał«."

### B. Właściwość abstrakcyjna

```csharp
abstract class Figura
{
    public abstract double Pole();
    public abstract string Nazwa { get; }
}

class Kolo : Figura
{
    private double r;
    public Kolo(double r) => this.r = r;
    public override double Pole() => Math.PI * r * r;
    public override string Nazwa => "Koło";
}

class Kwadrat : Figura
{
    private double a;
    public Kwadrat(double a) => this.a = a;
    public override double Pole() => a * a;
    public override string Nazwa => "Kwadrat";
}
```

```csharp
Figura[] figury = { new Kolo(2), new Kwadrat(3) };

foreach (Figura f in figury)
{
    Console.WriteLine($"{f.Nazwa}: {f.Pole():F2}");
}
```
→ `Koło: 12,57` i `Kwadrat: 9,00`

> „Tablica jest typu `Figura` — czyli typu, którego obiektu nie da się utworzyć. Czy to problem?"
→ nie. **Zmienna może być typu abstrakcyjnego; obiekt nie.** To jest dokładnie to, o czym mówił krok 3.F z lekcji 9.2.

### C. Klasa abstrakcyjna może mieć zwykłe składowe

```csharp
abstract class Figura
{
    public string Etykieta { get; set; } = "bez nazwy";

    public abstract double Pole();

    public void Opisz() => Console.WriteLine($"{Etykieta}: pole {Pole():F2}");
}
```

> „`Opisz` ma ciało i nie jest abstrakcyjne. `Etykieta` to zwykła właściwość. Co z tego wynika?"
→ klasa abstrakcyjna to **normalna klasa z dziurami**. Wypełnia je pochodna.

To jest jej największa przewaga nad interfejsem, o czym uczeń dowie się w module 10.

### D. Konstruktor w klasie abstrakcyjnej

> „Skoro nie da się utworzyć obiektu, po co jej konstruktor?"
→ bo **pochodne go wołają** przez `base(...)`. Konstruktor bazy wykonuje się przy tworzeniu każdej pochodnej.

Warto oznaczyć go `protected`:
```csharp
protected Zwierze(string imie) => Imie = imie;
```
> „`public` nie miałby sensu — nikt z zewnątrz i tak nie może go zawołać."

**To drobiazg stylistyczny.** Wspomnij, nie egzekwuj.

### E. Kiedy abstrakcyjna, a kiedy zwykła

Zapytaj o trzy przypadki i pozwól uczniowi zdecydować:

| Klasa bazowa | Abstrakcyjna? |
| --- | --- |
| `Zwierze` z metodą `DajGlos` | **tak** — „jakieś zwierzę" nie istnieje |
| `Pojazd` z `Marka` i `Rok` | zwykła może wystarczyć, jeśli sam pojazd ma sens |
| `Figura` z `Pole()` | **tak** — nie da się policzyć pola „figury" |
| `Pracownik` z `Wyplata()` | zależy: czy istnieje pracownik bez stanowiska? |

> „Pytanie rozstrzygające: **czy obiekt samej klasy bazowej ma sens w twoim programie?** Jeśli nie — `abstract`."

## Krok 4 — Pogłębienie (10 min)

**Trzy poziomy zobowiązania**

| Zapis | Znaczy |
| --- | --- |
| zwykła metoda | „robię to tak i koniec" |
| `virtual` | „robię tak, ale możesz zmienić" |
| `abstract` | „**ty** musisz to napisać" |

> „Idąc w dół tabeli, oddajesz coraz więcej decyzji klasom pochodnym."

**Klasa abstrakcyjna z samymi metodami abstrakcyjnymi**

> „Jeśli twoja klasa abstrakcyjna nie ma **żadnego** wspólnego kodu — same puste metody — to prawdopodobnie chciałeś **interfejsu**. To moduł 10."

Jedno zdanie, bez rozwijania. To jest naturalne wejście w następny moduł.

**Czego nie da się połączyć**

```csharp
// abstract i private
// abstract i static
```
> „Metoda abstrakcyjna musi być widoczna dla pochodnej (`protected` albo `public`) — inaczej nie dałoby się jej napisać."

**Wracamy do `object`**

Z lekcji 9.1 uczeń wie, że wszystko dziedziczy po `object`. Warto domknąć:

> „`object` **nie** jest abstrakcyjne — `new object()` jest legalne, choć rzadko przydatne. Za to jego `ToString` jest `virtual`, dlatego mogłeś je nadpisać w 8.2."

**Częsty wzorzec: szablon działania**

```csharp
abstract class Raport
{
    public void Generuj()
    {
        Console.WriteLine("=== POCZĄTEK ===");
        Tresc();
        Console.WriteLine("=== KONIEC ===");
    }

    protected abstract void Tresc();
}
```

> „Baza ustala **kolejność kroków**, pochodna wypełnia jeden z nich. Nagłówek i stopka są zawsze takie same."

To wzorzec, który uczeń rozpozna w wielu bibliotekach. **Pokaż, nie ćwicz.**

## Pułapki

- **`new` na klasie abstrakcyjnej** → `CS0144`.
- **Pochodna bez implementacji** → `CS0534`. Kompilator wymienia, czego brakuje.
- **Metoda abstrakcyjna z ciałem** → błąd. Abstrakcyjna kończy się średnikiem.
- **`abstract` bez `abstract` na klasie** — metoda abstrakcyjna wymusza abstrakcyjną klasę.
- **`private abstract`** — bez sensu i niedozwolone; pochodna musi ją widzieć.
- **Klasa abstrakcyjna bez wspólnego kodu** — to sygnał, że chciałeś interfejsu (moduł 10).
- **Zapominanie, że zmienna typu abstrakcyjnego jest legalna** — `Figura f = new Kolo(2);` jest w porządku i to jest sedno polimorfizmu.

## Notatki tutora

- **Krok 2 musi zacząć się od `new Zwierze("Coś")`.** Uczeń widział to w 9.2 i być może już mu to przeszkadzało. Nazwanie problemu przed rozwiązaniem jest połową lekcji.
- **Krok 3.A rób przez porównanie z 9.2.** Tabela `virtual` kontra `abstract` ma sens tylko wtedy, gdy uczeń pamięta, że tydzień temu pochodna **mogła** nie nadpisywać.
- **Nie wprowadzaj interfejsów.** Dwie wzmianki po jednym zdaniu — w kroku 3.C i 4. Obie zapowiadają moduł 10 i obie są celowe.
- **Wzorzec szablonu z kroku 4 pokaż, nie ćwicz** — poza gwiazdką, gdzie uczeń ma go użyć i uzasadnić.
- **Nie tłumacz, czemu `object` nie jest abstrakcyjne.** Jedno zdanie dla domknięcia i dalej.
- **Nie wprowadzaj `sealed override`** ani innych kombinacji. Poza kursem.
- Jeśli uczeń pyta, czy klasa abstrakcyjna może dziedziczyć po innej abstrakcyjnej — tak, i to normalne. Ale nie buduj z tego łańcucha; dwa poziomy wystarczą.
