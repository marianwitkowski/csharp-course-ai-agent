# Lekcja 10.3 — Kompozycja zamiast dziedziczenia

## Cel
Po lekcji uczeń:
- Odróżnia „**jest** rodzajem" od „**ma**" i wybiera właściwe narzędzie
- Buduje klasę z mniejszych obiektów zamiast dziedziczyć po jednej wielkiej
- Widzi, gdzie dziedziczenie zaczyna przeszkadzać
- Łączy kompozycję z interfejsem — najczęstszy układ w prawdziwym kodzie
- Umie uzasadnić swój wybór, a nie tylko go zapisać

> **To lekcja o decyzjach, nie o składni.** Nie ma tu ani jednego nowego słowa kluczowego. Jest za to najważniejsze pytanie projektowe w całym module 9 i 10.

## Krok 1 — Zakotwiczenie (5-8 min)

**Pytanie wejściowe — wróć do testu z lekcji 9.1:**
> „Silnik jest rodzajem samochodu?"

**Co chcesz usłyszeć:** nie — samochód **ma** silnik.

**Drugie pytanie:**
> „Wymień trzy rzeczy, które samochód **ma**, i jedną, którą **jest**."

**Co chcesz usłyszeć:** ma silnik, koła, radio; jest pojazdem.

**Trzecie pytanie — tu zaczyna się lekcja:**
> „Wymieniasz silnik na mocniejszy. Czy samochód przestaje być samochodem?"

**Co chcesz usłyszeć:** nie. **Części da się wymienić; rodzaju nie.**

To jest cała różnica: dziedziczenie ustala, czym rzecz **jest** — na stałe. Kompozycja ustala, co rzecz **ma** — i to da się zmienić.

## Krok 2 — Mostek (12 min)

**Pokaż problem na przykładzie, który się psuje.**

Uczeń projektuje pracowników z ćwiczenia 9.1, ale wymagania rosną:

```csharp
class Pracownik { }
class Handlowiec : Pracownik { }
class Kierownik : Pracownik { }
```

> „Teraz dochodzi wymaganie: jest kierownik, który też sprzedaje. Gdzie go wstawisz?"

Uczeń próbuje:
```csharp
class KierownikHandlowiec : Kierownik, Handlowiec { }
```
→ `CS1721` — dwie klasy bazowe. Znowu.

> „A gdyby doszedł jeszcze pracownik zdalny? I zdalny handlowiec? Ile klas będziesz mieć?"
→ przy trzech niezależnych cechach — osiem kombinacji. **Hierarchia wybucha.**

**Mostek:**
> „Zamiast dziedziczyć osiem razy, można powiedzieć: pracownik **ma** sposób wynagradzania. I ten sposób da się podmienić."

```csharp
interface ISposobWynagrodzenia
{
    decimal Oblicz(decimal podstawa);
}

class Etat : ISposobWynagrodzenia
{
    public decimal Oblicz(decimal podstawa) => podstawa;
}

class ZProwizja : ISposobWynagrodzenia
{
    private decimal prowizja;
    public ZProwizja(decimal prowizja) => this.prowizja = prowizja;
    public decimal Oblicz(decimal podstawa) => podstawa + prowizja;
}

class Pracownik
{
    public string Imie { get; }
    private decimal podstawa;
    private ISposobWynagrodzenia sposob;

    public Pracownik(string imie, decimal podstawa, ISposobWynagrodzenia sposob)
    {
        Imie = imie;
        this.podstawa = podstawa;
        this.sposob = sposob;
    }

    public decimal Wyplata() => sposob.Oblicz(podstawa);
}
```

```csharp
Pracownik a = new Pracownik("Ala", 5000, new Etat());
Pracownik b = new Pracownik("Bo", 4000, new ZProwizja(1500));

Console.WriteLine($"{a.Imie}: {a.Wyplata()}");
Console.WriteLine($"{b.Imie}: {b.Wyplata()}");
```
→ `Ala: 5000` i `Bo: 5500`

**Pytania:**
- „Ile klas `Pracownik` istnieje teraz?" → **jedna**
- „Co się zmienia między Alą a Bo?" → to, co dostały w konstruktorze
- „Ile klas trzeba dopisać dla nowego sposobu wynagradzania?" → jedną, i to **nie dotykając** `Pracownik`

Nazwij: **kompozycja** — budowanie obiektu z innych obiektów.

## Krok 3 — Eksperyment (20 min)

### A. Wymiana w trakcie działania

To jest rzecz, której dziedziczenie **nie potrafi**:

Wystarczy zamienić **prywatne pole** `sposob` na właściwość — resztę klasy zostawiasz bez zmian:

```csharp
class Pracownik
{
    public string Imie { get; }
    private decimal podstawa;

    public ISposobWynagrodzenia Sposob { get; set; }   // było: private ... sposob;

    public Pracownik(string imie, decimal podstawa, ISposobWynagrodzenia sposob)
    {
        Imie = imie;
        this.podstawa = podstawa;
        Sposob = sposob;
    }

    public decimal Wyplata() => Sposob.Oblicz(podstawa);
}
```

> **Uwaga:** `Wyplata()` musi teraz czytać **właściwość** `Sposob`, nie stare pole. Jeśli uczeń dopisze właściwość, a zostawi w metodzie `sposob`, podmiana nic nie da i wyjdzie dwa razy `4000` — bez żadnego błędu. To dobry moment na pytanie „skąd `Wyplata` bierze sposób?".

```csharp
Pracownik p = new Pracownik("Cyd", 4000, new Etat());
Console.WriteLine(p.Wyplata());

p.Sposob = new ZProwizja(2000);
Console.WriteLine(p.Wyplata());
```
→ `4000`, potem `6000`

> „Czy dałoby się zrobić to samo dziedziczeniem?"
→ **nie.** Obiekt utworzony jako `Handlowiec` jest handlowcem do końca życia. Typu nie da się zmienić.

To jest silnik z kroku 1: **część da się wymienić, rodzaju nie**.

### B. Kombinacje bez wybuchu

```csharp
Pracownik zdalnyHandlowiec = new Pracownik("Ewa", 4500, new ZProwizja(1000));
```

> „Ile klas potrzebujesz na cztery sposoby wynagradzania i trzy tryby pracy?"
→ przy dziedziczeniu: dwanaście. Przy kompozycji: **cztery plus trzy** — bo `Pracownik` dostaje drugą właściwość, np. `ITrybPracy Tryb`, dokładnie tak samo jak pierwszą. Osie są niezależne i każda dochodzi osobno.

**To jest główny argument praktyczny** i warto policzyć go razem z uczniem.

### C. Kompozycja bez interfejsu — zwykłe „ma"

Nie każda kompozycja potrzebuje interfejsu:

```csharp
class Silnik
{
    public int Moc { get; }
    public Silnik(int moc) => Moc = moc;
    public string Uruchom() => $"warkot ({Moc} KM)";
}

class Samochod
{
    public string Marka { get; }
    private Silnik silnik;

    public Samochod(string marka, Silnik silnik)
    {
        Marka = marka;
        this.silnik = silnik;
    }

    public void Odpal() => Console.WriteLine($"{Marka}: {silnik.Uruchom()}");
}
```

```csharp
new Samochod("Fiat", new Silnik(70)).Odpal();
```

> „Gdzie tu jest interfejs?"
→ nie ma. **Kompozycja to po prostu pole będące innym obiektem** — coś, co uczeń robił od lekcji 8.1, nie nazywając tego.

> „Kiedy dodać interfejs?"
→ gdy ta część ma być **wymienialna na inną**. Jeden silnik — pole wystarczy. Wiele rodzajów silnika — interfejs.

### D. Delegowanie — klasa oddaje robotę części

```csharp
class Koszyk
{
    private List<decimal> ceny = new List<decimal>();

    public void Dodaj(decimal cena) => ceny.Add(cena);
    public int Liczba => ceny.Count;
    public decimal Suma()
    {
        decimal suma = 0;
        foreach (decimal c in ceny) suma = suma + c;
        return suma;
    }
}
```

> „`Koszyk` **ma** listę, ale jej nie udostępnia. Pamiętasz to z lekcji 8.4?"
→ tak — to enkapsulacja. **Kompozycja i enkapsulacja to ta sama praktyka widziana z dwóch stron.**

> „Czy `Koszyk` mógłby zamiast tego **dziedziczyć** po `List<decimal>`?"
→ technicznie tak. Ale wtedy koszyk odziedziczyłby `Clear`, `RemoveAt`, `Insert` i wszystko inne — czyli dokładnie to, przed czym chroniłeś go w 8.4.

**To jest klasyczny przykład złego dziedziczenia:** koszyk **nie jest** listą, koszyk **ma** listę.

## Krok 4 — Pogłębienie (10 min)

**Tabela decyzyjna**

| Pytanie | Odpowiedź | Narzędzie |
| --- | --- | --- |
| „A jest rodzajem B?" | tak, na zawsze | dziedziczenie |
| „A ma B?" | tak | pole (kompozycja) |
| „A potrafi X?" | tak, ale nie jest rodziną | interfejs |
| „A potrafi X **na różne sposoby**?" | tak | interfejs + kompozycja |

> „Ostatni wiersz to układ, który zobaczysz w prawdziwym kodzie najczęściej."

**Kiedy dziedziczenie nadal jest właściwe**

Nie wyrzucaj go — w module 9 nie uczyliśmy się na darmo:

- `Figura` → `Kolo`, `Kwadrat` (9.3) — koło **jest** figurą i zawsze nią będzie
- `Zwierze` → `Kot`, `Pies` (9.1) — to samo
- gdy klasy pochodne **dzielą kod**, nie tylko zobowiązanie

> „Dziedziczenie jest dobre, gdy hierarchia jest **płytka**, **stabilna** i naprawdę opisuje rodzaje."

**Objawy, że dziedziczenie było złym wyborem**

- klasa pochodna nadpisuje metodę, żeby **nic nie robiła**
- klasa pochodna używa 10% tego, co odziedziczyła
- hierarchia rośnie wszerz przy każdym nowym wymaganiu
- pojawia się chęć dziedziczenia po dwóch klasach

> „Ostatni objaw jest najłatwiejszy do rozpoznania — kompilator sam go zgłasza jako `CS1721`."

**Podsumowanie modułów 9 i 10**

| Narzędzie | Odpowiada na | Poznane w |
| --- | --- | --- |
| dziedziczenie | „czym to jest" | 9.1 |
| polimorfizm | „jak to się zachowuje" | 9.2 |
| klasa abstrakcyjna | „czego wymagam od rodziny" | 9.3 |
| interfejs | „co to potrafi" | 10.1 |
| kompozycja | „z czego to się składa" | 10.3 |

> „Te pięć rzeczy to cały warsztat projektowania klas dla początkującego. Reszta to praktyka."

## Krok 5 — Ćwiczenie

→ Skill `cwiczenie`. Temat: „kompozycja". Propozycje:

- 🔥 **Rozgrzewka** (`31-kompozycja-a.cs`): klasa `Adres` z `Ulica` i `Miasto`. Klasa `Osoba` z `Imie` i **polem typu `Adres`**. Utwórz dwie osoby i wypisz ich pełne dane. Odpowiedz mi: czemu `Osoba` nie dziedziczy po `Adres`?
- ⭐ **Główne** (`31-kompozycja-b.cs`): przerób hierarchię powiadomień z ćwiczenia 9.2 na kompozycję. Interfejs `IKanal` z `Wyslij(string)`, trzy implementacje (`Email`, `Sms`, `Push`) i **jedna** klasa `Powiadomienie` z `Tresc` oraz polem `IKanal`. Wyślij pięć powiadomień różnymi kanałami. Dodaj możliwość **zmiany kanału** po utworzeniu i pokaż, że działa. Napisz mi, co ta wersja potrafi, czego nie potrafiła wersja z dziedziczeniem.
- ⚡ **Gwiazdka** (`31-kompozycja-c.cs`): kalkulator rabatów. Interfejs `IRabat` z `decimal Zastosuj(decimal kwota)`. Implementacje: `BezRabatu`, `Procentowy(10)`, `Kwotowy(50)`. Klasa `Zamowienie` z listą cen i polem `IRabat`. Policz sumę z rabatem dla trzech zamówień. Potem **rozszerz**: zrób `RabatLaczony`, który sam trzyma listę rabatów i stosuje je po kolei — czyli implementuje `IRabat` i **jednocześnie się nim składa**. Wyjaśnij mi, czemu to działa.

Gwiazdka to wzorzec, w którym implementacja interfejsu sama zawiera inne implementacje tego samego interfejsu. Uczeń, który go zrozumie, ma podstawę pod większość wzorców projektowych — których kurs celowo nie uczy.

## Pułapki

- **Dziedziczenie po `List<T>`** zamiast trzymania listy w polu — pochodna dostaje cały interfejs listy, w tym metody, których nie chcesz.
- **Interfejs tam, gdzie wystarczy pole** — jeden rodzaj silnika nie potrzebuje `ISilnik`.
- **Publiczne pole będące obiektem** — udostępnia całe wnętrze części. Ta sama dziura co z listą w 8.4.
- **Kompozycja bez enkapsulacji** — `public Silnik silnik;` pozwala zmienić silnik komukolwiek.
- **Zapominanie o `null`** — pole będące obiektem startuje jako `null` (8.1). Ustaw je w konstruktorze.
- **Hierarchia „na wszelki wypadek"** — trzy poziomy dziedziczenia przy dwóch klasach.
- **Odwrotna skrajność** — kompozycja tam, gdzie „jest rodzajem" jest oczywiste. `Kwadrat` naprawdę **jest** figurą.
