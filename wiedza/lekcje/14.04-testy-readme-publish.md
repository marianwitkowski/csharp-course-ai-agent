# Lekcja 14.4 — Testy, README, wydanie programu

## Cel
Po lekcji uczeń:
- Zakłada projekt testowy i podłącza go do projektu aplikacji
- Pisze testy z `[Fact]` i `[Theory]`, czyta wynik `dotnet test`
- Wie, dlaczego testowalny kod to ten z lekcji 14.3 (logika w klasach, bez `Console`)
- Pisze `README.md`, który wystarczy komuś obcemu
- Buduje wersję do wydania przez `dotnet publish` i wie, czego ona wymaga

> **To materiał na dwie sesje, nie na jedną.** Naturalna przerwa jest po kroku 3.F: testy działają, klasa jest `public`, uczeń ma co ćwiczyć. `README.md` i `dotnet publish` (kroki 3.G-3.H) to osobny temat — wydanie programu, nie jego sprawdzanie. Nie przeciągaj jednej sesji na siłę.

## Krok 1 — Zakotwiczenie (6 min)

**Pytanie wejściowe:**
> „Jak dotąd sprawdzałeś swój program?"

**Co chcesz usłyszeć:** uruchamiałem i patrzyłem.

> „Ile razy uruchomiłeś go w ostatniej sesji? I ile razy wklepywałeś te same dane?"

> „Teraz dołożysz nową funkcję. Skąd będziesz wiedział, że nie zepsułeś tych trzech, które już działały?"

**Co chcesz usłyszeć:** trzeba by sprawdzić wszystko od nowa. Ręcznie.

> „Testy to zapisane sprawdzanie. Piszesz raz, uruchamiasz jedną komendą — za każdym razem, gdy coś zmienisz."

## Krok 2 — Mostek (12 min)

Uczeń zakłada **drugi projekt**, obok pierwszego:

```sh
cd kurs/projekt
dotnet new xunit -o zadania.testy
cd zadania.testy
dotnet add reference ../zadania/zadania.csproj
```
→ `Do projektu zostało dodane odwołanie „..\zadania\zadania.csproj”.`

```
kurs/projekt/
├── zadania/           ← aplikacja
└── zadania.testy/     ← testy
```

**Pytania:**
- „Czemu osobny projekt, a nie plik obok `Program.cs`?" → bo testy **nie mają trafić** do programu, który oddajesz użytkownikowi
- „Co robi `add reference`?" → daje projektowi testów dostęp do klas aplikacji. Jednostronnie: aplikacja o testach nie wie.
- „`git status` w `kurs/projekt/` — co pokazuje?" → nowy katalog `zadania.testy/`, bez `bin/` i `obj/`. To dlatego repozytorium założyliśmy w `kurs/projekt/`, a nie w `zadania/` (14.2). Commit: `Projekt testowy`.

Niech uczeń skasuje wygenerowany `UnitTest1.cs` i utworzy `ZadanieTesty.cs`:

```csharp
public class ZadanieTesty
{
    [Fact]
    public void NoweZadanieJestNiezrobione()
    {
        Zadanie z = new Zadanie { Opis = "test" };

        Assert.False(z.Zrobione);
    }
}
```

```sh
dotnet test
```
→
```
Powodzenie!    — niepowodzenie:     0, powodzenie:     1, pominięto:     0, łącznie:     1
```

**Nazwij nowość składniową — jednym zdaniem:**
> „`[Fact]` w nawiasach kwadratowych to **atrybut**: etykieta przyklejona do metody, którą czyta narzędzie. Sam kompilator nic z nią nie robi — to `dotnet test` po niej rozpoznaje, co jest testem. Pierwszy i jedyny atrybut w tym kursie."

**Trzy części testu:**
| Część | W przykładzie |
| --- | --- |
| przygotuj dane | `new Zadanie { ... }` |
| wykonaj to, co sprawdzasz | tu: samo utworzenie |
| sprawdź wynik | `Assert.False(...)` |

## Krok 3 — Eksperyment (25 min)

### A. Test, który nie przechodzi

**Niech uczeń celowo zepsuje test** — zamieni `Assert.False` na `Assert.True`:
```
  Niepowodzenie ZadanieTesty.NoweZadanieJestNiezrobione [1 ms]
  Komunikat o błędzie:
   Assert.True() Failure
Expected: True
Actual:   False
  Ślad stosu:
     at ZadanieTesty.NoweZadanieJestNiezrobione() in .../ZadanieTesty.cs:line 7
```

> „Co dostajesz w komunikacie?"
→ nazwę testu, czego oczekiwano, co wyszło i **numer linii**.

> „To jest cała wartość testów: gdy coś się zepsuje, dowiadujesz się **co** i **gdzie**, bez zgadywania."

Niech przywróci `Assert.False` i uruchomi ponownie.

### B. `Assert` — kolejność argumentów

```csharp
Assert.Equal("[ ] mleko", z.ToString());
```

> „Który argument jest pierwszy?"
→ **oczekiwany**, potem faktyczny. Odwrotnie napisany test przechodzi tak samo, ale komunikat przy błędzie kłamie: pokaże twój wynik jako „oczekiwany".

Najczęściej używane:

| `Assert` | Sprawdza |
| --- | --- |
| `Assert.Equal(oczekiwane, faktyczne)` | równość |
| `Assert.True(warunek)` / `Assert.False(...)` | wartość logiczną |
| `Assert.Empty(kolekcja)` | że kolekcja jest pusta |
| `Assert.Single(kolekcja)` | że ma dokładnie jeden element |
| `Assert.Contains(element, kolekcja)` | obecność |
| `Assert.Throws<T>(() => ...)` | że kod rzuca wyjątek |

### C. Jeden test, wiele przypadków

```csharp
[Theory]
[InlineData(true, "[x] a")]
[InlineData(false, "[ ] a")]
public void ToStringPokazujeStan(bool zrobione, string oczekiwane)
{
    Zadanie z = new Zadanie { Opis = "a", Zrobione = zrobione };

    Assert.Equal(oczekiwane, z.ToString());
}
```
→ `dotnet test` policzy to jako **dwa** testy.

> „Skąd wartości parametrów?"
→ z `[InlineData]`. Każdy taki wiersz to osobne uruchomienie tej samej metody.

> „Kiedy `Theory`, a kiedy `Fact`?"
→ gdy różnica między przypadkami to **same dane**, a nie inny kod.

### D. Test klasy, która używa pliku

Tu widać, po co `Magazyn` dostawał ścieżkę w konstruktorze (14.3):

```csharp
[Fact]
public void ZapisIOdczytZachowujaDane()
{
    string plik = Path.GetTempFileName();
    Magazyn m = new Magazyn(plik);

    m.Zapisz(new List<Zadanie> { new Zadanie { Opis = "mleko" } });
    List<Zadanie> wczytane = m.Wczytaj();

    Assert.Single(wczytane);
    Assert.Equal("mleko", wczytane[0].Opis);

    File.Delete(plik);
}
```

> „Czemu `Path.GetTempFileName`, a nie `zadania.json`?"
→ żeby test **nie ruszał twoich prawdziwych danych**. To ta sama klasa `Path` z lekcji 12.2.

> „A gdyby `Magazyn` miał ścieżkę wpisaną na sztywno?"
→ ten test byłby niemożliwy. **Dlatego zależności podaje się z zewnątrz.**

### E. Czego przetestować się nie da

Niech uczeń spróbuje napisać test dla metody, która pyta użytkownika i wypisuje wynik.

> „Jak sprawdzisz coś, co czeka na `Console.ReadLine`?"
→ nie sprawdzisz. Test się zawiesi.

> „To jest praktyczne uzasadnienie zasady z 14.1: **`Program.cs` cienki, logika w klasach**. Nie chodziło o elegancję — chodziło o to, żeby dało się to sprawdzić."

Jeśli uczeń ma logikę wplecioną w `Program.cs` — **teraz jest moment, żeby ją wyjąć**. Prowadź pytaniami: „co ta pętla właściwie oblicza? jak nazwałbyś tę operację?"

### F. Klasa musi być `public`

Niech uczeń usunie `public` z klasy `Zadanie` i uruchomi `dotnet test`:
```
error CS0122: Element „Zadanie” jest niedostępny z powodu swojego poziomu ochrony.
```

> „Skąd znasz ten mechanizm?"
→ lekcja 8.4. Bez `public` klasa jest widoczna tylko w swoim projekcie, a testy są **osobnym** projektem.

### G. `README.md` — dla kogoś obcego

Uczeń uzupełnia plik z lekcji 14.1:

```markdown
# Zadania

Program, który trzyma listę zadań w pliku JSON i pozwala je dodawać,
oznaczać jako zrobione i wypisywać.

## Wymagania
.NET 10 (`dotnet --version`)

## Jak uruchomić
    cd zadania
    dotnet run -- lista
    dotnet run -- dodaj "kupić mleko"
    dotnet run -- zrobione 2

## Gdzie trzymane są dane
W pliku `zadania.json` w katalogu programu.

## Testy
    cd zadania.testy
    dotnet test
```

**Pytanie sprawdzające:**
> „Daj to komuś, kto nie zna projektu. Czy po przeczytaniu uruchomi program bez pytania cię o cokolwiek?"

To jedyne kryterium dobrego `README.md`.

### H. Wersja do wydania

```sh
cd zadania
dotnet publish -c Release
```
→ katalog `bin/Release/net10.0/publish/` z **pięcioma plikami** i rozmiarem rzędu 150 kB.

> „Pięć plików zamiast całego katalogu projektu. Co zniknęło?"
→ kod źródłowy, pliki tymczasowe, wszystko, czego program do działania nie potrzebuje.

**Uruchomienie — i pierwsza niespodzianka:**
```sh
cd bin/Release/net10.0/publish
./zadania
```
Jeśli uczeń instalował .NET skryptem `dotnet-install.sh` (skill `setup-dotnet`), czyli do katalogu `~/.dotnet`, zobaczy:
```
Download the .NET runtime:
https://aka.ms/dotnet-core-applaunch?missing_runtime=true...
```

> „Program się zbudował, ale nie umie znaleźć .NET. Dlaczego?"
→ ta wersja **nie zawiera** platformy .NET — zakłada, że jest zainstalowana w systemie. A twoja siedzi w katalogu domowym.

Dwa wyjścia, oba działają:
```sh
dotnet zadania.dll
DOTNET_ROOT=$HOME/.dotnet ./zadania
```

**Wersja, która działa u każdego:**
```sh
dotnet publish -c Release -r osx-arm64 --self-contained
```

> „Sprawdź rozmiar katalogu `publish` teraz."
→ dziesiątki megabajtów zamiast stu pięćdziesięciu kilobajtów. **Cała platforma .NET jest w środku** i program uruchamia się na komputerze, gdzie .NET nie ma wcale.

Identyfikator systemu (`-r`) dobiera się do odbiorcy:

| System | `-r` |
| --- | --- |
| macOS na Apple Silicon | `osx-arm64` |
| macOS na Intelu | `osx-x64` |
| Windows | `win-x64` |
| Linux | `linux-x64` |

> „Wybierasz system **odbiorcy**, nie swój. Budując na macOS możesz zrobić wersję dla Windows."

**Kod wyjścia — obietnica z lekcji 12.4**

```csharp
if (args.Length == 0)
{
    Console.WriteLine("Użycie: zadania <komenda>");
    return 1;
}

return 0;
```

> „W instrukcjach najwyższego poziomu `return` z liczbą staje się kodem wyjścia programu. Zero znaczy »udało się«. Skrypty i systemy budowania na tym polegają."

## Krok 4 — Pogłębienie (10 min)

**Co testować, a czego nie**

| Testuj | Nie testuj |
| --- | --- |
| własne obliczenia i reguły | `Console.WriteLine` |
| zachowanie przy pustych danych | kod frameworka i biblioteki standardowej |
| przypadki brzegowe z lekcji 14.3 | prostych właściwości `{ get; set; }` |
| to, co już raz się zepsuło | wszystkiego „dla procentów" |

> „Test pisze się **za każdy błąd, który znalazłeś**. Wtedy ten sam błąd nie wróci."

**Nazwy testów**

> „Nazwa testu to zdanie o tym, co ma być prawdą: `NoweZadanieJestNiezrobione`, `PustaListaDajeZeroNiezrobionych`. Gdy test padnie, sama nazwa ma mówić, co się zepsuło — dlatego mogą być długie."

**Kiedy uruchamiać testy**

> „Po każdej zmianie, która coś dodaje albo poprawia. `dotnet test` trwa sekundy, a ręczne sprawdzanie — minuty."

**Testy a projekt**

> „`dotnet publish` w projekcie aplikacji **nie zabierze** projektu testów. Użytkownik dostaje sam program."

**Czego tu nie ma**

> „Testy potrafią znacznie więcej: atrapy obiektów, testy integracyjne, pomiar pokrycia kodu, uruchamianie testów automatycznie po każdej zmianie w repozytorium. To osobny temat — dziś wystarczy `[Fact]`, `[Theory]` i `Assert`."

## Krok 5 — Ćwiczenie

→ Skill `cwiczenie`. Temat: „testy i wydanie projektu". Wszystko dotyczy **własnego projektu ucznia**:

- 🔥 **Rozgrzewka**: projekt testowy, podłączony referencją, z jednym przechodzącym `[Fact]` dla najprostszej metody w projekcie. Zepsuj go celowo, przeczytaj komunikat, napraw.
- ⭐ **Główne**: co najmniej pięć testów, w tym jeden `[Theory]` z trzema `[InlineData]`, jeden na pustą kolekcję i jeden na zapis-odczyt pliku na ścieżce tymczasowej. Uzupełniony `README.md` ze wszystkimi sekcjami z kroku 3.G.
- ⚡ **Gwiazdka**: znajdź w swoim programie sytuację, w której się wywraca albo zachowuje głupio (pusty plik, zły argument, tekst zamiast liczby). **Najpierw napisz test, który to pokazuje** — musi nie przechodzić. Potem napraw kod i pokaż, że test przechodzi. Na koniec zbuduj wersję samodzielną i uruchom ją spoza katalogu projektu.

Gwiazdka to pierwszy raz, gdy uczeń pisze test **przed** poprawką — i najlepszy sposób, żeby zrozumiał, po co testy istnieją.

## Pułapki

- **Brak `dotnet add reference`** → testy nie widzą klas aplikacji.
- **Klasa bez `public`** → `CS0122` przy `dotnet test`.
- **Odwrotna kolejność w `Assert.Equal`** — test działa, komunikat o błędzie myli.
- **Test logiki wplecionej w `Program.cs`** — nie da się. Trzeba najpierw wyjąć do klasy.
- **Test piszący do prawdziwego pliku danych** — kasuje pracę ucznia. `Path.GetTempFileName`.
- **`./program` po `dotnet publish`, gdy .NET siedzi w `~/.dotnet`** → komunikat „Download the .NET runtime". `dotnet program.dll` albo wersja samodzielna.
- **Wersja samodzielna zbudowana dla własnego systemu**, gdy program jest dla kogoś na innym.
- **Testy pisane „dla liczby"** — pięć sensownych jest warte więcej niż pięćdziesiąt na właściwości.

## Notatki tutora

- **Krok 3.E jest najważniejszy.** Jeśli uczeń ma logikę w `Program.cs`, ta lekcja jest momentem prawdy — pomóż mu ją wyjąć pytaniami, nie przepisując kodu za niego.
- **Atrybut nazwij jednym zdaniem i idź dalej.** Nie tłumacz, jak działa refleksja ani jak pisać własne atrybuty.
- **`dotnet test` uruchamia uczeń**, nie agent. Agent czyta wynik wklejony przez ucznia.
- **Nie wprowadzaj atrap (`Moq`) ani pokrycia kodu.** Jedno zdanie w kroku 4.
- **Nie wprowadzaj CI ani GitHub Actions.** To 14.7. Gałęzie i scalanie — następna lekcja (14.5), tu wystarczy commit po każdym kroku.
- **Nie każ pisać testów do wszystkiego.** Pięć sensownych wystarczy; nadmiar zniechęca skuteczniej niż brak.
- **Przy `publish` pokaż oba warianty**, ale nie każ rozumieć wewnętrznej różnicy — wystarczy zasada: „dla siebie zwykły, dla kogoś samodzielny".
- Jeśli uczeń zapyta o instalator albo publikację w sklepie — jedno zdanie i 14.7.
