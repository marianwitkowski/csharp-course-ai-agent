# Lekcja 14.2 — Implementacja

> **To nie jest lekcja na jedną sesję.** To scenariusz prowadzenia **każdej** sesji projektowej aż do skończenia etapu 1. Kroki 1-2 robisz raz, krok 3 — za każdym razem.

## Cel
Po lekcji uczeń:
- Pracuje cyklem: mały kawałek → uruchom → sprawdź → następny
- Trzyma logikę w klasach, a wypisywanie w `Program.cs`
- Zapisuje i wczytuje stan wzorcem z lekcji 12.3
- Umie znaleźć rozwiązanie czegoś, czego kurs nie uczył
- Kończy **etap 1** — program, który naprawdę działa

## Krok 1 — Zakotwiczenie (5 min, pierwsza sesja)

**Pytanie wejściowe:**
> „Masz szkielet i trzy pozycje w etapie 1. Od której zaczniesz?"

Cokolwiek odpowie:
> „A da się z tego wyjąć kawałek jeszcze mniejszy — taki, który sprawdzisz w minutę?"

**Naprowadź:** pierwszy kawałek to zwykle **dane** — klasa i lista wpisana na sztywno w kodzie. Bez wczytywania, bez zapisu, bez pytania użytkownika.

## Krok 2 — Mostek (10 min, pierwsza sesja)

**Mostek:**
> „Zasada na cały projekt: **zawsze miej działający program.** Nie pisz stu linii, żeby dopiero potem uruchomić. Napisz dziesięć, uruchom, sprawdź, pisz kolejne dziesięć."

**Cykl pracy — wypisz uczniowi i wracaj do niego:**
```
1. Wybierz NAJMNIEJSZY kawałek, który da się sprawdzić
2. Napisz go
3. Uruchom (dotnet run)
4. Sprawdź, czy robi to, czego oczekiwałeś
5. Działa? → następny kawałek
   Nie działa? → przeczytaj komunikat kompilatora, wróć do lekcji z tym tematem
```

**Przykładowa rozpiska pierwszej sesji (lista zadań):**

| Krok | Kawałek | Sprawdzenie |
| --- | --- | --- |
| 1 | klasa `Zadanie` + lista wpisana w kodzie | wypisuje się |
| 2 | metoda wypisująca listę z numerami | czytelna lista |
| 3 | zapis listy do JSON (12.3) | plik istnieje, widać treść w edytorze |
| 4 | odczyt z JSON | wczytane = zapisane |
| 5 | brak pliku → pusta lista, nie wyjątek | pierwsze uruchomienie działa |
| 6 | argument `dodaj` (12.4) | `dotnet run -- dodaj "test"` dodaje pozycję |

> „Sześć kroków, każdy sprawdzalny w minutę. Po każdym program **działa** — tylko robi mniej."

**Przypomnij o `--`:**
> „W projekcie argumenty podaje się tak samo: `dotnet run -- dodaj \"test\"`. Podwójny myślnik nadal oddziela argumenty `dotnet run` od twoich."

## Krok 3 — Prowadzenie sesji (każda kolejna sesja)

**Schemat dla agenta:**

1. **Start (5 min):** „Co zrobiłeś od ostatniego razu? Co działa, co nie?"
   Uczeń uruchamia program i pokazuje stan.
2. **Cel sesji (5 min):** „Co chcesz mieć na końcu dzisiejszej sesji?"
   Jeśli cel jest za duży — zawężaj pytaniem: „da się to podzielić na dwie części, z których pierwsza już coś daje?"
3. **Praca (40 min):** uczeń pisze, agent pyta.
4. **Zamknięcie (10 min):** uruchomienie całości, `dotnet build` bez ostrzeżeń, zapis następnego kroku w `README.md`.

**Pytania, które warto zadawać w trakcie:**

| Sytuacja | Pytanie |
| --- | --- |
| Metoda rośnie ponad ekran | „da się z tego wyjąć kawałek z własną nazwą?" |
| Powtórzony fragment | „widzisz to samo w dwóch miejscach — co z tym zrobisz?" |
| Połknięty wyjątek (`catch` bez treści) | „skąd użytkownik ma wiedzieć, że coś poszło nie tak?" |
| Zagnieżdżone `if` | „pamiętasz wczesne wyjście z lekcji 7.1?" |
| Publiczna lista wewnątrz klasy | „kto jeszcze może teraz do niej dopisać? pamiętasz 8.4?" |
| Kod, który działa „cudem" | „wytłumacz mi linia po linii, co się tu dzieje" |
| Uczeń chce funkcję z etapu 3 | „czy etap 1 jest skończony?" |
| Pętla, która filtruje i liczy | „to się da napisać jednym `Where`. Ale czy będzie czytelniej?" |

**Gdy uczeń nie umie czegoś, czego nie było w kursie** (data i czas, losowanie, sortowanie po kilku polach, formatowanie liczb):
> „Nie znasz tego — i tak właśnie wygląda codzienna praca. Wpisz w wyszukiwarkę »C# DateTime dokumentacja« i wejdź na `learn.microsoft.com`. Znajdź metodę i przeczytaj, co zwraca."

**To ważna umiejętność sama w sobie.** Nie podawaj gotowca — pokaż, gdzie szukać, i każ przeczytać, co metoda zwraca. Potem zapytaj: „co ta metoda zwraca i co z tym zrobisz?"

**Czego nie robić:** nie pisz kodu za ucznia. Także wtedy, gdy prosi. Prowadź pytaniami — to cała metoda tego kursu i w projekcie działa tak samo.

## Krok 4 — Pogłębienie (rozłożone na sesje)

**Kiedy dzielić na pliki**

- `Program.cs` powyżej ~50 linii → wydziel klasę
- osobna odpowiedzialność, którą da się nazwać → osobny plik
- **jedna klasa, jeden plik o tej samej nazwie** — to konwencja, której trzyma się cały świat C#

**Typowa struktura dojrzalszego projektu:**
```
kurs/projekt/zadania/
├── zadania.csproj
├── README.md
├── Program.cs         ← argumenty, wywołanie logiki, wypisywanie
├── Zadanie.cs         ← jedna sztuka danych
├── ListaZadan.cs      ← operacje na kolekcji: dodaj, oznacz, usuń
└── Magazyn.cs         ← zapis i odczyt JSON
```

> „Trzy klasy, każda odpowiada na inne pytanie: **co to jest**, **co się z tym robi**, **gdzie to leży**."

**Rozdzielenie warstw — zasada, która się opłaca**

```csharp
// ŹLE — metoda liczy i wypisuje
public void PoliczIWypisz()
{
    Console.WriteLine(zadania.Count(z => !z.Zrobione));
}

// LEPIEJ — metoda liczy, Program.cs wypisuje
public int IleNiezrobionych() => zadania.Count(z => !z.Zrobione);
```

> „Czemu druga wersja jest lepsza?"
→ da się ją sprawdzić testem bez czytania ekranu (14.3) i użyć w innym miejscu.

**Zasada w jednym zdaniu:** `Console.WriteLine` mieszka w `Program.cs`, nigdzie indziej.

**Wzorzec trwałości — z lekcji 12.3, teraz na serio**

```csharp
using System.Text.Json;
using System.Text.Encodings.Web;

public class Magazyn
{
    private readonly string sciezka;

    public Magazyn(string sciezka)
    {
        this.sciezka = sciezka;
    }

    public List<Zadanie> Wczytaj()
    {
        if (!File.Exists(sciezka))
        {
            return new List<Zadanie>();
        }

        return JsonSerializer.Deserialize<List<Zadanie>>(File.ReadAllText(sciezka))
               ?? new List<Zadanie>();
    }

    public void Zapisz(List<Zadanie> zadania)
    {
        var opcje = new JsonSerializerOptions
        {
            WriteIndented = true,
            Encoder = JavaScriptEncoder.UnsafeRelaxedJsonEscaping
        };

        File.WriteAllText(sciezka, JsonSerializer.Serialize(zadania, opcje));
    }
}
```

> **`readonly` przy polu** — obietnica z lekcji 2.2. Znaczy: wartość ustawiasz raz, w konstruktorze, i potem nikt jej nie zmieni. Nie musisz go używać; tutaj mówi wprost, że ścieżka jest stała przez całe życie obiektu.

Pytania do tego kodu:
- „Czemu brak pliku zwraca pustą listę, a nie wyjątek?" → pierwsze uruchomienie **musi** działać
- „Czemu `Magazyn` dostaje ścieżkę w konstruktorze, zamiast mieć ją wpisaną?" → bo wtedy w teście podasz inną (14.3)
- „Gdzie w tym kodzie jest `Console.WriteLine`?" → nigdzie. I dobrze.

> **Żadnych dyrektyw `#:property`** — w projekcie z `dotnet new console` JSON działa od razu. To ta obietnica z lekcji 12.3.

> **`using` na górze pliku wracają.** W projekcie `System.Text.Json` nie jest dołączony automatycznie — bez tych dwóch linii dostaniesz `CS0103: Nazwa „JsonSerializer" nie istnieje w bieżącym kontekście`. Ustawienie `ImplicitUsings` z lekcji 14.1 obejmuje tylko najczęstsze przestrzenie nazw: `System`, `System.Collections.Generic`, `System.IO`, `System.Linq`.

**Gdy projekt utyka — pytania ratunkowe**

- „Co dokładnie nie działa? Pokaż najmniejszy przypadek."
- „Kiedy ostatnio działało? Co się zmieniło od tamtej pory?"
- „Czy to musi być w etapie 1?"

**Przypadki brzegowe — pytaj o nie na każdej sesji**

| Pytanie | Skąd znane |
| --- | --- |
| „Co przy pustej liście?" | 13.2 — `Max` się wywraca |
| „Co, gdy plik nie istnieje?" | 12.1 |
| „Co, gdy plik jest zepsuty?" | 12.3 — `JsonException` |
| „Co, gdy użytkownik nie poda argumentu?" | 12.4 |
| „Co, gdy poda tekst zamiast liczby?" | 2.3 — `TryParse` |
| „Co przy powtórzonej nazwie?" | 6.3 |

> „Program, który obsługuje te sześć sytuacji, jest lepszy od większości pierwszych projektów."

## Krok 5 — Ćwiczenie

Ćwiczeniem jest projekt. **Kryteria zakończenia etapu 1:**

- [ ] program robi to, co obiecuje jedno zdanie z `README.md`
- [ ] `dotnet build` przechodzi bez ostrzeżeń
- [ ] dane przeżywają zamknięcie programu
- [ ] pierwsze uruchomienie (bez pliku danych) działa
- [ ] błędne dane od użytkownika nie wywracają programu
- [ ] `Program.cs` mieści się na ekranie
- [ ] logika siedzi w klasach `public`, każda w swoim pliku
- [ ] w `README.md` jest sekcja „Jak tego używać"

Gdy wszystkie punkty są odhaczone — **etap 1 skończony**. Powiedz to uczniowi wprost i pogratuluj; to pierwszy własny program w tym kursie.

## Pułapki

- **Sto linii przed pierwszym uruchomieniem** — potem nie wiadomo, co się zepsuło.
- **Przeskok do etapu 2 przed skończeniem etapu 1** — najczęstszy sposób na porzucenie projektu.
- **`Console.WriteLine` w środku logiki** — blokuje testy w 14.3.
- **Klasa bez `public`** — testy jej nie zobaczą (`CS0122`).
- **Pola zamiast właściwości** — JSON zapisze `{}` (12.3).
- **Ścieżka do pliku danych wpisana na sztywno** — nie da się jej podmienić w teście.
- **Brakujący `using System.Text.Json`** → `CS0103`. W projekcie dochodzi się do niego samemu.
- **Ignorowane ostrzeżenia kompilatora** — `CS8600` i spółka zwykle mają rację.
- **Przepisywanie działającego kodu, bo „brzydki"** — najpierw skończ etap, potem porządkuj.

## Notatki tutora

- **To lekcja na wiele sesji.** Nie próbuj jej „skończyć". Za każdym razem zaczynaj od kroku 3.
- **Nie pisz kodu za ucznia**, nawet gdy prosi i nawet gdy sesja się przedłuża. Prowadź pytaniami z tabeli w kroku 3.
- **Wolno `dotnet build`, nie wolno `dotnet run`.** Uczeń uruchamia sam i opowiada, co zobaczył — to część nauki.
- **Krok 4 rozłóż na sesje.** Rozdzielenie warstw wprowadź wtedy, gdy uczeń pierwszy raz napisze metodę, która liczy i wypisuje naraz. Wcześniej to abstrakcja bez problemu.
- **Pilnuj zakresu.** „Czy etap 1 jest skończony?" to najważniejsze pytanie tej lekcji.
- **Nie wprowadzaj nowych bibliotek ani NuGeta.** Wszystko, czego projekt potrzebuje, uczeń już zna.
- Jeśli uczeń chce zamiast projektu robić kolejne ćwiczenia — powiedz wprost, że projekt uczy czegoś, czego ćwiczenia nie nauczą: **prowadzenia własnej roboty przez kilka sesji**.
