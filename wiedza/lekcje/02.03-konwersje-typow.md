# Lekcja 2.3 — Konwersje typów

## Cel
Po lekcji uczeń:
- Rozumie, czemu `7 / 2` daje `3` — i umie to naprawić
- Wie, kiedy C# konwertuje typ sam, a kiedy trzeba napisać wprost
- Zamienia tekst na liczbę przez `int.Parse` i wie, kiedy to wybuchnie
- Używa `int.TryParse` i rozumie, po co istnieje
- Wie, że `(int)3.9` obcina, a nie zaokrągla

> **To najważniejsza lekcja modułu 2.** Dwie z trzech najczęstszych pułapek początkującego w C# są tutaj: dzielenie całkowite i `Parse` na danych od użytkownika.

## Krok 1 — Zakotwiczenie (5 min)

**Pytanie wejściowe:**
> „Masz 7 cukierków i 2 dzieci. Ile cukierków dostanie każde?"

**Co chcesz usłyszeć:** trzy, i jeden zostaje.

> „A gdybyś liczył 7 litrów wody rozlane do 2 butelek?"
→ 3,5 litra. Ta sama operacja, inny wynik — bo **cukierków nie da się przeciąć, a wody tak**.

**Drugie pytanie:**
> „Skąd komputer ma wiedzieć, czy dzielisz cukierki czy wodę?"

**Co chcesz usłyszeć:** z typu. To domyka pytanie zostawione otwarte na końcu lekcji 2.1.

## Krok 2 — Mostek (10 min)

**Mostek:**
> „C# patrzy na **typy**, nie na twoje intencje. Dwie liczby całkowite dzielone przez siebie dają liczbę całkowitą — bo `int` to cukierki. Żeby dostać wodę, przynajmniej jedna strona musi być `double`."

Uczeń tworzy `kurs/zadania/04-konwersje.cs`:

```csharp
Console.WriteLine(7 / 2);
Console.WriteLine(7.0 / 2);
```

> „Uruchom. Co widzisz? Co się zmieniło w kodzie między jedną a drugą linią?"
→ `3` i `3,5`. Zmieniła się jedna kropka i jedno zero.

**Pytanie kluczowe:**
> „Czy pierwsza linia to błąd?"
→ **Nie.** Program robi dokładnie to, co napisano. To najgroźniejszy rodzaj pomyłki: kompilator milczy, program działa, wynik jest zły.

Teraz nazwij: **konwersja typu** — zamiana wartości jednego typu na inny.

## Krok 3 — Eksperyment (25 min)

### A. Konwersja, którą C# zrobi sam

```csharp
int liczbaCalkowita = 7;
double zPrzecinkiem = liczbaCalkowita;
Console.WriteLine(zPrzecinkiem);
```
> „Zadziałało bez żadnego dodatkowego zapisu. Czemu C# się nie sprzeciwił, skoro to dwa różne typy?"
→ bo `7` mieści się w `double` bez straty. Nic nie ginie.

### B. Konwersja, której nie zrobi

```csharp
double cena = 19.99;
int cenaCalkowita = cena;
```
→ `CS0266: Cannot implicitly convert type 'double' to 'int'. An explicit conversion exists (are you missing a cast?)`

> „Przeczytaj komunikat do końca. Kompilator mówi ci nie tylko, co jest źle, ale i co zrobić."

Naprawa:
```csharp
int cenaCalkowita = (int)cena;
Console.WriteLine(cenaCalkowita);
```
→ `19`

> „Ile to jest 19,99 zaokrąglone? A co wypisał program?"
→ **obcina, nie zaokrągla.** To druga cicha pułapka lekcji.

```csharp
Console.WriteLine((int)3.9);      // 3
Console.WriteLine(Math.Round(3.9)); // 4
```

> „Kiedy chcesz obciąć, a kiedy zaokrąglić? Podaj przykład jednego i drugiego."
→ obcięcie: „ile pełnych paczek po 12 sztuk"; zaokrąglenie: „ile to jest w złotówkach".

**Nazwij `(int)`:** rzutowanie — nawias z nazwą typu przed wartością. „Piszesz je, bo coś ginie i C# chce, żebyś potwierdził, że wiesz."

### C. Naprawa dzielenia

Uczeń próbuje trzech wariantów:
```csharp
int a = 7;
int b = 2;

Console.WriteLine(a / b);                      // 3
Console.WriteLine((double)a / b);              // 3,5
Console.WriteLine(a / (double)b);              // 3,5
Console.WriteLine((double)(a / b));            // 3  ← uwaga!
```
> „Ostatnia linia daje 3, choć jest tam `(double)`. Dlaczego?"
→ bo nawias policzył się **najpierw**, jako dzielenie całkowite. Konwersja przyszła za późno.

To jest najlepsze pytanie tej lekcji. Daj uczniowi pomyśleć, nie podpowiadaj od razu.

### D. Tekst na liczbę

```csharp
string wpisane = "42";
int liczba = int.Parse(wpisane);
Console.WriteLine(liczba + 1);
```
→ `43`

> „A co, gdyby `wpisane` było `\"czterdzieści dwa\"`? Spróbuj."
→ program **przerywa działanie**:
```
Unhandled exception. System.FormatException: The input string 'czterdzieści dwa' was not in a correct format.
```

> „To nie jest komunikat kompilatora. Czym się różni od tych, które widziałeś do tej pory?"
→ program się **zbudował** i **uruchomił**, a przewrócił się dopiero w trakcie. Nowa kategoria problemu. (Pełne wyjaśnienie: moduł 11.)

### E. `TryParse` — wersja, która nie wywala programu

```csharp
string podejrzane = "czterdzieści dwa";

bool sieUdalo = int.TryParse(podejrzane, out int wynik);

Console.WriteLine(sieUdalo);
Console.WriteLine(wynik);
```
→ `False` i `0`

> „Uruchom. Co się stało z programem tym razem?"
→ **dokończył działanie.** Nie przewrócił się, choć tekst był ten sam co przed chwilą.

> „Jakiego typu jest `sieUdalo`? Znasz ten typ z lekcji 2.1."
→ `bool`. To jest cała różnica: `TryParse` **zwraca informację, czy się udało**, zamiast przerywać program.

> „A co wylądowało w `wynik`, skoro konwersja się nie powiodła?"
→ `0` — wartość domyślna. **Uwaga:** to znaczy, że samo zerowe `wynik` nic ci nie mówi; rozstrzyga `sieUdalo`. Ta pułapka wraca w module 4, gdy uczeń zacznie na tym budować warunki.

Teraz to samo z tekstem, który **jest** liczbą — niech uczeń podmieni `podejrzane` na `"42"` i uruchomi ponownie.
→ `True` i `42`

> „Czym `TryParse` różni się od `Parse`?"
→ `Parse` zwraca liczbę albo przewraca program. `TryParse` zwraca `bool` i **dodatkowo** wkłada liczbę do zmiennej podanej po `out`.

**Nie tłumacz teraz `out`.** Uczeń ma zobaczyć, że to działa; mechanizm poznaje w lekcji 7.3. Jedno zdanie, jeśli zapyta: „to sposób, żeby metoda oddała dwie rzeczy naraz".

**Zasada, która obowiązuje do końca kursu:**
> „Dane od użytkownika zawsze przez `TryParse`. `Parse` tylko wtedy, gdy jesteś pewien, że tekst jest liczbą — na przykład bo sam go przed chwilą stworzyłeś."

### F. Liczba na tekst

```csharp
int liczba = 42;
Console.WriteLine(liczba.ToString() + "0");
Console.WriteLine(liczba + 10);
```
→ `420` i `52`

> „Ta sama liczba, dwa różne wyniki. Co się zmieniło?"

## Krok 4 — Pogłębienie (10 min)

**Trzy sposoby na to samo — który wybrać:**

| Zapis | Co robi z tekstem, który nie jest liczbą |
| --- | --- |
| `int.Parse(s)` | przerywa program (`FormatException`) |
| `int.TryParse(s, out int x)` | zwraca `false`, program idzie dalej |
| `Convert.ToInt32(s)` | przerywa program — jak `Parse` |

> „`Convert.ToInt32` zobaczysz w starszych poradnikach. Robi praktycznie to samo co `Parse`. Używamy `Parse` i `TryParse`, bo są bardziej bezpośrednie."

**`double` też ma swoje `Parse` i `TryParse`** — działa tak samo:
```csharp
double.TryParse("3,14", out double d);
```
> **Uwaga: przy `double` liczy się ustawienie regionalne systemu.** Na polskim systemie separatorem jest przecinek, więc:
> - `double.TryParse("3,14", out var d)` → `True`, `d = 3,14`
> - `double.TryParse("3.14", out var d)` → `False`, `d = 0`
>
> Kropka **nie zadziała** — i nie jest to „niekoniecznie", tylko twarde `false`. Zaskakuje tym mocniej, że w **kodzie** piszesz `3.14` z kropką, a przy wczytywaniu z tekstu obowiązuje przecinek. To dwie różne rzeczy: literał w kodzie i tekst od użytkownika.

**Podsumowanie: kiedy C# konwertuje sam, a kiedy nie**

> Reguła jednym zdaniem: **jeśli nic nie ginie, C# zrobi to sam; jeśli coś ginie, musisz napisać wprost.**

```csharp
int  →  double     // sam       (7 mieści się w 7,0)
double  →  int     // rzutowanie ((int)19.99 gubi 0,99)
int  →  string     // .ToString() (to inna kategoria, nie liczba)
string  →  int     // Parse / TryParse (tekst może w ogóle nie być liczbą)
```

**Czego nie da się w ogóle:**
```csharp
// int flaga = true;   // CS0029: Cannot implicitly convert type 'bool' to 'int'
```
> „`bool` i liczba to dwa osobne światy. `true` nie jest jedynką, `false` nie jest zerem — nie ma między nimi żadnej automatycznej drogi."

Niech uczeń spróbuje sam i przeczyta komunikat: to ten sam `CS0029`, który widział przy tekście i liczbie. Trzeci raz ten sam kod błędu — warto to nazwać, bo uczy czytania komunikatów po numerze.

## Pułapki

- **Dzielenie całkowite** — `7 / 2` to `3`. Kompilator milczy. Najgroźniejsza pułapka całego modułu, bo nie daje żadnego sygnału.
- **`(double)(a / b)`** — nawias policzy się pierwszy, konwersja przyjdzie za późno. Konwertuj **przed** dzieleniem, nie po.
- **`(int)` obcina, nie zaokrągla** — `(int)3.9` to `3`. Do zaokrąglania `Math.Round`.
- **`int.Parse` na danych od użytkownika** — jedna literówka i program się przewraca. Zawsze `TryParse`.
- **Przecinek kontra kropka** — w kodzie `1.75`, w wyniku `1,75`, przy `double.Parse` liczą się ustawienia systemu. Trzy różne rzeczy, łatwo pomylić.
- **`out int wynik` wygląda dziwnie** — to deklaracja zmiennej w środku wywołania. Uczeń zapyta; odpowiedz: „tworzysz zmienną w miejscu, w którym jej potrzebujesz; szerzej w lekcji 7.3".
- **`CS0266` czytany do połowy** — komunikat zawiera podpowiedź („are you missing a cast?"). Ucz czytać do końca.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)

Sekcja `[moduł 2]`. Dwie rzeczy:

- **`out int wynik` w jednej linii** to C# 7. Starsze materiały pokazują dwie linie:
  ```csharp
  int wynik;
  bool sieUdalo = int.TryParse(s, out wynik);
  ```
  Obie formy działają. Uczymy krótszej — z deklaracją `out int wynik` w miejscu wywołania.
- **`Convert.ToInt32`** dominuje w materiałach z 2020. Nie jest błędem, ale `int.Parse` / `int.TryParse` są dziś częstsze i bardziej wprost mówią, co robią.

## Notatki tutora

- **Krok 3.C (`(double)(a / b)`) to najlepsze pytanie w module 2.** Nie skracaj go i nie podpowiadaj. Uczeń, który sam dojdzie, że nawias liczy się pierwszy, zrozumie coś ogólniejszego o kolejności działań, co przyda mu się przez cały kurs.
- **Krok 3.E celowo obywa się bez `if`.** `TryParse` zwraca `bool`, a `bool` uczeń zna z 2.1 — wystarczy przypisać wynik do zmiennej i go wypisać. Nie ulegaj pokusie pokazania `if (int.TryParse(...))`, choć tak wygląda ten kod w każdym prawdziwym programie: to moduł 4 i tam wróci. Uczeń, który dziś zobaczy sam `bool`, w module 4 zrozumie warunek od razu.
- **Nie wprowadzaj interpolacji `$"..."`.** W tej lekcji nie ma jej w żadnym przykładzie i tak ma zostać — sklejanie przez `+` z ćwiczenia w lekcji 2.1 w zupełności wystarcza. Interpolacja to 3.1.
- **`out` pokazujesz, nie tłumaczysz.** Jeśli uczeń zapyta: „to sposób, żeby metoda oddała dwie rzeczy naraz — lekcja 7.3". Ani słowa więcej.
- **`FormatException` w kroku 3.D to pierwszy wyjątek w kursie.** Nie tłumacz mechanizmu. Wystarczy: „program się przewrócił w trakcie działania — to inna kategoria niż błąd kompilacji; nauczysz się to obsługiwać w module 11".
- **Ta lekcja jest długa.** Jeśli uczeń jest nasycony po kroku 3.C, przenieś `Parse`/`TryParse` (3.D-3.F) na osobną sesję. Lepiej dwie krótkie niż jedna, po której nic nie zostaje. Ale **nie rozbijaj przed 3.C** — dzielenie całkowite musi się domknąć w jednym posiedzeniu.
- Jeśli uczeń zna Excela: `(int)` odpowiada funkcji `ZAOKR.DO.CAŁK`, a nie `ZAOKR`. Analogia działa dobrze.
