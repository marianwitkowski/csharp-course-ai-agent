# Lekcja 11.2 — `throw`, własne wyjątki i `using`

## Cel
Po lekcji uczeń:
- Rzuca wyjątek przez `throw`, gdy jego metoda dostaje bezsensowne dane
- Wybiera gotowy typ wyjątku zamiast wymyślać własny bez potrzeby
- Pisze własną klasę wyjątku dziedziczącą po `Exception`
- Używa `using`, żeby zasób zamknął się sam — nawet przy wyjątku
- Wie, że `using` opiera się na interfejsie `IDisposable`

## Krok 1 — Zakotwiczenie (5 min)

**Pytanie wejściowe:**
> „Prosisz kogoś: »policz średnią z tej listy ocen«. Lista jest pusta. Co ta osoba powinna odpowiedzieć?"

**Co chcesz usłyszeć:** że się nie da — a nie zmyślić zero.

**Drugie pytanie:**
> „Twoja metoda `Wplac(kwota)` z lekcji 8.4 przy kwocie ujemnej wypisywała komunikat i wracała. Kto zobaczy ten komunikat, jeśli program nie ma konsoli — bo jest częścią większej aplikacji?"

**Co chcesz usłyszeć:** nikt. **Wypisanie na ekran to nie jest zgłoszenie problemu** — to tylko napis.

**Trzecie pytanie:**
> „Wychodzisz z pokoju i zostawiasz zapalone światło. Kto je zgasi?"

To jest `using` — nie nazywaj jeszcze.

## Krok 2 — Mostek (12 min)

Wróć do metody z lekcji 8.4:

```csharp
public void Wplac(decimal kwota)
{
    if (kwota <= 0)
    {
        Console.WriteLine("Kwota musi być dodatnia.");
        return;
    }
    saldo = saldo + kwota;
}
```

> „Co robi ta metoda, gdy dostanie kwotę ujemną?"
→ wypisuje coś i **udaje, że wszystko w porządku**. Wywołujący nie ma pojęcia, że nic się nie stało.

**Mostek:**
> „Zamiast wypisywać, metoda może **zgłosić problem** — rzucić wyjątek. Robi to słowem `throw`."

Uczeń tworzy `kurs/zadania/33-throw-using.cs`:

```csharp
try
{
    Sprawdz(-5);
}
catch (ArgumentException e)
{
    Console.WriteLine($"Złapane: {e.Message}");
}

void Sprawdz(int wiek)
{
    if (wiek < 0)
    {
        throw new ArgumentException($"Wiek nie może być ujemny: {wiek}");
    }

    Console.WriteLine($"Wiek {wiek} jest w porządku.");
}
```
→ `Złapane: Wiek nie może być ujemny: -5`

**Pytania:**
- „Co robi `throw`?" → przerywa metodę i **przekazuje problem wywołującemu**
- „Czy kod po `throw` się wykonał?" → nie, jak po `return`
- „Kto decyduje, co z tym zrobić?" → **wywołujący**, nie metoda

Nazwij: **rzucenie wyjątku**, **`throw`**.

> **To jest podstawowa różnica:** metoda, która wypisuje komunikat, **decyduje za wszystkich**. Metoda, która rzuca wyjątek, **zgłasza fakt** i zostawia decyzję temu, kto ją wywołał.

## Krok 3 — Eksperyment (25 min)

### A. Gotowe typy wyjątków

C# ma sporo wyjątków na typowe sytuacje. Nie wymyślaj własnych bez potrzeby:

| Sytuacja | Wyjątek |
| --- | --- |
| zły argument | `ArgumentException` |
| argument poza zakresem | `ArgumentOutOfRangeException` |
| argument jest niczym | `ArgumentNullException` |
| operacja niemożliwa w tym stanie | `InvalidOperationException` |

```csharp
void UstawWiek(int wiek)
{
    if (wiek < 0 || wiek > 120)
    {
        throw new ArgumentOutOfRangeException(nameof(wiek), $"Wiek musi być z zakresu 0-120, dostałem {wiek}");
    }
}
```

> „`nameof(wiek)` wstawia **nazwę parametru** jako tekst. Po co?"
→ żeby komunikat mówił, **który** argument był zły. Przy trzech parametrach to oszczędza zgadywania.

Uczeń zobaczy wtedy:
```
Wiek musi być z zakresu 0-120, dostałem 200 (Parameter 'wiek')
```
> „Nazwa parametru doklejona na końcu w nawiasie — to robi sam `ArgumentOutOfRangeException`, nie ty."

**`nameof` to nowe narzędzie** — jedno zdanie i dalej.

### B. Wyjątek zamiast cichego zera

Wróć do średniej z kroku 1:

```csharp
double Srednia(int[] oceny)
{
    if (oceny.Length == 0)
    {
        throw new ArgumentException("Nie da się policzyć średniej z pustej listy.");
    }

    int suma = 0;
    foreach (int o in oceny) suma = suma + o;
    return (double)suma / oceny.Length;
}
```

> „W lekcji 8.4 pisałeś podobną metodę zwracającą zero dla pustej listy. Która wersja jest lepsza?"

**Nie ma jednej odpowiedzi** i warto to powiedzieć:
- zero jest w porządku, gdy „brak ocen" to normalna sytuacja
- wyjątek jest lepszy, gdy pusta lista oznacza **błąd w programie**

> „Pytanie rozstrzygające: **czy to się ma prawo zdarzyć?** Jeśli tak — zwróć wartość. Jeśli nie — rzuć wyjątek."

### C. Własny typ wyjątku

Gdy żaden gotowy nie pasuje:

```csharp
class SaldoException : Exception
{
    public SaldoException(string komunikat) : base(komunikat)
    {
    }
}
```

> „Ile linii ma ta klasa? Co robi konstruktor?"
→ przekazuje komunikat do klasy bazowej przez `base(...)` — dokładnie jak w lekcji 9.1.

Użycie:
```csharp
try
{
    Wyplac(1000, saldo: 100);
}
catch (SaldoException e)
{
    Console.WriteLine($"Problem z saldem: {e.Message}");
}

void Wyplac(decimal kwota, decimal saldo)
{
    if (kwota > saldo)
    {
        throw new SaldoException($"Brak środków: masz {saldo}, chcesz {kwota}");
    }
}
```

> „Po co własny typ, skoro `ArgumentException` też by zadziałał?"
→ żeby wywołujący mógł złapać **dokładnie tę** sytuację, a inne przepuścić dalej.

**Zasada:** własny wyjątek wtedy, gdy ktoś będzie chciał go łapać **osobno**. Inaczej — gotowy typ.

### D. `using` — zamknij po sobie

Przypomnij `finally` z lekcji 11.1: służyło do sprzątania. `using` robi to samo, krócej.

```csharp
class Zasob : IDisposable
{
    private string nazwa;

    public Zasob(string nazwa)
    {
        this.nazwa = nazwa;
        Console.WriteLine($"otwarto {nazwa}");
    }

    public void Uzyj() => Console.WriteLine($"używam {nazwa}");

    public void Dispose() => Console.WriteLine($"zamknięto {nazwa}");
}
```

```csharp
using (Zasob z = new Zasob("plik.txt"))
{
    z.Uzyj();
}

Console.WriteLine("po bloku");
```
→
```
otwarto plik.txt
używam plik.txt
zamknięto plik.txt
po bloku
```

> „Kto wywołał `Dispose`? Nie ma go w twoim kodzie."
→ **`using` sam**, na wyjściu z bloku.

Teraz najważniejsze — niech uczeń rzuci wyjątek w środku:
```csharp
using (Zasob z = new Zasob("plik.txt"))
{
    z.Uzyj();
    throw new Exception("coś poszło źle");
}
```
→ `zamknięto plik.txt` **wykonuje się mimo wyjątku**.

> „To jest to samo, co `finally` z 11.1 — tylko nie musisz go pisać."

### E. `using` opiera się na interfejsie

> „Co musi spełnić klasa, żeby dało się jej użyć w `using`?"
→ musi implementować **`IDisposable`** — interfejs z jedną metodą `Dispose()`.

To jest interfejs z lekcji 10.1 w praktyce. Spróbuj bez niego:
```csharp
class Zwykla { }
using (Zwykla z = new Zwykla()) { }
```
→ `CS1674: 'Zwykla': type used in a using statement must implement 'System.IDisposable'.`

> „W lekcji 10.2 mówiłem, że biblioteka C# stoi na interfejsach. `using` to kolejny dowód: nie zna twojej klasy, zna tylko kontrakt."

### F. Krótszy zapis `using`

```csharp
using Zasob z = new Zasob("plik.txt");
z.Uzyj();
Console.WriteLine("koniec bloku");
```

> „Bez nawiasów i bez klamer. Kiedy zostanie wywołane `Dispose`?"
→ na końcu **bloku, w którym stoi deklaracja** — tutaj na końcu programu.

Obie formy są poprawne. **Wersję z klamrami pokazuj pierwszą** — w niej wprost widać, gdzie kończy się życie zasobu.

## Krok 4 — Pogłębienie (10 min)

**Gdzie `using` przyda się naprawdę**

> „Sam raczej nie będziesz pisał klas z `Dispose`. Ale w module 12 otworzysz plik — i wtedy `using` będzie obowiązkowy, bo niezamknięty plik zostaje zablokowany."

To zapowiedź, nie dygresja: `StreamReader` i `StreamWriter` z lekcji 12.1 wymagają dokładnie tego.

**`throw` w bloku `catch` — przekaż dalej**

```csharp
try
{
    Ryzykowne();
}
catch (FormatException e)
{
    Console.WriteLine("Zapisuję do dziennika...");
    throw;
}
```

> „Samo `throw;` bez niczego po nim **rzuca ten sam wyjątek dalej**. Do czego to służy?"
→ do zareagowania (zapisania, posprzątania) **bez** przejmowania odpowiedzialności za decyzję.

> „Uwaga: `throw e;` zamiast `throw;` **gubi** informację, skąd wyjątek przyszedł. Pisz samo `throw;`."

To subtelne i warte jednego zdania.

**Czego nie robić**

- nie rzucaj `Exception` — jest zbyt ogólny, nikt go sensownie nie złapie
- nie używaj wyjątków do sterowania normalnym przebiegiem (11.1, krok 3.D)
- nie łap własnego wyjątku w tej samej metodzie, w której go rzuciłeś — to `if` napisany okrężnie

**Podsumowanie: `TryCoś`, wartość specjalna czy wyjątek?**

| Sytuacja | Rozwiązanie |
| --- | --- |
| zły wpis użytkownika | `TryParse` (2.3) |
| brak klucza w słowniku | `TryGetValue` (6.3) |
| „nie znalazłem" w liście | `-1` z `IndexOf` (6.2) |
| pusta lista, gdy to normalne | zwróć zero |
| argument, który nie ma prawa być zły | **wyjątek** |
| plik, którego nie ma | **wyjątek** (moduł 12) |

> „Ta tabela to podsumowanie całego kursu w kwestii błędów. Trzy różne narzędzia, każde do czego innego."

## Krok 5 — Ćwiczenie

→ Skill `cwiczenie`. Temat: „`throw` i `using`". Propozycje:

- 🔥 **Rozgrzewka** (`33-throw-a.cs`): metoda `double PierwiastekKwadratowy(double x)` rzucająca `ArgumentOutOfRangeException` dla liczb ujemnych. Wywołaj ją trzy razy: dla 16, 0 i −4, łapiąc wyjątek.
- ⭐ **Główne** (`33-throw-b.cs`): rozwiń klasę `Konto` z lekcji 8.4. Zamiast wypisywać komunikaty, `Wplac` ma rzucać `ArgumentOutOfRangeException` przy kwocie niedodatniej, a `Wyplac` — własny wyjątek `BrakSrodkowException` przy zbyt dużej kwocie. Napisz program obsługujący oba osobno. Odpowiedz mi: co zyskała klasa `Konto` względem wersji z 8.4?
- ⚡ **Gwiazdka** (`33-throw-c.cs`): klasa `Sesja` implementująca `IDisposable`, która przy tworzeniu wypisuje `otwarto sesję`, ma metodę `Zapisz(string)` i przy `Dispose` wypisuje `zamknięto sesję`. Użyj jej w trzech scenariuszach: normalnym, z wyjątkiem w środku bloku i z `return` w środku metody. Pokaż mi wszystkie trzy wyniki i napisz, w ilu z nich sesja została zamknięta.

Odpowiedź na gwiazdkę: **we wszystkich trzech**. To jest cały sens `using`.

## Pułapki

- **`throw` bez `new`** — `throw ArgumentException;` nie skompiluje się. Rzuca się **obiekt**.
- **`throw e;` zamiast `throw;`** — gubi ślad pochodzenia wyjątku.
- **Rzucanie `Exception`** — zbyt ogólne, nie da się sensownie złapać.
- **Własny wyjątek bez konstruktora z komunikatem** — `e.Message` będzie pusty albo domyślny.
- **Klasa wyjątku niedziedzicząca po `Exception`** → nie da się jej rzucić.
- **`using` na klasie bez `IDisposable`** → błąd kompilacji.
- **Zapomniany `using` przy pliku** — plik zostaje otwarty i zablokowany. Wraca w module 12.
- **Łapanie własnego wyjątku obok miejsca rzucenia** — okrężny `if`.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)

Sekcja `[moduł 11]`. Dwie rzeczy:

- **`using` bez klamer** (deklaracja zamiast bloku) to C# 8. Starsze materiały pokazują wyłącznie wersję z nawiasami i klamrami. Obie działają.
- **`nameof`** to C# 6. Wcześniej wpisywano nazwę parametru jako zwykły tekst — i po zmianie nazwy komunikat zaczynał kłamać.

## Notatki tutora

- **Krok 2 musi odwołać się do `Konto` z 8.4.** Uczeń napisał tam metodę, która wypisuje komunikat i wraca; teraz widzi, że to było ciche udawanie sukcesu.
- **Krok 3.B nie ma jednej poprawnej odpowiedzi i tak trzeba to powiedzieć.** „Czy to się ma prawo zdarzyć?" jest ważniejsze niż reguła.
- **Krok 3.D z wyjątkiem w środku `using`** to sedno lekcji. Bez tego `using` wygląda na skrót składniowy, a nie na gwarancję.
- **Nie wprowadzaj `try`/`finally` ręcznie zamiast `using`.** Uczeń zna `finally` z 11.1; wystarczy powiedzieć, że `using` to jego skrót.
- **Nie tłumacz `IDisposable` głębiej.** Jedna metoda, jeden kontrakt.
- **Nie wprowadzaj `IAsyncDisposable`** ani finalizatorów. Poza kursem.
- **Nie każ pisać własnych wyjątków na siłę.** Krok 3.C kończy się zasadą: gotowy typ, chyba że ktoś ma łapać osobno.
- **Moduł 11 jest krótki (dwie lekcje) i to celowe.** Obsługa błędów jest ważna, ale uczeń poznał już trzy inne mechanizmy (`TryParse`, wartości specjalne, walidacja w konstruktorze). Tabela w kroku 4 zbiera to w całość.
