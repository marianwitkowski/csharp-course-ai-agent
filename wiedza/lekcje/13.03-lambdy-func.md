# Lekcja 13.3 — Lambdy i `Func`

## Cel
Po lekcji uczeń:
- Czyta i pisze wyrażenia lambda: bez parametrów, z jednym, z wieloma, z blokiem
- Wie, że lambda to **wartość** — da się ją przypisać do zmiennej i przekazać
- Używa `Func<>` i `Action<>` jako typów
- Pisze **własną metodę przyjmującą funkcję** jako parametr
- Wie, że lambda pamięta zmienne z otoczenia — i co z tego wynika

> **To lekcja domykająca.** Nic tu nie jest nowe w działaniu — to wyjaśnienie, czym było `x => x > 5` z dwóch poprzednich lekcji.

## Krok 1 — Zakotwiczenie (6 min)

**Pytanie wejściowe:**
> „Napisałeś już kilkanaście zapytań LINQ. Co dokładnie przekazujesz do `Where`?"

Pozwól odpowiedzieć własnymi słowami. Typowo: „warunek", „sprawdzenie".

> „Warunek jest w `if`. To jest coś więcej: **coś, co dostaje wartość i coś zwraca**. Jak to nazwaliśmy w module 7?"

**Co chcesz usłyszeć:** metoda.

> „Czyli przekazujesz do `Where` **metodę**. Nie wynik metody — samą metodę. Skoro tak, to czy metodę da się przypisać do zmiennej?"

Niech uczeń zgadnie. Odpowiedź: tak, i o tym jest ta lekcja.

## Krok 2 — Mostek (12 min)

```csharp
Func<int, int> podwoj = x => x * 2;

Console.WriteLine(podwoj(5));
```
→ `10`

**Pytania:**
- „Co jest po lewej stronie `=`?" → zmienna o typie `Func<int, int>`
- „Co znaczą dwa `int` w nawiasach ostrych?" → **pierwszy to parametr, ostatni to wynik**
- „Jak jej użyłeś?" → nawiasami, dokładnie jak metody

> „`Func<int, int>` to typ. Taki sam typ jak `int` czy `List<string>` — tylko że zmienna tego typu trzyma **działanie**, a nie dane."

Porównaj z metodą z modułu 7:
```csharp
int Podwoj(int x) => x * 2;
```

> „Te dwie rzeczy robią to samo. Pierwsza ma nazwę wpisaną w nagłówek; druga jest **wartością**, którą można przypisać, przekazać dalej albo zwrócić."

Więcej parametrów:
```csharp
Func<int, int, int> dodaj = (a, b) => a + b;
Console.WriteLine(dodaj(2, 3));
```
→ `5`

> „Ile typów w nawiasach ostrych? Który jest wynikiem?"
→ trzy; **ostatni zawsze jest wynikiem**, reszta to parametry.

## Krok 3 — Eksperyment (22 min)

### A. Gdy nic nie zwraca — `Action`

```csharp
Action<string> wypisz = t => Console.WriteLine($"[{t}]");
wypisz("cześć");
```
→ `[cześć]`

> „Czemu nie `Func`?"
→ bo nie ma czego zwracać. **`Func` zwraca wartość, `Action` nie.** To ta sama różnica, co między metodą z typem zwracanym a `void` z lekcji 7.1.

### B. Cztery kształty lambdy

```csharp
Func<bool> zawsze = () => true;                 // bez parametrów
Func<int, int> podwoj = x => x * 2;             // jeden parametr, bez nawiasów
Func<int, int, int> dodaj = (a, b) => a + b;    // wiele parametrów, nawiasy obowiązkowe
Func<int, string> opis = x =>                   // blok, gdy nie mieści się w jednym wyrażeniu
{
    if (x > 10)
    {
        return "duża";
    }

    return "mała";
};

Console.WriteLine(opis(20));
```
→ `duża`

> „Kiedy potrzebujesz klamer?"
→ gdy potrzebujesz więcej niż jednego wyrażenia. **W wersji z klamrami `return` jest obowiązkowy**, w jednolinijkowej — zakazany.

To najczęstsza pomyłka składniowa przy lambdach.

### C. Twoja własna metoda przyjmująca funkcję

To jest sedno lekcji:

```csharp
int Zastosuj(int wartosc, Func<int, int> operacja)
{
    return operacja(wartosc);
}

Console.WriteLine(Zastosuj(4, x => x * 2));
Console.WriteLine(Zastosuj(4, x => x + 100));
```
→ `8` i `104`

**Pytania:**
- „Czy metoda `Zastosuj` wie, co zrobi z liczbą?" → **nie.** Decyduje wywołujący.
- „Gdzie już to widziałeś?" → `Where` też nie wie, co filtrujesz.
- „Co to zmienia?" → jedna metoda obsługuje **nieskończenie wiele** operacji.

Teraz coś bliższego LINQ:
```csharp
List<int> Filtruj(List<int> zrodlo, Func<int, bool> warunek)
{
    List<int> wynik = new List<int>();

    foreach (int x in zrodlo)
    {
        if (warunek(x))
        {
            wynik.Add(x);
        }
    }

    return wynik;
}

Console.WriteLine(string.Join(", ", Filtruj(liczby, x => x > 5)));
```

> „Właśnie napisałeś `Where`. Cały mechanizm z lekcji 13.1 mieści się w tych ośmiu liniach — reszta to odroczone wykonanie i to, że działa na każdej kolekcji."

**Zatrzymaj się tutaj.** To moment, w którym LINQ przestaje być magią.

### D. Zwykła metoda zamiast lambdy

```csharp
bool Duza(int x) => x > 5;

Console.WriteLine(string.Join(", ", liczby.Where(Duza)));
```
→ `12, 20, 8`

> „Nie ma tu żadnej strzałki. Co przekazałeś?"
→ **samą metodę, po nazwie i bez nawiasów.**

> „Nawiasy znaczą »wywołaj i weź wynik«. Bez nawiasów przekazujesz samą metodę."

To domyka wątek z lekcji 1.2, gdzie `Console.ReadLine` bez nawiasów dawał komunikat „czy chcesz wywołać tę metodę".

> „Kiedy warto? Gdy warunek jest długi albo używasz go w kilku miejscach — wtedy ma nazwę i da się go czytać."

### E. Lambda pamięta otoczenie

Lista `liczby` jak w lekcji 13.1: `5, 12, 3, 20, 8`.

```csharp
int prog = 4;
var ponad = liczby.Where(x => x > prog);

prog = 9;

Console.WriteLine(string.Join(", ", ponad));
```
→ `12, 20` — mimo że w chwili pisania `Where` próg wynosił 4. Przy progu 4 wyszłoby jeszcze `5` i `8`.

> „Zapytanie użyło progu 9. Dlaczego?"

Dwie rzeczy naraz:
1. **Odroczone wykonanie** z lekcji 13.1 — lambda wykonała się dopiero przy `string.Join`
2. Lambda trzyma **samą zmienną**, nie jej ówczesną wartość

> „To bywa użyteczne: próg możesz wczytać od użytkownika i zapytanie samo się dostosuje. I bywa pułapką: zmiana zmiennej po napisaniu zapytania cicho zmienia wynik."

Zasada praktyczna:
> „Gdy zapytanie ma korzystać z ustalonej wartości — domknij je przez `ToList` od razu po napisaniu."

## Krok 4 — Pogłębienie (10 min)

**Ściągawka typów**

| Zapis | Znaczenie |
| --- | --- |
| `Action` | nic nie bierze, nic nie zwraca |
| `Action<string>` | bierze tekst, nic nie zwraca |
| `Func<int>` | nic nie bierze, zwraca `int` |
| `Func<int, bool>` | bierze `int`, zwraca `bool` |
| `Func<string, int, bool>` | bierze tekst i `int`, zwraca `bool` |

> „**Ostatni typ w `Func` to zawsze wynik.** To jedyna reguła, którą trzeba zapamiętać."

**Gdzie to widziałeś w LINQ**

| Wywołanie | Typ lambdy |
| --- | --- |
| `Where(x => x > 5)` | `Func<int, bool>` |
| `Select(x => x * 2)` | `Func<int, int>` |
| `Select(u => u.Imie)` | `Func<Uczen, string>` |
| `OrderBy(u => u.Punkty)` | `Func<Uczen, int>` |

> „`Where` zawsze chce lambdy zwracającej `bool` — stąd przy `Where(x => x + 1)` dostajesz `CS0029`: »Nie można niejawnie przekonwertować typu int na bool«."

**Skąd `x`, skoro nigdzie nie podałeś typu?**

> „Kompilator zna typ kolekcji, więc wie, że `x` jest `int`. Da się napisać `(int x) => x > 5`, ale nikt tego nie robi."

**Nazwy parametrów**

> „`x`, `u`, `p` wystarczają, gdy lambda ma jedno wyrażenie i widać całość naraz. W dłuższej lambdzie nazwij sensownie — to zwykły parametr."

**Czego tu nie ma**

> „Lambdy potrafią więcej: `delegate`, zdarzenia, metody rozszerzające pisane samodzielnie. Wszystko to bierze się z tej samej rzeczy — z tego, że działanie jest wartością. Do modułu 14 nie będzie potrzebne."

## Krok 5 — Ćwiczenie

→ Skill `cwiczenie`. Temat: „lambdy i `Func`". Propozycje:

- 🔥 **Rozgrzewka** (`40-lambdy-a.cs`): zdefiniuj `Func<int,int>` podnoszący do kwadratu, `Func<int,int,int>` liczący większą z dwóch liczb, `Action<string>` wypisujący tekst w nawiasach kwadratowych i `Func<int,string>` z blokiem, zwracający `"parzysta"` albo `"nieparzysta"`. Wywołaj każdą.
- ⭐ **Główne** (`40-lambdy-b.cs`): napisz własną metodę `Podsumuj(List<int> dane, Func<int,bool> warunek)`, która zwraca liczbę elementów spełniających warunek. Wywołaj ją z trzema różnymi warunkami. Potem napisz `PrzeksztalcWszystkie(List<int> dane, Func<int,int> operacja)` zwracającą nową listę. Porównaj wyniki z `Count` i `Select`.
- ⚡ **Gwiazdka** (`40-lambdy-c.cs`): prosty kalkulator na słowniku. `Dictionary<string, Func<double,double,double>>`, gdzie kluczem jest `"+"`, `"-"`, `"*"`, `"/"`. Program pyta o dwie liczby i znak działania, wyszukuje operację w słowniku i wykonuje ją. Obsłuż nieznany znak oraz dzielenie przez zero.

Gwiazdka łączy słownik z 6.3, walidację z 2.3 i lambdy — i jest tym rodzajem kodu, w którym `Func` naprawdę się opłaca.

## Pułapki

- **`return` w lambdzie jednolinijkowej** → `CS1525`, „w wyrażeniu występuje nieprawidłowe określenie »return«". `return` jest tylko w wersji z klamrami.
- **Brak `return` na którejś ścieżce lambdy z klamrami** → `CS1643`, „nie dla wszystkich ścieżek w kodzie jest zwracana wartość".
- **Nawiasy przy przekazywaniu metody** — `Where(Duza())` próbuje ją wywołać zamiast przekazać: `CS7036`, „nie podano argumentu odpowiadającego wymaganemu parametrowi".
- **Zły typ wyniku w `Where`** → `CS0029`; `Where` wymaga `bool`.
- **Zmiana zmiennej użytej w lambdzie** cicho zmienia wynik odroczonego zapytania.
- **`Action` tam, gdzie potrzebny `Func`** — jeśli musisz coś zwrócić, `Action` się nie skompiluje.
- **Zbyt długa lambda** — powyżej kilku linii zrób z niej zwykłą metodę z nazwą.

## Notatki tutora

- **Krok 3.C to serce lekcji.** Dopóki uczeń nie napisze własnego `Filtruj`, LINQ pozostaje magią. Nie skracaj tego kroku.
- **Nie tłumacz `delegate`.** Wystarczy, że `Func` i `Action` to gotowe typy.
- **Nie wprowadzaj zdarzeń (`event`) ani `+=` na funkcjach.**
- **Nie nazywaj tego »programowaniem funkcyjnym«.** Nazwa nic tu nie wnosi, a otwiera wątek na godzinę.
- **Krok 3.E może zdezorientować.** Jeśli uczeń się gubi — pokaż wersję z `ToList` tuż po `Where` i porównaj wyniki. Zrozumienie „dlaczego" jest ważniejsze niż zapamiętanie nazwy.
