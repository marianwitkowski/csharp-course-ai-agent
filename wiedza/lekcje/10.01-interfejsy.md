# Lekcja 10.1 — Interfejs jako kontrakt

## Cel
Po lekcji uczeń:
- Definiuje interfejs i implementuje go w klasie
- Implementuje **kilka interfejsów naraz** — czyli obchodzi limit z lekcji 9.1
- Rozumie, że interfejs mówi **co**, a klasa **jak**
- Trzyma różne, niespokrewnione klasy w jednej kolekcji typu interfejsu
- Rozpoznaje `CS0535` i `CS0737`

> **Ta lekcja odpowiada na `CS1721` z 9.1:** klasa może dziedziczyć po jednej klasie, ale rzecz bywa dwiema rzeczami naraz.

## Krok 1 — Zakotwiczenie (5 min)

**Pytanie wejściowe:**
> „Co łączy długopis, ołówek, kredę i palec umoczony w farbie?"

**Co chcesz usłyszeć:** wszystkim można pisać. Nie wyglądem, nie budową — **tym, co potrafią**.

**Drugie pytanie:**
> „Czy kreda jest rodzajem długopisu? A długopis rodzajem kredy?"

**Co chcesz usłyszeć:** nie i nie. To **nie jest** rodzina — test „jest rodzajem" z lekcji 9.1 tu nie przechodzi.

**Trzecie pytanie:**
> „A jednak coś je łączy. Jak to nazwać, skoro nie są rodziną?"

**Co chcesz usłyszeć:** wspólna umiejętność, wspólne zobowiązanie. **To jest interfejs** — nie nazywaj jeszcze.

**Czwarte pytanie:**
> „Kreda dodatkowo daje się ścierać. Czy to samo co pisanie?"

Nie. Kreda ma **dwie** niezależne umiejętności — i to jest odpowiedź na limit z 9.1.

## Krok 2 — Mostek (12 min)

Przypomnij problem z lekcji 9.1:
```csharp
class Dziwo : Kot, Pies { }
```
→ `CS1721: Class 'Dziwo' cannot have multiple base classes`

> „Klasa może mieć jedną bazę. A co, gdy coś naprawdę potrafi dwie niezwiązane rzeczy?"

**Mostek:**
> „Lista umiejętności, bez ani jednej linii wykonania, nazywa się **interfejsem**. Klasa może zadeklarować dowolnie wiele interfejsów — bo nie dziedziczy po nich niczego do wykonania, tylko **zobowiązuje się**, że to potrafi."

Uczeń tworzy `kurs/zadania/29-interfejsy.cs`:

```csharp
Dlugopis d = new Dlugopis();
Console.WriteLine(d.Pisz("cześć"));

interface IPiszacy
{
    string Pisz(string tekst);
}

class Dlugopis : IPiszacy
{
    public string Pisz(string tekst) => $"długopis: {tekst}";
}
```
→ `długopis: cześć`

**Pytania:**
- „Co jest w interfejsie? A czego w nim nie ma?"
  → są **nagłówki metod**, nie ma ani jednego ciała. Metoda kończy się średnikiem.
- „Czym to przypomina klasę abstrakcyjną z 9.3?"
  → tam też były metody bez ciała. Różnicę zobaczysz w kroku 4.
- „Czemu nazwa zaczyna się od `I`?"
  → to konwencja C#: `IPiszacy`, `IComparable`, `IDisposable`. Nie wymóg języka, ale wszyscy się jej trzymają.

Nazwij: **interfejs**, **implementacja interfejsu**, **kontrakt**.

> **Interfejs mówi CO trzeba umieć. Klasa mówi JAK to robi.**

## Krok 3 — Eksperyment (25 min)

### A. Kompilator pilnuje kontraktu

```csharp
class Olowek : IPiszacy
{
}
```
→ `CS0535: 'Olowek' does not implement interface member 'IPiszacy.Pisz(string)'`

> „Zadeklarowałeś, że ołówek pisze, i nie napisałeś jak. Co odpowiedział kompilator?"

To ta sama zasada co `CS0534` przy klasie abstrakcyjnej z 9.3 — **deklaracja zobowiązuje**.

### B. Implementacja musi być `public`

```csharp
class Olowek : IPiszacy
{
    string Pisz(string tekst) => $"ołówek: {tekst}";
}
```
→ `CS0737: 'Olowek' does not implement interface member 'IPiszacy.Pisz(string)'. 'Olowek.Pisz(string)' cannot implement an interface member because it is not public.`

> „Pamiętasz z 8.4, że w klasie wszystko jest domyślnie prywatne? Tu to przeszkadza. Czemu?"
→ bo interfejs to **obietnica dana światu**. Metoda prywatna nie może jej spełnić.

### C. Dwa interfejsy naraz — odpowiedź na limit z 9.1

```csharp
interface IScieralny
{
    string Sciera();
}

class Kreda : IPiszacy, IScieralny
{
    public string Pisz(string tekst) => $"kreda: {tekst}";
    public string Sciera() => "starte";
}
```

```csharp
Kreda k = new Kreda();
Console.WriteLine(k.Pisz("x"));
Console.WriteLine(k.Sciera());
```
→ `kreda: x` i `starte`

> „Ile klas bazowych ma `Kreda`? Ile interfejsów?"
→ zero baz, dwa interfejsy. **I to jest legalne**, w przeciwieństwie do dwóch klas bazowych.

> „Czemu C# na to pozwala, skoro na dwie klasy bazowe nie?"
→ bo z dwóch klas bazowych trzeba by odziedziczyć **dwa różne ciała** tej samej metody i nie wiadomo które. Interfejsy w tej postaci nie mają ciał — nie ma czego mylić.

> **Dla ścisłości, jedno zdanie i dalej:** w podstawowej postaci, której używamy, interfejs opisuje kontrakt **bez** implementacji. Współczesny C# pozwala też umieścić w interfejsie pewne implementacje — to temat zaawansowany, poza kursem; jeśli uczeń zobaczy to w cudzym kodzie, ma wiedzieć, że to nadal interfejs.

**To jest domknięcie `CS1721`.** Zatrzymaj się i powiedz to wprost.

### D. Polimorfizm bez wspólnej rodziny

```csharp
IPiszacy[] rzeczy = { new Dlugopis(), new Kreda(), new Olowek() };

foreach (IPiszacy r in rzeczy)
{
    Console.WriteLine(r.Pisz("test"));
}
```

> „Jakiego typu jest ta tablica? Czy te trzy klasy mają wspólną klasę bazową?"
→ typu **interfejsu**; wspólnej bazy **nie mają**.

To jest różnica wobec `List<Zwierze>` z lekcji 9.2: tam wszystko było zwierzęciem. Tu nic nie jest niczyim rodzajem — łączy je **umiejętność**.

> „Co możesz zrobić z elementem tej tablicy?"
→ tylko to, co obiecuje interfejs. `r.Sciera()` nie skompiluje się, nawet gdy w środku siedzi kreda — bo zmienna jest typu `IPiszacy`.

To ta sama zasada co w 9.2 krok 3.F: **typ zmiennej ogranicza, co wolno**.

### E. Interfejsu nie da się utworzyć

```csharp
IPiszacy p = new IPiszacy();
```
→ `CS0144: Cannot create an instance of the abstract type or interface 'IPiszacy'`

> „Ten sam komunikat co przy klasie abstrakcyjnej z 9.3. Czemu?"
→ bo interfejs też jest tylko **opisem**, nie konkretem. Zmienna może być tego typu; obiekt nie.

### F. Interfejs jako parametr metody

```csharp
void Napisz(IPiszacy narzedzie, string tekst)
{
    Console.WriteLine(narzedzie.Pisz(tekst));
}

Napisz(new Dlugopis(), "raz");
Napisz(new Kreda(), "dwa");
```

> „Czego wymaga ta metoda od swojego argumentu?"
→ **tylko tego, żeby umiał pisać.** Nie obchodzi jej, czym jest.

> „Co się stanie, gdy za rok dopiszesz klasę `Pisak`?"
→ nic. Metoda `Napisz` będzie działać bez zmian.

**To jest najważniejsze praktyczne zastosowanie interfejsów** i warto na nim zatrzymać się dłużej niż na składni.

## Krok 4 — Pogłębienie (10 min)

**Interfejs czy klasa abstrakcyjna?**

| | interfejs | klasa abstrakcyjna |
| --- | --- | --- |
| ciała metod | brak w podstawowej postaci (współczesny C# dopuszcza — poza kursem) | mogą być |
| pola | **nie** | tak |
| konstruktor | nie | tak |
| ile na klasę | dowolnie wiele | **jedna** |
| odpowiada na pytanie | „co potrafi?" | „czym jest?" |

> „Reguła praktyczna: **klasa abstrakcyjna, gdy dzielisz kod. Interfejs, gdy dzielisz tylko zobowiązanie.**"

> „A gdy potrzebujesz obu? Klasa może mieć jedną bazę **i** kilka interfejsów: `class Kreda : Przybor, IPiszacy, IScieralny`. Baza zawsze pierwsza."

**Nazewnictwo**

| Element | Konwencja | Przykład |
| --- | --- | --- |
| interfejs | `I` + `PascalCase` | `IPiszacy`, `IComparable` |
| często przymiotnik lub „-able" | | `IScieralny`, `IDisposable` |

> „Litera `I` na początku nie jest wymogiem języka — ale w C# trzymają się jej wszyscy i kod bez niej wygląda obco."

**Co jeszcze może być w interfejsie**

Poza metodami: **właściwości**.

```csharp
interface IOpisany
{
    string Nazwa { get; }
}
```
> „Interfejs mówi, że nazwa ma być do odczytania. Nie mówi, skąd się bierze — klasa może ją trzymać w polu albo liczyć."

**Czego interfejs nie da**

- nie ma pól — nie przechowa danych
- nie ma konstruktora — nie zbuduje obiektu
- nie ma domyślnej implementacji (nowsze C# na to pozwala, ale **kurs tego nie używa**)

> „Jeśli twój interfejs chce mieć pole, prawdopodobnie potrzebujesz klasy abstrakcyjnej."

## Krok 5 — Ćwiczenie

→ Skill `cwiczenie`. Temat: „interfejsy". Propozycje:

- 🔥 **Rozgrzewka** (`29-interfejsy-a.cs`): interfejs `IGrajacy` z metodą `Zagraj()`. Trzy klasy: `Gitara`, `Pianino`, `Bebenek` — każda gra inaczej. Wrzuć je do tablicy `IGrajacy[]` i zagraj wszystkim jedną pętlą.
- ⭐ **Główne** (`29-interfejsy-b.cs`): interfejsy `IZapisywalny` (`string DoTekstu()`) i `IWalidowalny` (`bool CzyPoprawny()`). Klasa `Faktura` implementuje **oba**, klasa `Notatka` — tylko pierwszy. Napisz metodę `void Zapisz(IZapisywalny co)` i wywołaj ją dla obu. Potem napisz metodę, która przyjmuje `IWalidowalny` i sprawdź, czy da się jej podać `Notatke` — wklej mi komunikat.
- ⚡ **Gwiazdka** (`29-interfejsy-c.cs`): system płatności. Interfejs `IPlatnosc` z `bool Zaplac(decimal kwota)` i właściwością `Nazwa`. Trzy implementacje: `Karta` (odrzuca kwoty powyżej limitu), `Blik` (odrzuca kwoty ujemne), `Gotowka` (zawsze przyjmuje). Napisz metodę `void Rozlicz(IPlatnosc metoda, decimal kwota)` wypisującą wynik. Przetestuj sześć przypadków. Potem dopisz **czwartą** metodę płatności i policz, ile linii istniejącego kodu zmieniłeś.
- 🔧 **Naprawa** (`wiedza/przyklady/zepsute/29-interfejsy-zepsute.cs`): program **nie kompiluje się** — `CS0535`. Metoda z tą nazwą jest w klasie. Przeczytaj komunikat do końca, napraw i policz, ile znaków dzieliło kod od poprawnego.

Ostatnie pytanie gwiazdki ma odpowiedź **zero** — to samo, co w ćwiczeniu 9.2, ale tym razem bez żadnej wspólnej klasy bazowej.

## Pułapki

- **Brak implementacji** → `CS0535`. Kompilator wymienia, czego brakuje.
- **Implementacja bez `public`** → `CS0737`. W klasie domyślnie prywatne, a interfejs wymaga publicznego.
- **`new` na interfejsie** → `CS0144`.
- **Ciało metody w interfejsie** — w tym kursie nie piszemy. Metoda kończy się średnikiem.
- **Pole w interfejsie** → błąd. Interfejs nie przechowuje danych.
- **Sięganie po metodę spoza interfejsu** przez zmienną typu interfejsu → `CS1061`. Typ zmiennej ogranicza.
- **Kolejność przy dziedziczeniu i interfejsach** — klasa bazowa musi być **pierwsza**: `class A : Baza, IX, IY`.
- **Interfejs bez `I`** — działa, ale każdy czytający się potknie.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)

Interfejsy działają w C# tak samo od pierwszej wersji, z jednym wyjątkiem: **od C# 8 interfejs może mieć domyślną implementację metody**. Wygląda to jak metoda z ciałem w interfejsie.

**Kurs tego nie używa** i uczeń nie powinien tego pisać: zaciera różnicę między interfejsem a klasą abstrakcyjną, a rozwiązuje problem, którego początkujący nie ma. Jeśli trafi na to w internecie — „to nowsza możliwość, my zostajemy przy interfejsach bez ciał".

## Notatki tutora

- **Krok 3.C domyka `CS1721` z lekcji 9.1.** Uczeń widział wtedy, że dwie klasy bazowe są zakazane, i usłyszał „do tego są interfejsy, moduł 10". To jest ten moment.
- **Krok 3.F jest ważniejszy niż cała składnia.** Metoda przyjmująca interfejs działa z klasami, które jeszcze nie istnieją — to jest powód, dla którego interfejsy są w C# wszędzie.
- **Krok 1 celowo obala test „jest rodzajem" z 9.1.** Uczeń ma zobaczyć, że długopis i kreda **nie są** rodziną, a mimo to coś je łączy. Bez tego interfejs wygląda na „gorszą klasę bazową".
- **Nie wprowadzaj `IComparable` ani `IEnumerable`.** To lekcja 10.2, następna.
- **Nie wprowadzaj kompozycji.** To 10.3.
- **Nie wprowadzaj domyślnych implementacji w interfejsach.** Jedno zdanie w sekcji Aktualizacja, jeśli uczeń zapyta.
- **Nie tłumacz jawnej implementacji interfejsu** (`string IPiszacy.Pisz(...)`). Poza kursem.
- Jeśli uczeń pyta, czy interfejs może dziedziczyć po interfejsie — tak, i to normalne. Ale nie buduj z tego hierarchii; jeden poziom wystarczy.
