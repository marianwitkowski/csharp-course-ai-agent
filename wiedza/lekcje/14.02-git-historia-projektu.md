# Lekcja 14.2 — Git: historia projektu

> **Lekcja o narzędziu, nie o języku.** Nie ma tu ani jednej nowej linii C#. Jest jedna umiejętność, bez której program napisany w 14.3 będzie istniał tylko w jednej wersji — tej ostatniej, nawet jeśli poprzednia działała lepiej.

## Cel
Po lekcji uczeń:
- Zakłada repozytorium Git dla swojego projektu i wie, **gdzie** je założyć i dlaczego
- Czyta `git status` i rozróżnia: plik nieśledzony, zmieniony, przygotowany do zapisu
- Zapisuje stan projektu commitem z sensownym opisem i ogląda historię przez `git log`
- Widzi, **co dokładnie** zmienił od ostatniego zapisu (`git diff`), i umie tę zmianę cofnąć (`git restore`)
- Wie, co do historii **nie** trafia (`bin/`, `obj/`, plik z danymi) i jak to zapewnić przez `.gitignore`

## Krok 1 — Zakotwiczenie (5 min)

**Pytanie wejściowe:**
> „Masz na dysku plik `praca_v2_final_NAPRAWDE_ostatnia.docx`. Skąd się wziął i co z nim jest nie tak?"

**Co chcesz usłyszeć:** to kopie robione „na wszelki wypadek" przed zmianą. Nie wiadomo, czym `v2` różni się od `final`, ani która wersja była dobra.

**Drugie pytanie:**
> „Wczoraj twój program działał. Dziś przez godzinę coś w nim zmieniałeś i przestał. Jak wrócisz do wczorajszej wersji?"

**Co chcesz usłyszeć:** nie da się — chyba że zrobiłem kopię. A kopia nie mówi, co się zmieniło.

> „To są dwa problemy naraz: **nie masz poprzednich wersji** i **nie wiesz, co między nimi zmieniłeś**. Dziś rozwiążesz oba jednym narzędziem."

## Krok 2 — Mostek (12 min)

**Mostek:**
> „**Git** to program, który trzyma **historię katalogu**: każdy zapisany stan z datą, autorem i jednym zdaniem opisu. Taki zapisany stan nazywa się **commit**. Zamiast kopii `v2_final` masz listę commitów i możesz spojrzeć na dowolny z nich albo do niego wrócić."

### A. Czy Git jest zainstalowany

```sh
git --version
```
→ `git version 2.39.5 (Apple Git-154)` — numer u ciebie może być inny, ważne, że jest.

Jeśli komenda nie istnieje:

| System | Jak zainstalować |
| --- | --- |
| macOS | `xcode-select --install` (system sam zaproponuje instalację narzędzi) |
| Windows | https://git-scm.com/download/win — instalator, wszystkie opcje domyślne |
| Linux | `sudo apt install git` (Debian/Ubuntu) albo odpowiednik twojej dystrybucji |

### B. Trzy ustawienia, raz na komputer

```sh
git config --global user.name "Anna Nowak"
git config --global user.email "anna@example.com"
git config --global init.defaultBranch main
```

> „Po co Git chce znać twoje imię?"
→ każdy commit ma **autora**. Gdy za pół roku spytasz „kto to napisał", odpowiedź ma być w historii, nie w pamięci.

Trzecia linia: główna linia historii ma się nazywać `main`. Bez tego ustawienia na niektórych systemach nazywa się `master` — to samo, inna nazwa, ale komendy w tej i następnych lekcjach zakładają `main`.

**Komendy `git` mówią po angielsku** i nie tłumaczą się na język systemu, w przeciwieństwie do `dotnet`. Wszystkie komunikaty w tej lekcji są więc angielskie; dla wyniku `dotnet new gitignore` zobaczysz polski — to jedyny polski komunikat tutaj.

### C. Gdzie założyć repozytorium — i dlaczego tam

```sh
cd kurs/projekt
pwd
```

> „Masz tu `README.md` i katalog `zadania/`. W lekcji 14.4 obok `zadania/` stanie **drugi** katalog — projekt testowy. Gdzie założysz historię, żeby objęła oba?"
→ w `kurs/projekt/`, katalog **wyżej** niż aplikacja. Historia obejmuje wszystko poniżej.

```sh
git init
```
→ `Initialized empty Git repository in /Users/anna/Projects/claude-agent-csharp-course/kurs/projekt/.git/` (z twoją ścieżką)

> „Co powstało? Wpisz `ls -a`."
→ katalog `.git/`. Tam Git trzyma całą historię. **Nie zaglądaj tam i nic w nim nie zmieniaj** — jedyne, co masz z nim robić, to nie skasować go przypadkiem.

## Krok 3 — Eksperyment (25 min)

### A. `git status` — co Git widzi

```sh
git status
```
→
```
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md
	zadania/

nothing added to commit but untracked files present (use "git add" to track)
```

> „`Untracked` — nieśledzone. Git widzi te pliki, ale **jeszcze ich nie pilnuje**. Zanim je dodasz: zajrzyj do `zadania/`. Wpisz `ls zadania`."
→ `Program.cs`, `Zadanie.cs`, `zadania.csproj`, a obok **`bin`** i **`obj`**.

> „Które z tych pięciu rzeczy są twoim projektem, a które powstały same przy budowaniu?"
→ trzy pliki są projektem. `bin/` i `obj/` zrobił `dotnet` przy budowaniu — to lekcja 14.1.

> „Czy `bin/` i `obj/` mają trafić do historii?"
→ nie: powstają na nowo przy każdym `dotnet run`, ważą więcej niż cały kod i **zmieniają się przy każdym uruchomieniu**, więc historia byłaby zaśmiecona zmianami, których nie zrobiłeś.

Żeby zobaczyć, ile tego jest:
```sh
git status -u --short | wc -l
```
→ liczba rzędu **28** — przy czterech plikach, które naprawdę są twoje.

### B. `.gitignore` — czego Git ma nie widzieć

```sh
dotnet new gitignore
```
→ `Pomyślnie utworzono szablon "plik dotnet gitignore".`

Powstał plik `.gitignore`. Otwórz go w edytorze i znajdź linie:
```
[Bb]in/
[Oo]bj/
```

> „Co znaczy `[Bb]in/`?"
→ katalog o nazwie `bin` albo `Bin`, gdziekolwiek w projekcie. Git ma go **nie widzieć**.

```sh
git status -u --short
```
→
```
?? .gitignore
?? README.md
?? zadania/Program.cs
?? zadania/Zadanie.cs
?? zadania/zadania.csproj
```

> „Z dwudziestu ośmiu zostało pięć. Które?"
→ dokładnie te, które są twoją pracą — plus sam `.gitignore`, bo lista ignorowanych rzeczy też jest częścią projektu.

> „`.gitignore` ma ponad czterysta linii, a ciebie obchodzą dwie. Reszta to Visual Studio, Rider i narzędzia, których nie używasz. Zostaw — nie przeszkadza, a jeśli kiedyś sięgniesz po któreś z nich, będzie gotowe."

### C. `git add` i pierwszy commit

Zapis stanu to **dwa kroki**: najpierw mówisz, **które** pliki wchodzą do zapisu, potem robisz zapis.

```sh
git add .
git status
```
→
```
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   .gitignore
	new file:   README.md
	new file:   zadania/Program.cs
	new file:   zadania/Zadanie.cs
	new file:   zadania/zadania.csproj
```

> „Kropka w `git add .` — co znaczy?"
→ bieżący katalog, czyli wszystko poniżej. Git sam pominął to, co jest w `.gitignore`.

> „`Changes to be committed` — przygotowane do zapisu, ale **jeszcze nie zapisane**. Zapis:"

```sh
git commit -m "Szkielet projektu: klasa Zadanie"
```
→
```
[main (root-commit) bff16c3] Szkielet projektu: klasa Zadanie
 5 files changed, 504 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 README.md
 create mode 100644 zadania/Program.cs
 create mode 100644 zadania/Zadanie.cs
 create mode 100644 zadania/zadania.csproj
```

**Rozbierz tę pierwszą linię pytaniami:**
- „`main` — co to?" → nazwa linii historii, z ustawienia w kroku 2.B
- „`root-commit`?" → pierwszy commit, korzeń historii. Tylko ten jeden będzie tak oznaczony
- „`bff16c3`?" → **identyfikator** commita. U ciebie inny — to skrót z odcisku zawartości, nie numer kolejny. Git nie liczy commitów 1, 2, 3; rozpoznaje je po tych skrótach
- „`504 insertions`, przy czterech krótkich plikach?" → `.gitignore` ma ponad czterysta linii. Zgadza się

> „`-m` to opis commita. **Zawsze** go podawaj — bez `-m` Git otworzy edytor tekstu w terminalu i będzie czekał, aż wpiszesz opis w środku. Jeśli ci się to zdarzy i utkniesz w edytorze o nazwie `vim`: wpisz `:q!` i Enter."

```sh
git status
```
→
```
On branch main
nothing to commit, working tree clean
```

> „`working tree clean` — katalog zgadza się z ostatnim zapisem. To zdanie, które chcesz widzieć na koniec każdej sesji."

### D. Zmiana, `git diff`, drugi commit

Uczeń dopisuje do `Zadanie.cs` właściwość `Id` — ta z kroku 4 lekcji 14.1 — i uwzględnia ją w `ToString`:

```csharp
public class Zadanie
{
    public int Id { get; set; }
    public string Opis { get; set; } = "";
    public bool Zrobione { get; set; }

    public override string ToString() => $"[{(Zrobione ? "x" : " ")}] {Id}. {Opis}";
}
```

```sh
git status
```
→
```
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   zadania/Zadanie.cs

no changes added to commit (use "git add" and/or "git commit -a")
```

> „Trzeci stan pliku. Był `untracked`, był `new file`, teraz jest `modified`. Co to znaczy?"
→ Git go pilnuje i widzi, że różni się od ostatniego zapisu.

> „A **co** się różni? Nie zgaduj — zapytaj:"

```sh
git diff
```
→
```
diff --git a/zadania/Zadanie.cs b/zadania/Zadanie.cs
index f8a930b..0359973 100644
--- a/zadania/Zadanie.cs
+++ b/zadania/Zadanie.cs
@@ -1,7 +1,8 @@
 public class Zadanie
 {
+    public int Id { get; set; }
     public string Opis { get; set; } = "";
     public bool Zrobione { get; set; }
 
-    public override string ToString() => $"[{(Zrobione ? "x" : " ")}] {Opis}";
+    public override string ToString() => $"[{(Zrobione ? "x" : " ")}] {Id}. {Opis}";
 }
```

> „Czytaj tylko linie z `+` i `-`. Co dodałeś, co usunąłeś?"
→ jedna linia dodana; jedna linia zamieniona na nową (stara z `-`, nowa z `+`). Linie bez znaku to kontekst — Git pokazuje je, żebyś wiedział, **gdzie** w pliku to jest.

> „To jest odpowiedź na drugie pytanie z kroku 1. Nie musisz pamiętać, co zmieniłeś od wczoraj — `git diff` pamięta."

Zapis — tym razem jedną komendą, bo plik jest już śledzony:
```sh
git commit -am "Zadanie dostaje Id"
```
→
```
[main bab02bb] Zadanie dostaje Id
 1 file changed, 2 insertions(+), 1 deletion(-)
```

> „`-a` znaczy: dołącz wszystkie **śledzone** pliki, które się zmieniły. Uwaga na słowo »śledzone« — **nowy** plik `-a` nie złapie, jego trzeba raz dodać przez `git add`."

### E. Historia

```sh
git log --oneline
```
→
```
bab02bb Zadanie dostaje Id
bff16c3 Szkielet projektu: klasa Zadanie
```

> „W jakiej kolejności? Najnowszy na górze czy na dole?"
→ na górze. Historia rośnie ku górze.

Pełny wpis jednego commita:
```sh
git log -1
```
→
```
commit bab02bb7c092f25069b37a4e2f894261a5d24439
Author: Anna Nowak <anna@example.com>
Date:   Wed Sep 2 15:46:49 2026 +0200

    Zadanie dostaje Id
```

> „Skąd wziął się autor i data?"
→ z kroku 2.B i z zegara. Nie wpisywałeś ich — Git wpisał je za ciebie.

> „Skrót `bab02bb` to pierwsze siedem znaków tego długiego identyfikatora. Siedem zwykle wystarcza, żeby był jednoznaczny."

### F. Cofnięcie zmiany — po co to wszystko

Niech uczeń **celowo zepsuje** `Zadanie.cs`: skasuje połowę pliku, wpisze cokolwiek, zapisze.

```sh
git status --short
```
→ ` M zadania/Zadanie.cs`

> „Plik jest zepsuty. Ostatni commit — nie. Jak wrócić?"

```sh
git restore zadania/Zadanie.cs
git status
```
→
```
On branch main
nothing to commit, working tree clean
```

> „Otwórz plik w edytorze. Co w nim jest?"
→ wersja z ostatniego commita, z `Id`. Zepsuta wersja zniknęła — **bez śladu i bez pytania**.

> „To jest odpowiedź na pierwsze pytanie z kroku 1: poprzednia wersja **istnieje**, bo ją zapisałeś. `git restore` cofa plik do ostatniego commita. Jeśli czegoś nie zapisałeś commitem, `restore` tego nie odzyska — dlatego commit robi się **po każdym działającym kroku**, nie na koniec dnia."

## Krok 4 — Pogłębienie (8 min)

**Co trafia do historii, a co nie**

| Do historii | Poza historią |
| --- | --- |
| kod źródłowy (`.cs`) | `bin/`, `obj/` — odtwarzalne z kodu |
| `.csproj` | plik z danymi programu (`zadania.json`) — to **treść użytkownika**, nie kod |
| `README.md` | hasła, klucze, tokeny — **nigdy**, nawet „na chwilę" |
| `.gitignore` | to, czego nie umiałbyś opisać w commicie |

> „Plik z danymi: gdy twój program zapisze `zadania.json`, `git status` pokaże go jako nowy. Czy twoja lista zakupów jest częścią programu?"
→ nie. To ćwiczenie ⚡ dzisiaj.

**Opis commita — jedno zdanie o tym, co się zmieniło**

Dobre: `Zadanie dostaje Id`, `Zapis listy do JSON`, `Brak pliku daje pustą listę zamiast wyjątku`.
Złe: `zmiany`, `poprawki`, `działa`, `asdf`.

> „Test: czy za miesiąc, czytając samo `git log --oneline`, będziesz wiedział, w którym commicie szukać?"

**Kiedy commit**

Cykl z lekcji 14.3 dostaje szósty punkt: **działa → `dotnet build` bez ostrzeżeń → commit → następny kawałek**. Sesja projektowa kończy się zawsze na `working tree clean`.

> „Nie commituj kodu, który się nie kompiluje. Commit to punkt, do którego chcesz móc wrócić — do zepsutego wracać nie warto."

**Dwa kroki (`add` + `commit`), skoro jest `-a`?**

> „`add` pozwala zapisać **część** zmian: poprawiłeś dwie rzeczy naraz, chcesz dwa osobne commity. Na razie `-am` wystarcza; `add` z nazwą pliku przyda się, gdy zaczniesz robić za dużo naraz."

**Podejrzenie o historię — `git show`**

```sh
git show --stat HEAD
```
→ opis, autor, data i lista plików ostatniego commita. `HEAD` znaczy „ostatni commit"; `HEAD~1` — ten przed nim. `git diff HEAD~1 HEAD` pokaże, co się zmieniło między nimi.

→ Skill `cwiczenie`. Temat: „historia projektu". Wszystko w `kurs/projekt/`, na własnym projekcie ucznia — **żadnych plików w `kurs/zadania/`**.

- 🔥 **Rozgrzewka**: `git log --oneline` pokazuje co najmniej dwa commity, a `git status` kończy się `working tree clean`. Wklej oba wyniki.
- ⭐ **Główne**: dopisz do `README.md` sekcję „Historia" z jednym zdaniem, po co ci Git. Zanim zrobisz commit, pokaż `git diff` i powiedz, ile linii ma `+`. Zrób commit z opisem, który mówi, co się zmieniło. Potem **zepsuj `Program.cs`** tak, żeby się nie kompilował, sprawdź to przez `dotnet build`, i cofnij jedną komendą Gita. Pokaż `git status` po cofnięciu.
- ⚡ **Gwiazdka**: utwórz ręcznie w `zadania/` plik `zadania.json` z zawartością `[]` — to plik, który twój program będzie zapisywał w 14.3. `git status --short` ma pokazać `?? zadania/zadania.json`. Dopisz do `.gitignore` linię, po której ten plik **zniknie** ze `git status`, a pojawi się tylko ` M .gitignore`. Zrób commit. Odpowiedz w jednym zdaniu w `README.md`: dlaczego danych programu nie ma w historii, a `.gitignore` jest.

Gwiazdka jest prawdziwym problemem z 14.3: pierwszy `dotnet run -- dodaj` stworzy plik danych i uczeń, który tego nie przewidział, zacommituje swoją listę zakupów.

## Pułapki

- **`git init` w `zadania/` zamiast w `kurs/projekt/`** — działa dziś, a w 14.4 projekt testowy zostaje poza historią i nikt tego nie zauważy do 14.5. Sprawdź `pwd` przed `init`.
- **`git status` przed `git init` coś pokazuje** — to repozytorium **kursu** (`claude-agent-csharp-course` jest w Gicie, a `kurs/projekt/` ma w nim ignorowany). Po twoim `git init` w `kurs/projekt/` komendy dotyczą już twojej historii, nie kursu. Jeśli uczeń pobrał kurs jako ZIP, tego efektu nie ma.
- **Commit bez ustawionego imienia** — na macOS Git zgadnie je z nazwy użytkownika i ostrzeże, na Linuksie i Windows odmówi zapisu i każe ustawić. Krok 2.B załatwia to raz.
- **`git commit` bez `-m`** → otwiera się edytor w terminalu. `:q!` i Enter wychodzi z `vim` bez zapisu; potem powtórz z `-m`.
- **`-am` nie widzi nowych plików** — `git status` pokaże je jako `Untracked` po commicie. `git add .` i jeszcze jeden commit.
- **`bin/` i `obj/` już w historii**, bo `git add .` poszło przed `dotnet new gitignore`: `git rm -r --cached zadania/bin zadania/obj`, potem commit. Pliki z dysku nie znikają — znikają z historii.
- **`git restore` nie pyta.** Cofnięta zmiana przepada. Zanim cofniesz, `git diff` — może tam było coś, co chcesz zachować.
- **Gałąź nazywa się `master`, nie `main`** — brak ustawienia `init.defaultBranch` z kroku 2.B. Dla tej lekcji bez różnicy; ustaw je teraz, żeby 14.5 się zgadzało.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)

Sekcja `[moduł 14]` nie obejmuje Gita — kontrola wersji nie należy do .NET i zmieniła się niewiele. Dwie rzeczy, które uczeń zobaczy w starszych poradnikach:

| Stare poradniki | Dzisiaj |
| --- | --- |
| `git checkout -- plik` do cofnięcia zmiany | `git restore plik` (od Gita 2.23) |
| główna gałąź `master` | `main` — nowe repozytoria na GitHubie i to ustawienie z kroku 2.B |

`git checkout` nadal działa i robi kilka rzeczy naraz; `restore` i `switch` (14.5) robią po jednej i dlatego kurs uczy ich.

## Notatki tutora

- **Nie wykonuj za ucznia `add`, `commit` ani `restore`.** Zasada z całego kursu: agent czyta, uczeń wpisuje i wkleja. Wolno ci `git status`, `git log --oneline` i `git diff` w `kurs/projekt/`, gdy uczeń utknął i trzeba zobaczyć stan — powiedz wtedy, że to robisz.
- **Krok 3.F jest sercem lekcji.** Uczeń ma **zobaczyć**, jak zepsuty plik wraca do wersji z commita. Bez tego Git zostaje rytuałem „bo tak się robi".
- **Nie tłumacz, jak Git działa w środku** (obiekty, drzewa, skróty SHA). Jedno zdanie o identyfikatorze w kroku 3.C wystarcza.
- **Nie wprowadzaj gałęzi ani GitHuba.** To 14.5. Jeśli uczeń pyta o GitHub — „miejsce w sieci, gdzie kładzie się takie repozytorium; lekcja 14.5".
- **Nie wprowadzaj `git stash`, `reset`, `rebase`, `cherry-pick`.** Uczeń dostaje pięć komend i wystarczy: `status`, `add`, `commit`, `diff`, `restore`, do tego `log`.
- **Uczeń na Windows:** `ls -a` → `dir /a`, ale komendy `git` identyczne. Podczas `git add` może pojawić się ostrzeżenie o `LF will be replaced by CRLF` — nieszkodliwe, jedno zdanie: „Windows i macOS inaczej kończą linie, Git to wyrównuje".
- Jeśli uczeń ma już `.git` w `kurs/projekt/zadania/` z własnych prób — `rm -rf zadania/.git` jest wyjątkiem od zakazu kasowania, ale **uczeń robi to sam** po tym, jak wyjaśnisz, że kasuje historię, nie kod.
